//?play and the playground

?play and the playground

The ?play bot runs a rawr snippet posted in Discord and replies with the result. The playground does the same in a browser. Neither needs anything installed.

This page is a reference for both. It covers how a snippet is read and what it may touch. It covers the clock an app runs on and when the reply is a PNG or a GIF. It also lists the limits, the ways ?play differs from rawr run and every note the bot can print.

In Discord

Write ?play on the first line of a message and put the snippet in a code block below it. The fence can be ```rust, ```rs or a bare ```. The bot also answers when ?play is in the fence’s info string, as in ```rust ?play.

Discord
?play 320x200 light msg=Message::Increment
```rust
column![text("hi"), button("go")]
```

The bot runs the first code block in the message. A snippet that uses iced gets an image. A plain program gets its output in a text block. An error gets the report that rawr check would print. The report names the snippet play.rs. The bot cuts an error reply to fit Discord’s 2000 characters.

The bot shows Discord’s typing indicator while it runs a snippet. If you edit a message the bot already answered, it runs the snippet again and edits its reply. The bot ignores messages from other bots.

Options

Options go on the ?play line after the command. They are separated by spaces.

OptionMeaning
WxH or size=WxHThe canvas size in logical pixels. Each side can be from 1 to 2048. Without a size the canvas fits the content.
dark, light or theme=..The theme to render with. The default is dark. An app that passes its own function to .theme(..) uses its own theme.
msg=EXPR or message=EXPRA message to apply to an app. Repeat it to apply several in order. The expression can’t contain ;, {, } or #.

Snippet shapes

A snippet uses iced when it names the iced crate. It also uses iced when it uses a name from rawr-iced’s prelude without declaring or importing it. column!, text, button, Color and Fill are examples. Every other snippet is a plain program.

An expression

A bare iced expression renders as a view.

column![text("hi"), button("go")]

A view

A function named view with no arguments renders what it returns.

fn view() -> impl Widget<()> {
    row![text("left"), text("right")].spacing(20)
}

Expressions and views can’t take messages. Only an app takes them.

An app

A type with fn view(&self) and fn update(&mut self, message) is an app. The snippet can have its own main that calls iced::run or iced::application. Without one, the bot boots State::default(). A main whose iced::run takes closures is an app too. iced::run(|n: &mut u32, _: Message| *n += 1, |n: &u32| text(n)) is one example. It needs no fn view.

The bot applies each msg= in order. Output says what the reply shows. An app doesn’t get imports for free. Write its use lines as you would in a file.

?play light msg=Message::Increment msg=Message::Increment
use iced::widget::{Widget, button, column, text};

#[derive(Default)]
struct Counter {
    value: i64,
}

#[derive(Debug, Clone, Copy)]
enum Message {
    Increment,
}

impl Counter {
    fn update(&mut self, message: Message) {
        match message {
            Message::Increment => self.value += 1,
        }
    }

    fn view(&self) -> impl Widget<Message> {
        column![
            text(self.value).size(40),
            button("Increment").on_press(Message::Increment),
        ]
        .padding(20)
    }
}

A snippet with its own #[preview] is refused. Use the size option instead.

A plain program

A plain program runs the way rawr run runs a file. Its top-level statements run first. Then fn main runs if there is one. The reply is its stdout and stderr in the order it wrote them.

A snippet of statements alone runs as the body of main. If its last expression has no semicolon, its value is printed with {:?}. So 1 + 2 prints 3, and 1 + 2; prints nothing. A last value whose type has no Debug runs and isn’t printed.

let xs = vec![3, 1, 2];
xs.iter().sum::<i64>()
6

The reply shows the exit status when it isn’t 0. A main that returns Err prints Error: .. and exits with status 1. A panic exits with status 101. A program stopped by a limit exits with status 1. Messages don’t apply to a plain program. The reply notes that they were ignored.

The sandbox

A snippet runs on a server whose files and settings belong to someone else. So ?play gives it no files, no environment variables and no network. Each run is its own process, and that process starts with an empty environment. The table shows what each attempt gets.

The snippet usesWhat happens
include_str!("notes.txt")The snippet doesn’t compile. The error is cannot use `include_str!` here: ?play has no files.
include_bytes!("cat.png")The snippet doesn’t compile. The error is cannot use `include_bytes!` here: ?play has no files.
image("cat.png") or svg("logo.svg")The image draws as a missing file. Handle::from_path does the same. The Discord reply adds the note ?play has no files. Paths given to image and svg do not exist here.
env!("HOME")The snippet doesn’t compile. The error is cannot use `env!` here: ?play has no files. It has no environment variable `HOME` either.
std::fs, std::env, std::net or std::threadThe snippet doesn’t compile. rawr has none of these modules. The error for std::fs is unknown type `std::fs`.
tokio::fs, tokio::net, tokio::process, tokio::signal or tokio::ioThe snippet doesn’t compile. ?play’s tokio has none of these modules. The error for tokio::fs is unknown type `tokio::fs`.
use reqwest; or any crate other than icedThe snippet doesn’t compile. The error is unknown import `reqwest`.

A snippet can still draw an image from bytes it holds. Images in memory shows how.

The clock

An app runs on a simulated clock. The clock starts when the app boots. It moves 50 ms for each frame the bot draws. No step waits for real time to pass.

  • time::every ticks as the clock passes each interval.
  • window::frames fires on each frame.
  • Instant::now() reads the simulated clock.
  • tokio’s sleep, interval and timeout run on a paused tokio clock. The bot moves that clock forward with its own.
  • A view can ask to be redrawn at a later time. When no timer is running, the clock jumps straight to that time.

So the same snippet gives the same frames on every run. A 400 ms sleep shows as 400 ms in the GIF, and it takes no real time to render.

Only an app runs on this clock. A plain program reads the real clock. Real time still limits every run. The scripts and the drawing count against the time budgets.

Output

A bare expression and a view each get a PNG. An app is recorded frame by frame on the simulated clock. Its reply is a PNG or a GIF, depending on how its frames change.

Size and scale

Without a size option the canvas fits the content and adds a 12 px margin. A widget that fills its width gets 480 logical pixels. One that fills its height gets 360.

A PNG is drawn at twice the logical size, so it stays sharp on high-density screens. A large image is drawn at a lower scale, so no side passes 2048 pixels. The scale never goes below 1. A GIF is drawn at the logical size. That is half the scale of a PNG.

How an app is recorded

The bot boots the app and runs its boot task. Then it draws a frame every 50 ms of simulated time.

  • A frame where a widget publishes a message applies that message and draws again at the same time. A frame that changes the interface also draws again. A component handling its own event is one example. A sensor firing is another. One frame draws at most 8 times.
  • A frame settles when no timer or subscription is running and nothing asked to be redrawn.
  • Each msg= is applied after the frames before it settle. So each message’s change shows.
  • If the frames after the boot or a message never settle, the next message is applied after 20 frames.

After the last message, the recording goes on until one of these happens.

What happensThe reply
The view never changedA PNG.
The view changed and then settledA GIF that plays once. Its last frame shows for 3 s. The settled frame before each later message shows for 1 s.
The frames repeatA GIF of one cycle that loops forever. How loops are found explains the rule.
100 frames are drawn, or 5 s of simulated time pass after the last message, with no repeatA GIF that plays once and holds its last frame. The reply notes how much it shows.
The messages need more than 100 framesA PNG of the last frame with a note.
The GIF is over 8 MBA PNG of the last frame with a note.
The time budget runs outA GIF of the frames so far that plays once. The reply notes when rendering stopped.

Frames that show the same picture are merged into one longer frame. Each GIF frame shows for at least 20 ms. Each frame stores only the rectangle that changed.

This bar eases from empty to full in one second. It listens to window::frames only while it moves. Its GIF plays once and stops on the full bar.

fill.rs
use iced::animation::Easing;
use iced::time::{Instant, milliseconds};
use iced::widget::{column, progress_bar, text};
use iced::{Animation, Subscription, Widget, window};

pub fn main() -> iced::Result {
    iced::application(Fill::new, Fill::update, Fill::view)
        .subscription(Fill::subscription)
        .run()
}

struct Fill {
    progress: Animation<bool>,
    now: Instant,
}

#[derive(Debug, Clone, Copy)]
enum Message {
    Frame(Instant),
}

impl Fill {
    fn new() -> Self {
        let now = Instant::now();
        let mut progress = Animation::new(false)
            .duration(milliseconds(1000))
            .easing(Easing::EaseInOut);
        progress.go_mut(true, now);
        Self { progress, now }
    }

    fn update(&mut self, message: Message) {
        match message {
            Message::Frame(now) => self.now = now,
        }
    }

    fn subscription(&self) -> Subscription<Message> {
        if self.progress.is_animating(self.now) {
            window::frames().map(Message::Frame)
        } else {
            Subscription::none()
        }
    }

    fn view(&self) -> impl Widget<Message> {
        let value = self.progress.interpolate(0.0, 100.0, self.now);
        column![
            text(format!("{value:.0}%")).size(24),
            progress_bar(0.0..=100.0, value).length(240),
        ]
        .spacing(8)
    }
}
(plays a bar filling up)

How loops are found

An app that never settles is checked for a cycle after its last message. The bot hashes each frame. Frame k repeats when it shows the same picture as an earlier frame j. The frames from j to k must not all show one picture. The two frames after k must also match the two after j. So must the time between them. A cycle shorter than two frames needs only as many.

The GIF is then frames j to k. It loops with no hold, so the seam doesn’t show. Frames before j are left out. The GIF starts the cycle at a frame where the picture changes. A 40-frame cycle is found after 43 frames.

These dots light up one at a time. The next one lights up every 250 ms. Their cycle is four pictures long, so the reply is a looping GIF of four frames.

dots.rs
use iced::time::{self, milliseconds};
use iced::widget::{row, text};
use iced::{Subscription, Widget};

pub fn main() -> iced::Result {
    iced::application(Dots::default, Dots::update, Dots::view)
        .subscription(Dots::subscription)
        .run()
}

#[derive(Default)]
struct Dots {
    lit: usize,
}

#[derive(Debug, Clone, Copy)]
enum Message {
    Tick,
}

impl Dots {
    fn update(&mut self, message: Message) {
        match message {
            Message::Tick => self.lit = (self.lit + 1) % 4,
        }
    }

    fn subscription(&self) -> Subscription<Message> {
        time::every(milliseconds(250)).map(|_| Message::Tick)
    }

    fn view(&self) -> impl Widget<Message> {
        let dot = |at: usize| text(if at == self.lit { "●" } else { "○" }).size(32);
        row![dot(0), dot(1), dot(2), dot(3)].spacing(8)
    }
}
(loops four dots)

The playground shows the same GIF. A share link’s preview image is the last frame as a PNG.

Limits

Snippets are untrusted. Each one runs in its own process. The hosted bot and playground use these limits.

LimitValue

Animation budget15 seconds from the frame where an app’s view first changes. One render at a time holds it.
Idle budget60 seconds for a render that starts when no other render is queued or running.
Animation allowance90 seconds of animation time per user in any 10 minutes.
Whole run80 seconds. The process is stopped after that.

Operations1,000,000 per evaluation. Booting, each update and each view are separate evaluations.
Call depth32.
Strings65,536 bytes.
Arrays, vectors and maps65,536 items.
Program output64 KiB. Longer output ends with … output truncated, and the program is stopped.
Canvas2048 logical pixels per side.
Frames100 per recording. 5 seconds of simulated time after the last message. 20 frames after the boot or a message before the next message.
GIF8 MB.
Image upload10 MB.
Discord reply2000 characters.
Runs in Discord4 a minute per user. 12 a minute per channel.

A run over the Discord rate limit gets an hourglass reaction instead of a reply. An edit over the limit is ignored.

The animation budget

Every render starts on the still budget. An app moves to the animation budget at the frame where its view first changes. From then on its scripts and its recording share that deadline. Each frame is encoded into the GIF as it is recorded, so the encoding counts too.

Only one render at a time holds the longer budget. Discord and the playground share it. A render that starts while another one holds it keeps the still budget.

A render that starts with no other render queued or running gets the idle budget instead. Someone who sends a snippet during an idle render doesn’t wait for all of it. The bot asks the idle render to stop. It stops at once if it has run past 15 seconds. Otherwise it stops when it reaches 15 seconds. It stops before its next frame and keeps the frames it has.

The allowance

Each user has 90 seconds of animation time in any 10 minutes. A Discord user is counted by user ID. A playground visitor is counted by a hash of their IP address. The allowance fits one idle render and two at the animation budget.

  • A render that ends within the still budget costs nothing.
  • A render that runs past the still budget counts its whole time.
  • A render can use up the allowance, but it can’t take it below zero.
  • A render gets the smaller of its budget and the allowance left.
  • A user with 5 seconds or less left gets the still budget.

When the clock cuts a render that had only the still budget, its note says why. Notes and replies lists each case.

Where ?play differs from rawr run

A snippet has no project around it. It has no Cargo.toml, no files and no window. So ?play fills some gaps with stand-ins and shortcuts. Each one is listed here with its reason and what to write instead.

Images in memory

?play has no files, so an image or svg path draws as a missing file. include_str! and include_bytes! fail with ?play has no files. rawr run reads all three from disk.

Write the image’s bytes into the snippet instead. svg::Handle::from_memory takes svg text as bytes. image::Handle::from_bytes takes the bytes of a PNG or JPEG file. image::Handle::from_rgba takes a width, a height and 4 bytes for each pixel. Bytes are an array at runtime, so they can be at most 65,536 bytes long. An RGBA image of that size is 128 by 128 pixels.

circle.rs
let circle = r#"<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 100 100">
  <circle cx="50" cy="50" r="40" fill="hotpink"/>
</svg>"#;

svg(svg::Handle::from_memory(circle.as_bytes())).width(160).height(160)
(draws a pink circle)

No crates

rawr run imports the crates a project’s Cargo.toml names. A snippet has no Cargo.toml, so it can use only rawr’s std, iced and ?play’s tokio. Keep a snippet to those. Use rawr run for a program that needs another crate.

The prelude

A short snippet shouldn’t need use lines. So a bare expression or a view with no top-level use gets rawr-iced’s prelude imported for it. The prelude has iced’s widget functions and macros. text, button, column! and svg are some of them. It also has iced’s common types. Color, Length, Fill, Center, Theme, Task, Subscription and Widget are some of those.

One top-level use turns the prelude off for the whole snippet. Then write every use line the snippet needs. A use inside a function body leaves the prelude on. An app never gets the prelude. rawr run never imports names for you either.

Expressions, views and apps without main

?play wraps a snippet so it can run on its own. An expression becomes the body of fn view() -> impl Widget<()>. A view gets a #[preview] with the canvas size. That is why a snippet can’t have its own #[preview]. An app without main gets one that calls iced::run(State::update, State::view), so it boots from State::default(). A main that passes closures to iced::run runs as written.

rawr run needs a main. To run a snippet there, put the expression in an app’s view and write a main that calls iced::run.

Messages instead of clicks

A render has no window, so nobody can click it. Use msg= to apply the message a click would send. In the playground, write one message per line in the messages box.

tokio

A snippet has no Cargo.toml, so it can’t depend on tokio. rawr-iced declares its own tokio for it instead. Each item is backed by the real tokio type holding rawr values. Its timers run on the simulated clock, so a GIF shows each wait.

  • tokio::time has sleep, interval with tick().await, timeout, Instant and Duration.
  • tokio::sync::mpsc has channel and unbounded_channel. Their senders have send and clone, and their receivers have recv.
  • tokio::sync::oneshot has channel.
  • tokio::sync::watch has channel with send, subscribe, changed, borrow and borrow_and_update.
  • tokio::sync::Mutex has new and lock().await.
  • tokio::task has yield_now and spawn_blocking.
  • tokio::join!, tokio::try_join! and tokio::select! take up to 5 futures. select! accepts biased;. use tokio::join; makes join! tokio’s.

It doesn’t have JoinSet, Notify, Semaphore, RwLock, broadcast or time::sleep_until. A Mutex has no try_lock or into_inner. A plain program has no async code, so only an app can use tokio.

rawr run uses the same stand-in for a program that doesn’t depend on tokio. There its timers run on the real clock. A project whose Cargo.toml depends on tokio gets the real crate.

This app adds up what a producer sends over a channel. Its GIF shows “adding up” and then the sum at 400 ms of simulated time. The sender moves into the producer, as in Rust. The channel closes when the producer ends, so the consumer’s loop stops.

channel.rs
use iced::widget::text;
use iced::{Task, Widget};
use std::time::Duration;
use tokio::sync::mpsc;

pub fn main() -> iced::Result {
    iced::application(Sum::start, Sum::update, Sum::view).run()
}

#[derive(Default)]
struct Sum {
    total: Option<u32>,
}

#[derive(Debug, Clone)]
enum Message {
    Total(u32),
}

async fn total() -> u32 {
    let (sender, mut receiver) = mpsc::channel(2);
    let producer = async move {
        for n in 1..=4 {
            sender.send(n).await.unwrap();
            tokio::time::sleep(Duration::from_millis(100)).await;
        }
    };
    let consumer = async move {
        let mut sum = 0;
        while let Some(n) = receiver.recv().await {
            sum += n;
        }
        sum
    };
    let (_, sum) = tokio::join!(producer, consumer);
    sum
}

impl Sum {
    fn start() -> (Self, Task<Message>) {
        (Self::default(), Task::perform(total(), Message::Total))
    }

    fn update(&mut self, message: Message) {
        match message {
            Message::Total(total) => self.total = Some(total),
        }
    }

    fn view(&self) -> impl Widget<Message> {
        text(match self.total {
            Some(total) => format!("sum {total}"),
            None => "adding up".to_string(),
        })
    }
}
(shows adding up, then sum 10)

No tokio::spawn

Async code runs on iced’s UI thread, one step at a time. A spawned future would need to start a task outside the one it belongs to, and that model has no way to do it. So tokio::spawn doesn’t compile. task::spawn and spawn_local don’t either. The error says what to use instead.

unsupported syntax: `tokio::spawn` in a program without a tokio dependency, whose async code runs on iced's UI thread; run futures at once with `tokio::join!`, run blocking work with `tokio::task::spawn_blocking`, or return a `Task` from `update`

Use tokio::join! to run futures at once. Return a Task from update to start work that outlives the current message.

spawn_blocking

tokio::task::spawn_blocking(move || ..) runs a closure on a worker thread, as iced’s blocking work describes. Task::perform takes its handle, and .await takes its output. In a recording the worker reads the simulated clock, and the recording waits for the closure to end. So its output is ready at the instant its task started, and a GIF is the same on every run. A closure that takes long uses up the snippet’s time limit, as the same work in update would. std::thread::spawn doesn’t compile, and its error points to spawn_blocking.

Where ?play’s tokio behaves differently

Two things work differently from the real tokio.

  • A select! branch whose pattern doesn’t match ends the wait. It goes to the else branch, or panics when there is none. The real tokio would keep waiting for the other branches. A branch can’t have an if condition either. Give each branch a pattern that always matches. value = receiver.recv() is one. Then match on value in the branch’s body.
  • A read through a lock doesn’t wait. let mut held = mutex.lock().await; waits until no other task holds the lock. A read inside a larger expression reads without waiting. *mutex.lock().await + 1 is one such read. This keeps += from locking twice. When a task must hold the lock across an .await, bind the guard with let first.

Script sippers

A sipper written in rawr with task::sipper(async |sender| ..) is rawr’s own sipper. Its body runs in steps on the UI thread. Each sender.send(value).await hands the value to the progress mapper, and the body goes on after that. The sipper crate sends through a channel that holds one value, so a fast sender waits for the receiver. rawr’s sipper has no such channel, so it has none of that backpressure. rawr run uses the same sipper for rawr code. A program that needs the backpressure should send from a Rust sipper in a project and run it with rawr run.

The playground

rawr.airstrike.fyi/play has an editor and an output pane. Ctrl+Enter or Cmd+Enter runs the code. Tab indents. You can pick the theme and a size. The messages box takes one Message expression per line.

The Examples menu loads some of iced’s own examples. Examples → Reset brings back the counter. The editor keeps your latest snippet in the browser, so /play opens where you left off.

Each visitor gets 6 runs a minute and 60 an hour. Code can be up to 16 KiB. A run takes up to 32 messages, and each message can be up to 256 bytes. The playground uses the same renderer as the bot, with the same limits and allowance. Discord runs go first. When the renderer is busy for too long, the playground says the playground is busy; try again in a moment.

Share links

Share saves the code and options and gives a link of the form /play/<id>. The id comes from the content, so the same snippet always gets the same link. A shared snippet can be up to 64 KiB.

A shared link shows a preview card when posted in Discord and other apps. For an iced snippet the card is its last frame. For a plain program it is the site card with the first line of output. A share that nobody opens for 30 days is deleted.

Adding the bot to a server

Use the invite link to add the bot to a Discord server you manage. The bot answers only in channels a moderator turns on. It doesn’t answer in direct messages.

Moderators choose the channels with the /play-channel command. It needs the Manage Channels permission in the channel it changes. Its replies are visible only to the moderator who ran it.

CommandWhat it does
/play-channel add [channel]Turns the bot on in a channel. The default is the current channel.
/play-channel remove [channel]Turns the bot off in a channel.
/play-channel listLists the channels where the bot answers.

A thread follows its parent channel. Running /play-channel add in a thread turns the bot on for the parent channel.

The status page shows whether the bot is up. It also counts recent runs.
