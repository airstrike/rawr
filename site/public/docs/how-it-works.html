How it works

How the interpreter works, what it costs and where it came from.

What kind of interpreter is rawr?

rawr is a tree-walking interpreter over a typed program. Its front end parses Rust. It resolves names and checks types, traits and generics before anything runs. It reports errors the way rustc does. Then an evaluator walks the checked program and runs it.

Values at run time carry a tag for their type. They are reference-counted. Standard library types such as Vec and HashMap are backed by native Rust code. So are the crates a program imports and iced’s widgets.

An experimental bytecode VM also exists. It is off by default.

Where does the evaluator come from?

rawr began as a fork of Rhai. Rhai is an embedded scripting language for Rust. Its source is on GitHub. rawr keeps Rhai’s evaluator as its foundation. It also keeps Rhai’s dynamic values and its machinery for calling host functions. These parts are mature. rawr adds a typed Rust front end on top of them, and every program and script is typed Rust.

Thank you to the Rhai authors for the work that rawr is built on.

rawr doesn’t run Rhai scripts. Rhai is licensed under MIT or Apache-2.0. rawr uses the same two licenses. The LICENSE files in the repository carry the attribution.

How fast is it?

Interpreted code runs slower than the same code compiled by rustc. Calls into native code run at native speed. In an iced app most of the time goes to native iced code, such as layout and drawing.

The interpreter shows in a tight loop that runs many times. Keep a loop like that in a native module or a crate, and Cargo compiles it.

An edit to a marked file needs no native build. In RawrGallery, a gallery app built with rawr-iced, such an edit was live in the running app in about 0.2 s on an Apple Silicon Mac.

How does rawr handle borrow checking?

rawr doesn’t have a full borrow checker. It rejects a use after a move, as rustc’s E0382 does. It also rejects two live &mut borrows of one value. It accepts some programs that rustc rejects, and Supported Rust lists them.

Values are reference-counted, so a program can’t corrupt memory. Borrow checking only rejects programs. It never changes what a valid program does.

rawr aims to run every program that rustc accepts with Rust’s meaning. Where it can’t yet, it refuses the program. A few known differences remain, and each one is a defect to fix.

rustc says whether a program is valid Rust. rawr check runs cargo check on the crate after its own check, and fails if either check fails. Marked files are ordinary .rs files, so rust-analyzer checks them as well.

How are generics handled?

rawr checks generics as rustc does. Each call is checked against the bounds of the function it calls. A missing bound is an error.

At run time each generic function has one body. rawr does not make a copy for each type. Values carry their types, so a trait method call dispatches on the value it is called on. A call like T::default() has no value to dispatch on. rawr passes the type to the function as a hidden argument for these calls.

In an iced app, a function whose signature names a type parameter inside an iced type gets the same hidden argument. fn card<Message: Clone>(label: &str) -> Element<'static, Message> is one such function. Each iced call in its body uses the caller’s message type at run time.

Generic code in an imported Rust crate is compiled natively. It is compiled for the concrete types your program uses.

Code that relies on a separate copy of a function for each type is not supported. std::mem::size_of::<T>() is an example.

Why not use Miri or interpret rustc’s MIR?

Miri interprets the whole program. It cannot call native code. iced, wgpu and the window system all need native code, so Miri cannot drive them. Miri is also slow on purpose. It checks each operation for undefined behaviour.

An interpreter for rustc’s MIR would still have two problems. The first is that iced is generic over your app’s message type. Native iced code is compiled for concrete types. A type defined in interpreted code has no compiled copy of iced to call. The second is that rustc’s front end would run on each edit. That takes much longer than reloading a marked file does today.

Using rustc’s typed output as rawr’s front end is a possible future direction.
