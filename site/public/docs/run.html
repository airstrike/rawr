Run

What rawr run and rawr check do with a crate or a file. Which files are interpreted, who runs a program and what ships in release.

What rawr runs

rawr run takes a Cargo crate or a single .rs file. Without a path, rawr looks in the current directory and its parents for a crate with a marked file. The crate’s root file may start with // rawr, or a module it declares may. The root file is src/main.rs or src/lib.rs.

A single file runs with or without the marker. It may hold top-level statements. rawr runs them first and then calls fn main.

A program with a main that returns Err prints Error: .. and exits with status 1. A panic exits with status 101, as in Rust.

The // rawr marker

A file whose first line is // rawr is interpreted. Every other file is native Rust. The marker is a comment, so Cargo ignores it.

  • The crate root may be marked or not. An unmarked root is native Rust, and the crate runs when a module it declares is marked. The module may be declared by the root or through native modules. If no file is marked, rawr run stops with RAWR-ENVIRONMENT-MISSING-SOURCE and says to add the line.
  • A mod util; declaration loads util.rs or util/mod.rs. That module is interpreted when its first line is // rawr. Otherwise it is native, and Cargo compiles it.
  • Marked code may call native modules.
  • Native code may call marked modules when the crate root is native. A native main says how.
  • With a marked root, native code must not use code from marked files yet, and rawr reports an error if it does.
  • A path dependency is compiled natively, even if its files start with // rawr. Only the crate you run is interpreted.

A native main

An ordinary app can keep its main native and mark only the module you are working on. Under rawr run, each function of the marked module that native code can call gets a generated stub. The stub has the function’s signature, and it runs the function in the interpreter.

The stubs live in rawr’s own copy of the crate, under target/rawr/crate. Your crate never depends on rawr. cargo build compiles your files as they are.

Native code sees the public items of a marked module: its functions, methods, structs, enums, constants and type aliases. Private items stay in the interpreter.

Numbers, bool, char, String and &str cross between native code and a marked module. Vec and Option of them cross too. So do the structs and enums of marked modules whose fields cross.

A parameter may be one of those values or a reference to one. A &mut argument comes back with the changes the function made.

A function whose values can’t cross yet panics when native code calls it, and the message names the function. A public function that returns impl Trait stops rawr run with an error that names it.

A save of a marked file reaches the running program at its next call into that file. An edit to a function body or to a private item swaps in place, and the program keeps its state. An edit that changes what native code sees needs a new native build. That covers a signature, a struct’s fields and a public constant. rawr then restarts the program and prints one line that says why:

rawr: `physics::Ball` changed its fields; restarting the program

An edit to a native file restarts the program too.

The examples/islands crate in rawr’s repository is such an app. Its native main moves a ball each tick through the marked physics.rs.

Limits today:

  • A native module other than the root can’t declare a marked module.
  • Marked code can’t call items written in the native root itself.
  • The native main runs on a thread of its own, not on the process’s main thread.
  • The program’s standard input is closed.

Checking

rawr checks a whole program before any of it runs. The check resolves names, types, traits and method calls. It also checks that every match covers every case.

rawr check runs that check without running the program. Then it runs cargo check on the crate, because rawr’s check accepts some code that rustc rejects. Supported Rust lists those cases.

rawr run runs cargo check beside the program. For a program that runs once, its errors are printed after the program ends.

Who runs a program

The rawr command parses a program once. Then it runs the program itself or hands it to an installed extension.

ProgramRuns in
No dependencies and no native modulesrawr itself.
Dependencies in Cargo.toml or native modulesrawr-import, which compiles the native code with Cargo.
Uses the iced craterawr-iced, which opens the app in a window.

If the extension a program needs isn’t installed, rawr says which one and prints the commands that install it. Set RAWR_VERBOSE=1 to see which binary ran a program.

Reload

rawr-iced reloads an iced app when you save a marked file. Reload an iced app says what it keeps.

A program with a native main keeps running, and a save of a marked file reaches it at its next call. A native main covers it.

Any other program that isn’t an iced app runs once and exits. Run it again after an edit. A crate with no dependencies needs no build, so it starts at once. With rawr-import, a crate whose native code didn’t change reuses its earlier build. On an Apple Silicon Mac, a small crate with one path dependency ran again in about 2.4 s after an edit to its marked file.

Planned: rawr run will watch every program and restart it on save.

Release builds

cargo build --release compiles every file natively, the marked ones included. No interpreter ships with the build.

rawr-iced’s #[preview] and #[widget] attributes come from the rawr-macros crate. Under Cargo they leave the item as written.

Embedding is different. An app that runs scripts with the rawr crate ships the interpreter. Embedding covers that use.

Speed

Interpreted code runs slower than the same code compiled by rustc. Calls into native code run at native speed. Keep a hot loop in a native module or a crate, and Cargo compiles it.
