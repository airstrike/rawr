Play

How the playground and the ?play bot run a snippet. Both use the same renderer and the same limits.

The sandbox

A snippet has no files, no environment variables and no network. Each run is its own process, and that process starts with an empty environment.

The snippet usesWhat happens
include_str!("notes.txt")The snippet doesn’t compile. The error is cannot use `include_str!` here: ?play has no files.
include_bytes!("cat.png")The snippet doesn’t compile. The error is cannot use `include_bytes!` here: ?play has no files. Inside an app’s .fonts(..) setting it is skipped instead, as Images in memory explains.
image("cat.png") or svg("logo.svg")The image draws as a missing file. Handle::from_path does the same. The Discord reply adds a note.

A snippet can still draw an image from bytes it holds. Images in memory shows how.

The clock

An app runs on a simulated clock. The clock starts when the app boots. It moves 50 ms for each frame the bot draws. No step waits for real time to pass.

  • time::every ticks as the clock passes each interval.
  • window::frames fires on each frame.
  • Instant::now() reads the simulated clock.
  • tokio’s sleep, interval and timeout run on a paused tokio clock. The bot moves that clock forward with its own.
  • A view can ask to be redrawn at a later time. When no timer is running, the clock jumps straight to that time.

So the same snippet gives the same frames on every run. A 400 ms sleep shows as 400 ms in the GIF, and it takes no real time to render.

A plain program whose main is async runs on this clock too. Its clock moves only while it waits on a timer. Any other plain program reads the real clock. Real time still counts against the time budgets.

Output

A bare expression and a view each get a PNG. An app is recorded frame by frame. Its reply is a PNG or a GIF, depending on how its frames change.

Size and scale

Without a size option the canvas fits the content and adds a 12 px margin. A widget that fills its width gets 480 logical pixels. One that fills its height gets 360. A wrapping layout such as Row::wrap() wraps only with a size, as in ?play size=480x200.

A PNG is drawn at twice the logical size. A large image is drawn at a lower scale, so no side passes 2048 pixels. The scale never goes below 1. A GIF is drawn at the logical size.

How an app is recorded

The bot boots the app and runs its boot task. Then it draws a frame every 50 ms of simulated time.

  • A frame where a widget publishes a message applies that message and draws again at the same time. A frame that changes the interface also draws again. One frame draws at most 8 times.
  • A frame settles when no timer or subscription is running and nothing asked to be redrawn.
  • Each msg= is applied after the frames before it settle.
  • If the frames after the boot or a message never settle, the next message is applied after 20 frames.

After the last message, the recording goes on until one of these happens.

Frames that show the same picture are merged into one longer frame. Each GIF frame shows for at least 20 ms.

This bar eases from empty to full in one second. It listens to window::frames only while it moves. Its GIF plays once and stops on the full bar.

fill.rs
use iced::animation::Easing;
use iced::time::{Instant, milliseconds};
use iced::widget::{column, progress_bar, text};
use iced::{Animation, Subscription, Widget, window};

pub fn main() -> iced::Result {
    iced::application(Fill::new, Fill::update, Fill::view)
        .subscription(Fill::subscription)
        .run()
}

struct Fill {
    progress: Animation<bool>,
    now: Instant,
}

#[derive(Debug, Clone, Copy)]
enum Message {
    Frame(Instant),
}

impl Fill {
    fn new() -> Self {
        let now = Instant::now();
        let mut progress = Animation::new(false)
            .duration(milliseconds(1000))
            .easing(Easing::EaseInOut);
        progress.go_mut(true, now);
        Self { progress, now }
    }

    fn update(&mut self, message: Message) {
        match message {
            Message::Frame(now) => self.now = now,
        }
    }

    fn subscription(&self) -> Subscription<Message> {
        if self.progress.is_animating(self.now) {
            window::frames().map(Message::Frame)
        } else {
            Subscription::none()
        }
    }

    fn view(&self) -> impl Widget<Message> {
        let value = self.progress.interpolate(0.0, 100.0, self.now);
        column![
            text(format!("{value:.0}%")).size(24),
            progress_bar(0.0..=100.0, value).length(240),
        ]
        .spacing(8)
    }
}
(plays a bar filling up)

How loops are found

An app that never settles is checked for a cycle after its last message. The bot hashes each frame. Frame k repeats when it shows the same picture as an earlier frame j. The frames from j to k must not all show one picture. The two frames after k must also match the two after j. So must the time between them. A cycle shorter than two frames needs only as many.

The GIF is then frames j to k. It loops with no hold, so the seam doesn’t show. Frames before j are left out. The GIF starts the cycle at a frame where the picture changes. A 40-frame cycle is found after 43 frames.

These dots light up one at a time every 250 ms. The reply is a looping GIF of four frames.

dots.rs
use iced::time::{self, milliseconds};
use iced::widget::{row, text};
use iced::{Subscription, Widget};

pub fn main() -> iced::Result {
    iced::application(Dots::default, Dots::update, Dots::view)
        .subscription(Dots::subscription)
        .run()
}

#[derive(Default)]
struct Dots {
    lit: usize,
}

#[derive(Debug, Clone, Copy)]
enum Message {
    Tick,
}

impl Dots {
    fn update(&mut self, message: Message) {
        match message {
            Message::Tick => self.lit = (self.lit + 1) % 4,
        }
    }

    fn subscription(&self) -> Subscription<Message> {
        time::every(milliseconds(250)).map(|_| Message::Tick)
    }

    fn view(&self) -> impl Widget<Message> {
        let dot = |at: usize| text(if at == self.lit { "●" } else { "○" }).size(32);
        row![dot(0), dot(1), dot(2), dot(3)].spacing(8)
    }
}
(loops four dots)

The animation budget

Every render starts on the still budget. An app moves to the animation budget at the frame where its view first changes. From then on its scripts, its recording and the GIF encoding share that deadline.

Only one render at a time holds the longer budget. Discord and the playground share it. A render that starts while another one holds it keeps the still budget.

A render that starts with no other render queued or running gets the idle budget instead. When someone else sends a snippet, the idle render stops at its first frame past 15 seconds. It keeps the frames it has.

The allowance

A Discord user is counted by user ID. A playground visitor is counted by a hash of their IP address. The allowance fits one idle render and two at the animation budget.

  • A render that ends within the still budget costs nothing.
  • A render that runs past the still budget counts its whole time.
  • A render can use up the allowance, but it can’t take it below zero.
  • A render gets the smaller of its budget and the allowance left.
  • A user with 5 seconds or less left gets the still budget.

When the clock cuts a render that had only the still budget, its note says why. Notes and replies lists each case.

Where ?play differs from rawr run

A snippet has no Cargo.toml, no files and no window. ?play fills those gaps with stand-ins and shortcuts.

Images in memory

An image or svg path draws as a missing file. include_bytes! fails. An app’s window settings in main are the exception. ?play skips .fonts(..), .font(..), .window_size(..) and iced’s other window settings. Their arguments are never compiled. So .fonts([include_bytes!("icons.ttf").as_slice()]) gives no error. The font isn’t loaded, so text set in it falls back to another font.

Write the image’s bytes into the snippet instead. svg::Handle::from_memory takes svg text as bytes. image::Handle::from_bytes takes the bytes of a PNG or JPEG file. image::Handle::from_rgba takes a width, a height and 4 bytes for each pixel. Bytes are an array at runtime, so they can be at most 65,536 bytes long. An RGBA image of that size is 128 by 128 pixels.

circle.rs
let circle = r#"<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 100 100">
  <circle cx="50" cy="50" r="40" fill="hotpink"/>
</svg>"#;

svg(svg::Handle::from_memory(circle.as_bytes())).width(160).height(160)
(draws a pink circle)

No crates

A snippet can use only rawr’s std, iced and ?play’s tokio. Use rawr run for a program that needs another crate.

The prelude

A bare expression or a view with no top-level use gets rawr-iced’s prelude imported for it. The prelude has iced’s widget functions and macros. text, button, column! and svg are some of them. It also has iced’s common types. Color, Length, Fill, Center, Theme, Shadow, Rectangle, Radians and Widget are some of those. It has the modules iced’s examples use most in a view: border, padding, alignment, font, gradient, mouse and theme. It has the color! macro and the rule widgets too.

One top-level use turns the prelude off for the whole snippet. A use inside a function body leaves the prelude on. An app never gets the prelude. rawr run never imports names for you either.

Expressions, views and apps without main

An expression becomes the body of fn view() -> impl Widget<()>. A view gets a #[preview] with the canvas size. That is why a snippet can’t have its own #[preview]. An app without main gets one that calls iced::run(State::update, State::view), so it boots from State::default(). A main that passes closures to iced::run runs as written.

To run a snippet with rawr run, put the expression in an app’s view and write a main that calls iced::run.

Messages instead of clicks

Use msg= to apply the message a click would send. In the playground, write one message per line in the messages box.

tokio

A snippet can’t depend on tokio, so rawr-iced declares its own. Each item is backed by the real tokio type holding interpreted values. Its timers run on the simulated clock.

  • tokio::time has sleep, interval with tick().await, timeout, Instant and Duration.
  • tokio::sync::mpsc has channel and unbounded_channel. Their senders have send and clone, and their receivers have recv.
  • tokio::sync::oneshot has channel.
  • tokio::sync::watch has channel with send, subscribe, changed, borrow and borrow_and_update.
  • tokio::sync::Mutex has new and lock().await.
  • tokio::task has yield_now and spawn_blocking.
  • tokio::join!, tokio::try_join! and tokio::select! take up to 5 futures. select! accepts biased;. A select! branch whose pattern doesn’t match its value is disabled, and the others keep running, as in tokio. Once every branch is disabled, the else branch runs, or the program panics when there is none. A branch can’t have an if condition. use tokio::join; makes join! tokio’s.

It doesn’t have JoinSet, Notify, Semaphore, RwLock, broadcast or time::sleep_until. A Mutex has no try_lock or into_inner. A plain program can use it too when its main is async, as #[tokio::main] async fn main() is. In the playground’s browser mode the same items run on the browser’s real clock instead of the simulated one, and spawn_blocking runs its closure at once, because a page has no threads.

rawr run uses the same stand-in for a program that doesn’t depend on tokio. There its timers run on the real clock. A project whose Cargo.toml depends on tokio gets the real crate.

This app adds up what a producer sends over a channel. Its GIF shows “adding up” and then the sum at 400 ms of simulated time. The channel closes when the producer ends, so the consumer’s loop stops.

channel.rs
use iced::widget::text;
use iced::{Task, Widget};
use std::time::Duration;
use tokio::sync::mpsc;

pub fn main() -> iced::Result {
    iced::application(Sum::start, Sum::update, Sum::view).run()
}

#[derive(Default)]
struct Sum {
    total: Option<u32>,
}

#[derive(Debug, Clone)]
enum Message {
    Total(u32),
}

async fn total() -> u32 {
    let (sender, mut receiver) = mpsc::channel(2);
    let producer = async move {
        for n in 1..=4 {
            sender.send(n).await.unwrap();
            tokio::time::sleep(Duration::from_millis(100)).await;
        }
    };
    let consumer = async move {
        let mut sum = 0;
        while let Some(n) = receiver.recv().await {
            sum += n;
        }
        sum
    };
    let (_, sum) = tokio::join!(producer, consumer);
    sum
}

impl Sum {
    fn start() -> (Self, Task<Message>) {
        (Self::default(), Task::perform(total(), Message::Total))
    }

    fn update(&mut self, message: Message) {
        match message {
            Message::Total(total) => self.total = Some(total),
        }
    }

    fn view(&self) -> impl Widget<Message> {
        text(match self.total {
            Some(total) => format!("sum {total}"),
            None => "adding up".to_string(),
        })
    }
}
(shows adding up, then sum 10)

No tokio::spawn

Async code runs on iced’s UI thread, one step at a time. So tokio::spawn doesn’t compile. task::spawn and spawn_local don’t either.

unsupported syntax: `tokio::spawn` in a program without a tokio dependency, whose async code runs on iced's UI thread; run futures at once with `tokio::join!`, run blocking work with `tokio::task::spawn_blocking`, or return a `Task` from `update`

Return a Task from update to start work that outlives the current message.

spawn_blocking

tokio::task::spawn_blocking(move || ..) runs a closure on a worker thread, as iced’s blocking work describes. Task::perform takes its handle, and .await takes its output. In a recording the worker reads the simulated clock, and the recording waits for the closure to end. So its output is ready at the instant its task started. std::thread::spawn doesn’t compile, and its error points to spawn_blocking.

Where ?play’s tokio behaves differently

  • A read through a lock doesn’t wait. let mut held = mutex.lock().await; waits until no other task holds the lock. A read inside a larger expression reads without waiting. *mutex.lock().await + 1 is one such read. This keeps += from locking twice. When a task must hold the lock across an .await, bind the guard with let first.

Script sippers

A sipper written in a snippet with task::sipper(async |sender| ..) is rawr’s own sipper. Its body runs in steps on the UI thread. It has no backpressure. The sipper crate sends through a channel that holds one value, so a fast sender waits for the receiver. rawr run uses the same sipper for code in marked files. A program that needs the backpressure should send from a Rust sipper in a project and run it with rawr run.
