rawr-iced

rawr-iced is an extension for iced apps. iced draws the window, and rawr interprets the marked files. Saving a marked file reloads the running app.

When rawr-iced is used

The rawr command reads a program once and decides who runs it. A program goes to rawr-iced when it names the iced crate. A program that imports Rust crates from its Cargo.toml but doesn’t use iced goes to rawr-import. rawr-iced imports an iced app’s other crates the same way and adds iced to its runner. Every other program runs in rawr itself. Set RAWR_VERBOSE=1 to see which way a program went.

rawr-iced follows iced master. It is built against one iced revision, be88873d, and rawr doctor prints it. A project on another revision is refused with a message.

Install

rawr-iced needs a Unix system and the pinned Rust nightly nightly-2026-07-11 with the rustc-dev and rust-src components. It has been tested on Apple Silicon Macs. Install the rawr command first.

rustup toolchain install nightly-2026-07-11 --component rustc-dev,rust-src
cargo +nightly-2026-07-11 install --locked --git https://github.com/airstrike/rawr rawr-iced-cli
cargo +nightly-2026-07-11 install --locked --git https://github.com/airstrike/rawr rawr-import --features rustc-driver

The rawr-iced-cli package installs rawr-iced. The rawr-import package installs rawr-import-driver, which reads the API of iced and your other dependencies. rawr-iced imports an app’s dependencies the way rawr-import does, and adds iced to its runner.

Run rawr doctor to see what is installed. Its report from rawr-iced adds the iced revision, the renderer and the manifest.

The iced template

rawr-iced offers one template to rawr new. It writes a starter iced crate.

rawr new counter --template iced && cd counter && rawr run

rawr new counter --template iced creates the counter directory. It holds an ordinary Cargo crate. rawr run opens the app in a window.

counter/Cargo.toml depends on iced from git. The revision is the one rawr-iced is built against. rawr doctor prints it. iced turns on every widget rawr offers.

Cargo.toml
[package]
name = "counter"
version = "0.1.0"
edition = "2024"

[dependencies]
iced = { git = "https://github.com/iced-rs/iced", rev = "be88873d38544455e26c7a104eb757da2cbbac6b", features = ["advanced", "canvas", "image-without-codecs", "qr_code", "selector", "sipper", "svg"] }

Two more files make the crate build as rawr builds it. rust-toolchain.toml pins the nightly rawr reads Rust with. .cargo/config.toml sets build.target to "host-tuple", so builds go in target/<host>/debug. With both, rawr run and cargo build compile iced once and share it. Whichever runs second reuses what the first compiled.

rust-toolchain.toml
[toolchain]
channel = "nightly-2026-07-11"
components = ["rust-src", "rustfmt", "clippy"]
.cargo/config.toml
[build]
target = "host-tuple"

A crate of your own needs the same two files. Without them, rawr run stops with RAWR-ENVIRONMENT-PROJECT-BUILD and prints the files to add.

counter/src/main.rs is iced’s own counter example with // rawr as its first line. rawr check accepts it.

src/main.rs
// rawr
use iced::Center;
use iced::widget::{Widget, button, column, text};

pub fn main() -> iced::Result {
    iced::run(Counter::update, Counter::view)
}

#[derive(Default)]
struct Counter {
    value: i64,
}

#[derive(Debug, Clone, Copy)]
enum Message {
    Increment,
    Decrement,
}

impl Counter {
    fn update(&mut self, message: Message) {
        match message {
            Message::Increment => {
                self.value += 1;
            }
            Message::Decrement => {
                self.value -= 1;
            }
        }
    }

    fn view(&self) -> impl Widget<Message> {
        column![
            button("Increment").on_press(Message::Increment),
            text(self.value).size(50),
            button("Decrement").on_press(Message::Decrement)
        ]
        .padding(20)
        .align_x(Center)
    }
}

cargo run compiles and runs the same app natively. cargo build --release compiles it for release, and the release build doesn’t need the interpreter.

The first rawr run compiles iced and the runner in the project’s target/. For a new template project on an Apple Silicon Mac that took about 2 minutes. Later runs reuse the build. Reload an iced app covers editing the app while it runs.

App shapes

An app starts from main with one of iced’s own entry points.

iced::run

iced::run(State::update, State::view) boots State::default(). The state type needs #[derive(Default)]. The counter from the template has this shape.

update and view can also be closures with typed parameters. iced::run(|state: &mut State, message: Message| state.update(message), State::view) is one example. A parameter can be a pattern such as _: Message. An update closure returns () unless it is written with a return type such as -> Task<Message>. An untyped closure parameter fails the check with an error that asks for its type.

The state can be any type with a Default. iced::run(|n: &mut u32, _: Message| *n += 1, |n: &u32| text(n)) keeps a u32.

The application builder

iced::application(boot, update, view) takes a boot function such as State::default. It accepts these builders before .run():

  • .title(..) with a method of the state or a string literal.
  • .theme(..) with a method that returns a Theme, or with a theme such as Theme::Dark.
  • .subscription(..) with a method that returns a Subscription.
  • .centered().

Window and renderer settings such as .window_size(..), .font(..) and .style(..) are accepted. rawr-iced doesn’t apply them yet.

The builder may come from a function of your own, as iced’s todos example writes it. fn application() -> Application<impl Program<Message = Message, Theme = Theme>> returns the chain, and main ends with application().run(). rawr reads the chain as if main held it. main must be the function’s only caller. use iced::{Application, Program}; imports the two names.

update can return nothing or a Task<Message>. This app uses the builder, a Task, a text input and a list built at run time:

src/main.rs
// rawr
use iced::widget::{Column, Widget, button, column, row, text, text_input};
use iced::{Element, Fill, Task};
use rawr::preview;

pub fn main() -> iced::Result {
    iced::application(Todos::default, Todos::update, Todos::view)
        .title("Todos")
        .run()
}

#[derive(Default)]
struct Todos {
    draft: String,
    items: Vec<String>,
}

#[derive(Debug, Clone)]
enum Message {
    Edit(String),
    Add,
    Remove(usize),
}

impl Todos {
    fn sample() -> Todos {
        Todos {
            draft: String::new(),
            items: vec!["Write the docs".to_string(), "Ship them".to_string()],
        }
    }

    fn update(&mut self, message: Message) -> Task<Message> {
        match message {
            Message::Edit(draft) => self.draft = draft,
            Message::Add => {
                if !self.draft.is_empty() {
                    self.items.push(self.draft.clone());
                    self.draft.clear();
                }
            }
            Message::Remove(index) => {
                self.items.remove(index);
            }
        }
        Task::none()
    }

    #[preview(name = "two items", seed = Todos::sample, size = (360, 180))]
    fn view(&self) -> impl Widget<Message> {
        let items: Vec<Element<'_, Message>> = self
            .items
            .iter()
            .enumerate()
            .map(|(index, item)| {
                row![text(item).width(Fill), button("x").on_press(Message::Remove(index))]
                    .spacing(8)
                    .boxed()
            })
            .collect();
        column![
            text_input("What needs doing?", &self.draft)
                .on_input(Message::Edit)
                .on_submit(Message::Add),
            Column::with_children(items).spacing(4),
        ]
        .spacing(12)
        .padding(16)
    }
}

The line use rawr::preview; is there for cargo. The rawr-macros dependency provides it, as Previews and snapshots describes.
