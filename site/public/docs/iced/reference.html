Supported iced APIs

The parts of iced that work in marked files today, and what isn’t available yet.

Views and elements

A view returns impl Widget<Message> as views do in iced master. It can also return Element<'_, Message>.

To turn a widget into an Element, call .boxed(). The list above uses it to collect its rows into a Vec<Element>. A widget’s .into() into an Element fails the check, as rustc rejects it on iced master. Element::from(widget) fails the same way. Both errors say to call .boxed() instead.

Row<Element<'_, Message>> and Column<Element<'_, Message>> name a row’s or a column’s type as iced master writes it. That works in a signature and in a let inside a function body.

Helper functions can build part of a view. A helper can name the app’s own Message type. It can also be generic over the message type, as in fn card<Message: Clone + 'static>(label: &str) -> Element<'static, Message>. Each caller passes its own message type. That type must be a type your program declares, a number, a String, a bool, a char or ().

Components

A type can implement iced’s component::Component trait. Its state lives in the widget tree. Its events reach its own update. component(value) puts it in a view.

Custom drawing with canvas

A type that implements canvas::Program<Message> draws in a canvas. Its draw returns the geometry to show. update and mouse_interaction are optional, as in iced. update turns iced’s events into a canvas::Action, which can publish a message, request a redraw or capture the event. The program’s State lives in the widget tree.

  • canvas(program) and Canvas::new(program) make the widget. canvas(self) works in a view.
  • Frame has fill, stroke, fill_rectangle, stroke_rectangle, fill_text, translate, rotate, scale, with_save, center and into_geometry.
  • Path has circle, line, rectangle and rounded_rectangle. Path::new(|b| ..) builds one with move_to, line_to, arc_to, circle, rectangle, quadratic_curve_to, bezier_curve_to and close.
  • Stroke, Fill and canvas::Text take struct literals with ..Default::default(). Stroke also has with_width, with_color, with_line_cap and with_line_join.
  • Cache keeps what its draw drew until clear is called or the size changes.
  • The same names import from iced::advanced::graphics::geometry.

Gradients, images, with_clip, Degrees and Radians are not there yet. rotate takes radians as a float.

sun.rs
use iced::mouse;
use iced::widget::canvas::{Cache, Geometry, LineCap, Path, Stroke};
use iced::widget::{canvas, center};
use iced::{Color, Element, Point, Rectangle, Renderer, Theme, Vector};

#[derive(Default)]
struct Sun {
    rays: Cache,
}

#[derive(Debug, Clone)]
enum Message {}

impl Sun {
    fn update(&mut self, _message: Message) {}

    fn view(&self) -> Element<'_, Message> {
        center(canvas(self).width(240).height(240)).boxed()
    }
}

impl<Message> canvas::Program<Message> for Sun {
    type State = ();

    fn draw(
        &self,
        _state: &(),
        renderer: &Renderer,
        _theme: &Theme,
        bounds: Rectangle,
        _cursor: mouse::Cursor,
    ) -> Vec<Geometry> {
        let sun = self.rays.draw(renderer, bounds.size(), |frame| {
            let center = frame.center();
            frame.fill(&Path::circle(center, 50.0), Color::from_rgb8(0xff, 0xb3, 0x00));
            frame.translate(Vector::new(center.x, center.y));
            for ray in 0..12 {
                frame.with_save(|frame| {
                    frame.rotate(ray as f32 * std::f32::consts::PI / 6.0);
                    frame.stroke(
                        &Path::line(Point::new(70.0, 0.0), Point::new(100.0, 0.0)),
                        Stroke::default()
                            .with_width(6.0)
                            .with_color(Color::from_rgb8(0xff, 0x2e, 0x93))
                            .with_line_cap(LineCap::Round),
                    );
                });
            }
        });
        vec![sun]
    }
}

fn main() -> iced::Result {
    iced::run(Sun::update, Sun::view)
}

Widgets of your own

A type can implement iced’s advanced::Widget trait, as iced’s custom_widget, custom_quad, geometry and loupe examples do. A value of that type goes in a view like any other widget. The trait is iced master’s, so layout sets tree.size and returns nothing.

  • size, layout and draw are required. update, mouse_interaction, tag, state, diff, operate and overlay are optional. A method the impl leaves out runs iced’s own default, without calling your code.
  • draw fills quads with renderer.fill_quad. It draws meshes with draw_mesh. renderer::Quad takes its bounds, border, shadow and snap. with_translation and with_transformation run their closure where they are written, as in iced.
  • update receives iced’s events. Its Shell publishes a message, requests a redraw or captures the event.
  • A widget can wrap an Element, as loupe does. It forwards size, layout, draw, update, operate, overlay and the rest to it. iced shows the first overlay its overlay returns. The wrapped widget draws in its place among the widget’s own drawing, inside the transformation and clipping around it.
  • A widget keeps a State of its own with tree::Tag::of::<State>() and tree::State::new(value). tree.state.downcast_ref::<State>() reads it. let state = tree.state.downcast_mut::<State>(); changes it. A reload keeps the State while its type and its fields stay the same. A change to them starts it again from state.
  • Size<Length>, layout::Limits, Layout, Transformation, Rectangle::expand, graphics::color::pack and iced::Never work as in iced. iced::run((), view) runs a view whose Message is Never.

A widget’s drawing is kept while its draw runs and shown when draw returns. A call that fails shows its error in the widget’s bounds. Its drawing and its Shell requests are dropped.

A panic in a wrapped Element’s own code is an error of the call that reached it. ?play and snapshots draw with tiny-skia, which does not draw meshes. A mesh shows in a window.

circle.rs
use iced::advanced::layout::{self, Layout};
use iced::advanced::renderer;
use iced::advanced::widget::{self, Widget};
use iced::widget::{center, column, slider, text};
use iced::{border, mouse, Center, Color, Length, Rectangle, Size};

struct Circle {
    radius: f32,
}

impl widget::Meta for Circle {}

impl<Message, Theme, Renderer> Widget<Message, Theme, Renderer> for Circle
where
    Renderer: renderer::Renderer,
{
    fn size(&self) -> Size<Length> {
        Size {
            width: Length::Shrink,
            height: Length::Shrink,
        }
    }

    fn layout(&mut self, tree: &mut widget::Tree, _renderer: &Renderer, _limits: &layout::Limits) {
        tree.size = Size::new(self.radius * 2.0, self.radius * 2.0);
    }

    fn draw(
        &self,
        _tree: &widget::Tree,
        renderer: &mut Renderer,
        _theme: &Theme,
        _style: &renderer::Style,
        layout: Layout,
        _cursor: mouse::Cursor,
        _viewport: &Rectangle,
    ) {
        renderer.fill_quad(
            renderer::Quad {
                bounds: layout.bounds(),
                border: border::rounded(self.radius),
                ..renderer::Quad::default()
            },
            Color::from_rgb8(0xff, 0x2e, 0x93),
        );
    }
}

struct App {
    radius: f32,
}

impl Default for App {
    fn default() -> Self {
        App { radius: 50.0 }
    }
}

#[derive(Debug, Clone, Copy)]
enum Message {
    Radius(f32),
}

impl App {
    fn update(&mut self, message: Message) {
        match message {
            Message::Radius(radius) => self.radius = radius,
        }
    }

    fn view(&self) -> impl iced::Widget<Message> {
        let radius = self.radius;
        center(
            column![
                Circle { radius },
                text!("Radius: {radius:.0}"),
                slider(10.0..=100.0, radius, Message::Radius),
            ]
            .spacing(20)
            .width(300)
            .align_x(Center),
        )
    }
}

fn main() -> iced::Result {
    iced::run(App::update, App::view)
}

Subscriptions

A .subscription(..) method returns a Subscription<Message>. iced::time::every, iced::keyboard::listen, iced::event::listen and iced::window::frames work. Subscriptions combine with map and filter_map. Subscription::run(builder) takes a Rust function that returns a sipper, as Async code describes.

use iced::Subscription;
use iced::time::{self, Duration};

fn subscription(&self) -> Subscription<Message> {
    if self.running {
        time::every(Duration::from_millis(100)).map(|_| Message::Tick)
    } else {
        Subscription::none()
    }
}

Rust crates in an iced app

An iced app uses its dependencies the way Cargo dependencies describes. List iced in Cargo.toml at the revision rawr doctor prints.

Cargo.toml
[dependencies]
mathx = { path = "mathx" }
iced = { git = "https://github.com/iced-rs/iced", rev = "be88873d38544455e26c7a104eb757da2cbbac6b" }
mathx/src/lib.rs
pub fn double(x: i64) -> i64 {
    x * 2
}
src/main.rs
// rawr
use iced::widget::{Widget, button, column, text};
use mathx::double;

pub fn main() -> iced::Result {
    iced::run(App::update, App::view)
}

#[derive(Default)]
struct App {
    value: i64,
}

#[derive(Debug, Clone, Copy)]
enum Message {
    Bump,
}

impl App {
    fn update(&mut self, message: Message) {
        match message {
            Message::Bump => self.value += 1,
        }
    }

    fn view(&self) -> impl Widget<Message> {
        column![
            text(double(self.value)),
            button("Bump").on_press(Message::Bump),
        ]
    }
}

A custom iced widget written in Rust is imported like any other item. A Message can hold an imported value, and a match can bind it.

Async code

An app runs futures as iced tasks. A Rust function that returns a future gives a Task. That covers an async fn in a Rust crate and tokio::time::sleep. A Rust method that takes self by value and returns a future gives one too, as reqwest’s Response::text does. A Rust function that returns an iced Task, such as system::information(), gives that task.

// rawr
mod fetch; // native Rust: pub async fn size(url: String) -> usize

fn update(&mut self, message: Message) -> Task<Message> {
    match message {
        Message::Load => Task::perform(fetch::size(self.url.clone()), Message::Loaded),
        Message::Loaded(size) => {
            self.size = Some(size);
            Task::none()
        }
    }
}

Task::perform, Task::future, Task::sip, Task::abortable with task::Handle and Subscription::run work. Task::sip and Subscription::run take a Rust sipper. The interpreted code that maps a task’s values runs on the UI thread.

A variant passed as a function keeps its payload’s type. So .map(Message::Number) maps a Task<u32> when Number holds a u32. Task::<Message>::none() names the task’s message type with a turbofish, as in Rust.

A task’s future runs on iced’s thread pool, so it must be Send, as iced requires. rawr check names the Rust function whose future is not.

Async code in marked files

Code in marked files can be async too. async fn, async blocks, async move blocks and async closures work. .await takes a future’s output inside them. An async fn returns impl Future<Output = T> of its declared output, as in Rust. rawr runs such a future as iced’s Task<T>, so Task::perform takes it.

use iced::task::sipper;
use std::time::Duration;

fn start() -> (Download, Task<Message>) {
    let download = sipper(async |mut progress| {
        for step in 0..=10 {
            progress.send(step as f32 * 10.0).await;
            tokio::time::sleep(Duration::from_millis(100)).await;
        }
    });
    (Download::default(), Task::sip(download, Message::Progress, |_| Message::Done))
}

iced::task::sipper takes an async closure. The closure sends its progress with progress.send(value).await. Task::sip maps each value it sends, and then its output.

An async body runs on the UI thread, one step at a time. It stops at each .await and goes on from there once the future ends. Its locals keep their values in between, and no work it did runs again. .await works in a loop, a branch, a match arm and a call’s arguments. ? returns from the async body, as in Rust.

futures::future::join and try_join run two futures at once, through iced’s iced::futures. try_join ends at the first Err.

A program that does not depend on tokio still has tokio’s timers, channels, Mutex and join!, try_join! and select!. rawr runs its own tokio for them. In ?play its timers follow the recording’s clock, so the GIF shows each step. ?play’s tokio lists what it has. A program that depends on tokio uses the real crate instead.

A Rust async method that borrows its receiver does not cross.

Blocking work

tokio::task::spawn_blocking runs a closure from a marked file off the UI thread. Its handle is a future of Result<T, JoinError>, as in tokio. So Task::perform takes it, and .await takes its output in an async body.

use tokio::task::spawn_blocking;

fn update(&mut self, message: Message) -> Task<Message> {
    match message {
        Message::Count => {
            let limit = self.limit;
            Task::perform(spawn_blocking(move || count_primes(limit)), |result| {
                Message::Counted(result.unwrap())
            })
        }
        Message::Counted(primes) => {
            self.primes = Some(primes);
            Task::none()
        }
    }
}

The closure runs on a worker thread of its own when its task starts. It has its own evaluation, so the window keeps drawing while it works. It sees only the values it moved in, and those are its own, so its work never changes the State. A shared handle such as a channel sender stays shared, as in Rust. Its output reaches update on the UI thread, after the same check as every other step of a task. A reload drops the output of a closure that is still running, but it cannot stop the thread. The thread ends when the closure returns.

A closure that fails fails its task, as a failing update does. So the Result is always Ok, and JoinError exists only so the type can be named. tokio starts the closure when spawn_blocking is called. rawr starts it when the task runs, which iced does right after update returns it.

std::thread::spawn does not compile, and the error points to spawn_blocking. Its join waits on the calling thread, which would stop the UI thread. rawr runs a closure off the UI thread only as a task whose output reaches update. In a project that depends on tokio, tokio::task::spawn_blocking is still rawr’s, so it takes an interpreted closure there too.

A reload cancels running tasks. Reload an iced app says what happens to them.

What of iced is available

Most of iced’s everyday widgets and modules work. A missing one fails the check with unknown import.

Available

  • Layout: column!, row!, Column, Row, container, center, stack, space, scrollable, responsive, pin and lazy. Row::wrap gives a row::Wrapping that puts the children in as many lines as they need, with its own vertical_spacing and align_x. Container::clip cuts what its child draws outside it. keyed_column takes pairs of a key and an element and returns a Column. A key may be a number, a string or another value such as a Uuid. A child keeps its state when it moves to another place in the list.
  • Controls: button, checkbox, toggler, radio, slider, vertical_slider, pick_list, combo_box, text_input and progress_bar. pick_list takes its options as a Vec, a slice or an array. radio and pick_list find the selected value with its type’s PartialEq, as iced does. A hand-written eq decides which value is selected. slider moves over numbers, or over an angle with Degrees::RANGE or Radians::RANGE as its range. Checkbox has text_size.
  • Display: text, image, svg, qr_code, rule and tooltip. Svg::style takes a style function. So does Text::style, whose function returns a text::Style with a color and a selection. iced’s value types such as Color, ContentFit, Point and Vector have default(). A container’s style function can return a gradient::Linear made with new(angle) and add_stop, turned into the style with into(). image::Handle has from_path, from_bytes and from_rgba. svg::Handle has from_path and from_memory.
  • Rich text: rich_text, rich_text! and span. A string works as a span. on_link_click maps a span’s link to a message. A span without a link needs no link type.
  • Drawing: canvas, as above, and widgets of your own, as above. Frame::rotate takes radians as a number, a Radians or a Degrees.
  • Interaction: mouse_area, opaque, hover, sensor, component and widget::operation.
  • float draws its content scaled and moved above the rest. It takes scale, translate with a function of the content’s bounds and the viewport, and style with a function of the theme that returns a float::Style.
  • selector::find with a widget Id. Its Target has bounds and visible_bounds.
  • Modules: iced::time, iced::keyboard, iced::event, iced::window, iced::mouse, iced::font, iced::border and iced::theme. font::list() lists the system’s font families. Seed::LIGHT and iced’s other built-in seeds are in iced::theme::palette. Color, color!, Length, Fill, Center and the other alignment names work, also by their full paths such as iced::Center. space::horizontal() and space::vertical() work. std::time names iced::time’s Duration and Instant.

An available widget may still miss some of its methods. Rotation::radians_mut works, so *rotation.radians_mut() = angle turns a rotation in place. Animation<T> animates a bool or a number with go, go_mut, is_animating and interpolate at an Instant. go also ends a chain of builders, as in Animation::new(false).quick().go(true, now). A Vector adds, subtracts, and scales by an f32. A Point moves by a Vector, and two points differ by one. color!(0xffc8a8, alpha) and color!(r, g, b, alpha) take any f32 alpha. A helper such as text passes as a function, as in .map(text). A canvas program’s State may be a RefCell. canvas::Group and Cache::with_group work. A function of yours that takes impl Into<Length> takes a number or a Length.

Not available yet

  • A widget type of your own that borrows, as Circular<'a, Theme> does.
  • pane_grid, text_editor, markdown and grid.
  • iced::clipboard and application::timed.
  • Multi-window apps (iced::daemon), shaders and wgpu.
  • std::thread::spawn. tokio::task::spawn_blocking runs blocking work instead, as Blocking work describes.

iced’s own examples

iced master has 56 examples. 34 of them pass rawr check with // rawr added as the first line of their files: arc, bezier_tool, checkbox, combo_box, component, counter, custom_quad, custom_widget, delineate, download_progress, events, exit, ferris, geometry, lazy, loupe, modal, pick_list, progress_bar, qr_code, sandpiles, scrollable, slider, stopwatch, styling, svg, system_information, table, text, toast, tooltip, url_handler, vectorial_text and websocket. Six of the others use async code and now stop at other gaps. Two need iced::application::timed. The rest need iced items or Rust features listed above. The playground’s Examples menu has several of the passing examples ready to run.
