Embedding

Let the people who use your Rust app change its behaviour in Rust, without rebuilding it.

Your app links the rawr crate and loads rules, hooks or mods that its users write. With plain Rust, a user would need your source and a toolchain to change anything. With Lua or Rhai, they would learn another language, and you would write bindings for it. With rawr, the rules are Rust and use your app’s own types. A mistake fails when the rules load, with the error rustc would give.

Add the crate

The crate needs Rust 1.95 or newer.

cargo add --git https://github.com/airstrike/rawr rawr

An example

This is examples/rules in the repository, an app with its own Cargo workspace. It totals a bank statement by category. Its users decide the categories in rules.rs.

examples/rules/src/main.rsyour app
//! A bank-statement tool whose users write their own rules in Rust. It
//! exports `Transaction`, reads a CSV, loads the user's `rules.rs` and
//! prints the total for each category. `scripts/embed-check.sh` runs it.
//!
//! - `cargo run` uses `rules.rs`.
//! - `cargo run -- scripts/typo.rs` fails as the rules load.
//! - `cargo run -- scripts/wrong.rs` fails as the app looks up `category`.
//! - `cargo run -- rules.rs scripts/edited.rs` saves an edit and reloads.
//! - `cargo run -- rules.rs scripts/wrong.rs` keeps the old rules.

use rawr::{Engine, Exports, Func};
use std::collections::BTreeMap;

#[derive(Clone)]
#[rawr::export]
pub struct Transaction {
    pub date: String,
    pub payee: String,
    pub amount: f64,
}

#[rawr::export]
impl Transaction {
    pub fn is_income(&self) -> bool {
        self.amount > 0.0
    }
}

fn main() -> Result<(), Box<rawr::EvalAltResult>> {
    // Paths are relative to the app, as rustc names source files.
    std::env::set_current_dir(env!("CARGO_MANIFEST_DIR")).expect("the app's directory");
    let mut args = std::env::args().skip(1);
    let rules = args.next().unwrap_or("rules.rs".into());
    let edit = args.next();
    let transactions = read("transactions.csv");

    let mut bank = Exports::new("bank");
    bank.add::<Transaction>();
    let mut engine = Engine::new();
    engine.export(bank)?;

    // To show a reload, work on a copy the app can save an edit over.
    let path = match &edit {
        Some(_) => {
            let copy = std::env::current_exe().unwrap().with_file_name("rules.rs");
            std::fs::copy(&rules, &copy).expect("a copy of the rules");
            copy.to_string_lossy().into_owned()
        }
        None => rules,
    };

    let script = engine.load(&path)?;
    let category = script.func::<(Transaction,), Option<String>>("category")?;
    report(&category, &transactions)?;

    if let Some(edit) = edit {
        // The user saves new rules. The app reloads them between reports,
        // and `category` runs the new code at its next call. Rules that
        // fail to compile, or no longer fit `category`, leave the old rules
        // running.
        std::fs::copy(&edit, &path).expect("the edited rules");
        match script.reload() {
            Ok(true) => println!("reloaded"),
            Ok(false) => println!("unchanged"),
            Err(error) => eprintln!("{error}"),
        }
        report(&category, &transactions)?;
    }
    Ok(())
}

/// The total for each category, in name order. A transaction the rules
/// leave out is `other`.
fn report(
    category: &Func<(Transaction,), Option<String>>,
    transactions: &[Transaction],
) -> Result<(), Box<rawr::EvalAltResult>> {
    let mut totals = BTreeMap::new();
    for tx in transactions {
        let name = category.call(tx.clone())?.unwrap_or("other".into());
        *totals.entry(name).or_insert(0.0) += tx.amount;
    }
    for (name, total) in totals {
        println!("{name:<10} {total:>8.2}");
    }
    Ok(())
}

fn read(path: &str) -> Vec<Transaction> {
    let text = std::fs::read_to_string(path).expect("the transactions");
    text.lines()
        .skip(1)
        .map(|line| {
            let fields: Vec<&str> = line.split(',').collect();
            Transaction {
                date: fields[0].into(),
                payee: fields[1].into(),
                amount: fields[2].parse().expect("an amount"),
            }
        })
        .collect()
}

The rules import Transaction from the root the app named, as Rust code imports from a crate. They read its fields and call its methods as Rust would.

examples/rules/rules.rsyour user’s rules
use bank::Transaction;

fn category(tx: Transaction) -> Option<String> {
    let payee = tx.payee.to_lowercase();
    if payee.contains("coffee") {
        Some("coffee".into())
    } else if payee.contains("whole foods") || payee.contains("trader joe") {
        Some("groceries".into())
    } else if tx.is_income() {
        Some("income".into())
    } else {
        None
    }
}
cargo runcoffee -14.50 groceries -85.58 income 2500.00 other -56.49
  • engine.load(path) reads the rules and checks them against the app’s exports. It returns a Script. engine.script(text) does the same with text.
  • script.func::<(Transaction,), Option<String>>("category") looks up category once and checks its signature. The first type is a tuple of the parameter types, and the second is the return type. The result is a Func, a typed handle.
  • category.call(tx) runs the function. The arguments take their types from the handle. A call skips the script’s top-level statements.

Since the handle fixes the types, literals need no suffixes. A &str parameter takes a String.

src/main.rsyour app
use rawr::Engine;

const SCRIPT: &str = "
fn price(subtotal: f64, items: i64) -> f64 {
    subtotal + 4.99 * items as f64
}

fn greet(name: &str) -> String {
    format!(\"hello, {name}\")
}
";

fn main() -> Result<(), Box<rawr::EvalAltResult>> {
    let script = Engine::new().script(SCRIPT)?;
    let price = script.func::<(f64, i64), f64>("price")?;
    let greet = script.func::<(String,), String>("greet")?;
    println!("{:.2} {}", price.call(100.0, 2)?, greet.call("Rust".into())?);
    Ok(())
}
cargo run109.98 hello, Rust

A handle takes up to eight parameters. Clone it to share it. load and script take the engine, so a second script needs its own Engine with the exports installed again.

Reloading

script.reload() rereads the script’s file. If the text is unchanged, it does nothing and returns false. Otherwise it compiles the new text and checks every live handle against it. Then it publishes the new program, and every handle runs the new code at its next call. Your app decides when to reload, such as between two reports or when its file watcher fires.

A reload publishes all of the new program or none of it. If the new text doesn’t compile, or a handle no longer matches its function, reload returns the error and the old program keeps running. Reloading the same text again returns the same error without compiling it again. A dropped handle isn’t checked.

Reloads on two threads take turns: each one reads, compiles and publishes before the next one reads the file, so an older text never replaces a newer one.

Run the example with an edit. It loads a copy of rules.rs, saves scripts/edited.rs over the copy and reloads it.

cargo run -- rules.rs scripts/edited.rscoffee -14.50 groceries -85.58 income 2500.00 other -56.49 reloaded coffee -14.50 fuel -41.00 groceries -85.58 income 2500.00 streaming -15.49

With scripts/wrong.rs as the edit, the reload fails with E0308 and the second report uses the old rules.

Export your types

Put #[rawr::export] on a struct, on its impl block and on a free function.

  • On a struct, it exports the type and its pub fields. A script reads a field and assigns it.
  • On the impl block, it exports the pub methods and associated functions. A method keeps its receiver, so a script calls a &mut self method only on a mut binding.
  • On a free function, it exports the function.

Private fields and methods stay private. As in Rust, a field and a method may share a name. Calling a field or reading a method without parentheses is rustc’s error.

Exports::new names the root that scripts use. add takes each exported struct and function by name. Engine::export installs them. Export everything before you load a script that uses the exports. After that, the exports can’t change, and Engine::export returns an error.

The first release exports one impl block per struct. It doesn’t export generic items, &mut parameters or functions that return a reference.

What crosses the boundary

A handle’s parameters and return type, and the exported items’ own, are i64, f64, bool, char, String, (), Option of these and exported structs. An exported struct crosses as itself. A script gets the Rust value, and Rust gets back the value the script returns. A script parameter may borrow, as &str or &Transaction does, and takes the handle’s owned value. Integers are i64 and floats are f64, so a script function that takes an i32 doesn’t match an i64 handle.

The check knows the items exported to the engine that loads the script. A call to any other name is rustc’s error at the name.

Statements and expressions

A script can be items, as above, or plain statements. Statements run as if they were the body of fn main() { .. }, the way rustdoc runs a doctest. The value of the last expression is what Engine::eval returns. Functions in the script can’t read its let variables, as in Rust.

src/main.rsyour app
use rawr::{Engine, Scope};

fn main() -> Result<(), Box<rawr::EvalAltResult>> {
    let engine = Engine::new();
    println!("{}", engine.eval::<i64>("40 + 2")?);
    println!("{}", engine.eval::<i64>("fn double(x: i64) -> i64 { x * 2 } double(21)")?);

    let mut scope = Scope::new();
    scope.push("count", 40_i64);
    engine.run_with_scope(&mut scope, "count += 2;")?;
    println!("{}", scope.get_value::<i64>("count").unwrap());
    Ok(())
}
cargo run42 42 42

A Scope holds variables across runs. A value pushed into it becomes a typed variable in the script. Its type comes from its value. An i64, f64, bool, char or string has that type. A constant from push_constant can’t be assigned. Engine::eval_expression takes one expression and refuses statements.

Capturing output

By default println! and print! write to the process’s stdout. eprintln! and eprint! write to stderr. Engine::on_output sends that text to a callback instead. The callback gets the stream and the exact text. println! text includes its newline.

src/main.rsyour app
use rawr::{Engine, Output};
use std::sync::{Arc, Mutex};

fn main() -> Result<(), Box<rawr::EvalAltResult>> {
    let mut engine = Engine::new();
    let lines = Arc::new(Mutex::new(Vec::new()));
    let sink = lines.clone();
    engine.on_output(move |output, text| {
        sink.lock().unwrap().push((output == Output::Stderr, text.to_string()));
    });

    let script = engine.script(
        r#"
        fn main() {
            println!("to stdout");
            eprintln!("to stderr");
        }
        "#,
    )?;
    script.func::<(), ()>("main")?.call()?;
    println!("{:?}", lines.lock().unwrap());
    Ok(())
}
cargo run[(false, "to stdout\n"), (true, "to stderr\n")]

In a release build

An app that runs scripts ships the rawr crate, because the interpreter runs the scripts at run time. This differs from the dev loop, where Cargo compiles the marked files and no interpreter ships.

Errors

Errors print as rustc prints them, with the code, the message and the source line. Display prints them. So does the Debug output that fn main() -> Result shows when ? returns one. load names the file, and script names the source <script>.

A mistake in the rules fails when they load:

cargo run -- scripts/typo.rsexit 1
Error: error[E0609]: no field `payye` on type `Transaction`
 --> scripts/typo.rs:4:11-4:16
 4 |     if tx.payye.contains("Coffee") {
   |           ^^^^^

A function whose signature differs from the handle’s fails when the app looks it up. The error points at the script’s signature:

cargo run -- scripts/wrong.rsexit 1
Error: error[E0308]: mismatched types
 --> scripts/wrong.rs:3:1-3:39
 3 | fn category(tx: Transaction) -> String {
   | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ expected `fn(Transaction) -> Option<String>`, found `fn(Transaction) -> String`

A function the script doesn’t have is E0425. Here the app asks the price script above for cost:

error[E0425]: cannot find function `cost` in this script
 --> <script>
  = help: the app calls `cost` as `fn(f64) -> f64`

Every call returns Result<_, Box<EvalAltResult>>. A runtime error, such as a panic or a limit the script reached, names the problem and its position in the script.

Limits

An Engine can bound what a script may do. Set the limits on the engine before loading a script.

  • set_max_operations stops a script after a number of steps. An endless loop then fails with Too many operations.
  • set_max_call_levels bounds recursion depth.
  • set_max_string_size, set_max_array_size and set_max_map_size bound the size of values.
  • on_progress runs a callback as the script runs. Returning Some(value) from it stops the script. A host can use it for a wall-clock deadline.

The playground and the ?play bot use these limits for untrusted snippets.
