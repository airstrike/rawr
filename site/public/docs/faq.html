Frequently asked questions

Short answers to common questions about how rawr works and where it is going.

What kind of interpreter is rawr?

rawr is a tree-walking interpreter over a typed program. Its front end parses Rust. It resolves names and checks types, traits and generics before anything runs. It reports errors the way rustc does. Then an evaluator walks the checked program and runs it.

Values at run time carry a tag for their type. They are reference-counted. Everything a program calls is native Rust. That includes iced, the standard library and the Rust crates you import.

An experimental bytecode VM also exists. It is off by default.

Where does the evaluator come from?

rawr began as a fork of Rhai. Rhai is an embedded scripting language for Rust. Its source is on GitHub. rawr keeps Rhai’s evaluator as its foundation. It also keeps Rhai’s dynamic values and its machinery for calling host functions. These parts are mature. rawr adds a typed Rust front end on top of them, and every program and script is typed Rust.

Thank you to the Rhai authors for the work that rawr is built on.

rawr is not compatible with Rhai scripts. Rhai is licensed under MIT or Apache-2.0. rawr uses the same two licenses. The LICENSE files in the repository carry the attribution.

How fast is it?

Interpreted rawr code runs slower than the same code compiled by rustc. Calls into native code run at full speed. In an iced app most of the time goes to native iced code. Layout and drawing are examples.

The interpreter shows in a tight loop that runs many times. Keep a loop like that in a Rust crate and import the crate. The crate is compiled natively.

Saving a file in a running app reloads it in about 0.2 s.

How does rawr handle borrow checking?

rawr does not have a full borrow checker. It rejects two live &mut borrows of the same value. It accepts some programs that rustc rejects. Use after a move is one example. The language page lists these cases.

Values are reference-counted, so a rawr program cannot corrupt memory. Borrow checking only rejects programs. It never changes what a valid program does. A program that rustc accepts behaves the same in rawr.

rustc is what tells you whether a program is valid Rust. rawr check runs cargo check on the crate after its own check. It fails if either check fails. rawr run runs cargo check in the background. With an iced app, its errors appear in the window and don’t block the reload. With a plain program, they are printed after the program ends. rawr files are ordinary .rs files, so rust-analyzer checks them as well.

How are generics handled?

rawr checks generics as rustc does. Each call is checked against the bounds of the function it calls. A missing bound is an error.

At run time each generic function has one body. rawr does not make a copy for each type. Values carry their types, so a trait method call dispatches on the value it is called on. A call like T::default() has no value to dispatch on. rawr passes the type to the function as a hidden argument for these calls.

A function whose signature names a type parameter inside an iced type gets the same hidden argument. fn card<Message: Clone>(label: &str) -> Element<'static, Message> is one such function. Each iced call in its body uses the caller’s message type at run time.

Generic code in an imported Rust crate is compiled natively. It is compiled for the concrete types your program uses.

Code that relies on a separate copy of a function for each type is not supported. std::mem::size_of::<T>() is an example.

Why not use Miri or interpret rustc’s MIR?

Miri interprets the whole program. It cannot call native code. iced, wgpu and the window system all need native code, so Miri cannot drive them. Miri is also slow on purpose. It checks each operation for undefined behaviour.

An interpreter for rustc’s MIR would still have two problems. The first is that iced is generic over your app’s message type. Native iced code is compiled for concrete types. A type defined in interpreted code has no compiled copy of iced to call. The second is that rustc’s front end would run on each edit. That takes much longer than a 0.2 s reload.

Using rustc’s typed output as rawr’s front end is a possible future direction.

Can I ship a rawr app?

Yes. A rawr project is an ordinary Cargo crate. cargo build --release builds it natively. No interpreter ships with it.

rawr runs the files marked // rawr while you develop. Cargo ignores the marker, because it is a comment. If you use #[preview] or #[widget], add the rawr-macros crate to [dependencies]. Under cargo those attributes leave the item as written.

Is it safe to run snippets on the bot?

The ?play bot runs each snippet in a separate process. That process has time and memory limits. It writes nothing to disk. rawr code has no access to files, processes, the network or the environment. The playground runs snippets the same way.
