How it works

How rawr runs Rust without compiling it, and why it is built this way.

What kind of interpreter is rawr?

rawr is a tree-walking interpreter over a typed program. Its front end checks names, types, traits and generics before anything runs. Then an evaluator walks the checked program.

Values at run time carry a tag for their type and are reference-counted. Standard library types such as Vec and HashMap are backed by native Rust code. So are the crates a program imports and iced’s widgets.

How fast is it?

Calls into native code run at native speed. In an iced app most of the time goes to native iced code, such as layout and drawing.

The interpreter shows in a tight loop that runs many times. Keep a loop like that in a native module or a crate, and Cargo compiles it.

In RawrGallery, an edit to a marked file was live in the running app in about 0.2 s on an Apple Silicon Mac.

How does rawr handle borrow checking?

rawr checks the borrows of a function’s locals as rustc does. A borrow ends at its last use along the function’s control flow, through branches, loops, break, continue, return and ?. rustc calls this rule non-lexical lifetimes (NLL). A conflict is reported with rustc’s code: E0499, E0502, E0503, E0505, E0506, E0597 or E0716. rawr also rejects a use after a move, as rustc’s E0382 does.

borrow.rs
fn main() {
    let mut v = vec![1];
    let big = v.len() > 5;
    let r = &mut v;
    if big {
        v.push(2); // fine: `r` isn't used on this path
    } else {
        r.push(3);
    }
    let first = &v[0];
    v.push(4); // error[E0502]: `first` is used below
    println!("{first}");
}

A borrow also flows through values. A call’s result keeps what the function’s signature says it keeps. rawr reads that from the lifetimes written in it, the outlives bounds such as 'b: 'a, 'static, the type parameters, and Rust’s elision rules when no lifetime is written. std’s methods, such as v.first() and s.trim(), keep what their signatures say too. A struct, a tuple, an array, a Vec, a map or an Option holds the borrows it is made of or is given, as v.push(&x) gives one.

kept.rs
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() > b.len() { a } else { b }
}

fn main() {
    let mut x = String::from("long one");
    let y = String::from("short");
    let l = longest(&x, &y);
    x.push_str("!"); // error[E0502]: `l` keeps `x` borrowed
    println!("{l}");
}

A function’s body is checked against its own signature. A returned borrow of one of its locals or of a temporary is rustc’s E0515. A returned borrow of a parameter must outlive the lifetime the signature gives the output. Where it doesn’t, rawr reports rustc’s E0621 or its “lifetime may not live long enough”. An output lifetime that elision can’t fill is E0106, and so is a reference without a lifetime in a struct’s field.

A temporary lives to the end of its statement. A let keeps a temporary it borrows with & to the end of its block, as rustc’s temporary lifetime extension does. That covers let r = &String::from("a"); and the same borrow inside a struct, a tuple, Some, a block’s tail or a branch. A temporary that a method borrows, as in String::from("a").as_str(), isn’t extended. Using its value after the statement is E0716. A constant such as &5 or &[1, 2] is promoted to 'static and borrows nothing.

temporary.rs
fn name() -> &'static str {
    let s = String::from("rawr");
    &s // error[E0515]: returns a borrow of `s`
}

fn main() {
    let kept = &String::from("kept"); // fine: the `let` extends it
    let lost = String::from("lost").as_str(); // error[E0716]
    println!("{kept} {lost} {}", name());
}

A pattern borrows, reads or moves only the parts it binds and tests, as in rustc. A ref or ref mut binding is a borrow of its part. So is a binding in a match through & or &mut.

The check looks at each function on its own. Some borrows are not checked yet: one a closure keeps after its statement, an item that a method gives from a container (copied, collect, next), a value with a Drop impl that holds a borrow, a lifetime written in a type inside a function body, and a returned parameter whose type has several lifetimes. rawr runs such a program, and the cargo check that rawr run keeps going in the background reports any error. The Overview lists them.

Values are reference-counted, so a program can’t corrupt memory. At run time a shared borrow is a copy and a &mut local is the place it borrows. A &mut local that is given new borrows, as in r = &mut b;, holds which local it borrows, and each use reaches that local. The checker is what makes that match Rust. Borrow checking only rejects programs. It never changes what a valid program does.

rawr aims to run every program that rustc accepts with Rust’s meaning. Where it can’t yet, it refuses the program. A few known differences remain, and each one is a defect to fix.

Marked files are ordinary .rs files, so rust-analyzer checks them too.

How are generics handled?

rawr checks each generic call against the bounds of the function it calls, as rustc does.

At run time each generic function has one body. Values carry their types, so a trait method call dispatches on the value it is called on. A call like T::default() has no value to dispatch on. rawr passes the type to the function as a hidden argument for these calls.

In an iced app, a function whose signature names a type parameter inside an iced type gets the same hidden argument. fn card<Message: Clone>(label: &str) -> Element<'static, Message> is one such function. Each iced call in its body uses the caller’s message type at run time.

Generic code in an imported crate is compiled natively for the concrete types your program uses.

Code that relies on a separate copy of a function for each type is not supported. std::mem::size_of::<T>() is an example.

Why not use Miri or interpret rustc’s MIR?

Miri cannot call native code, so it cannot drive iced, wgpu or the window system. Miri is also slow on purpose, because it checks each operation for undefined behaviour.

An interpreter for rustc’s MIR would have two problems. Native iced code is compiled for concrete message types, and a type defined in interpreted code has no compiled copy of iced to call. rustc’s front end would also run on each edit. That takes much longer than a reload does today.

Using rustc’s typed output as rawr’s front end is a possible future direction.
