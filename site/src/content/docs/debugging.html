Debugging

Debug a rawr program in a window, in a terminal or from your editor: set breakpoints, step, read the call stack and expand values field by field, while each save still reloads the program.

A run has one debugger session. Each shell is a view of it: rawr gui in a window of its own, rawr tui in a terminal, your editor through rawr dap, and an agent through rawr mcp. Every shell shows the same breakpoints and values, so several can work on one run at once, as With an agent on the same run explains.

The debugger window

rawr gui [path] opens a window on the program’s run. It attaches to a rawr run already going for the program, else it starts one and ends it when the window closes. The window draws in a process of its own, so it keeps drawing while the program is paused. Figure 1 shows it paused at a breakpoint.

  1. The toolbar continues and pauses (F8), and steps over (F10), into (F11) and out (Shift+F11), as in DevTools. Beside it is where the program is: running, or paused and why.
  2. The source shows the file around the paused line, which is highlighted. Click in the gutter left of a line number to set a breakpoint there, drawn as a red dot, and click it again to clear it.
  3. The call stack lists the frames, each by its Rust path. Pick one to see its bindings.
  4. The bindings are the picked frame’s, each as Rust’s {:?} prints it. A struct, a list or a map opens into its fields or items. Here the map players is open to a row per key.
  5. The console evaluates Rust where the program is paused, in the picked frame.
  6. The output is what the program printed. A program with a window also shows its latest frame in the debugger window.

In a terminal

rawr tui [path] is the same debugger in a terminal, with the same panes: the source, the frames, the bindings and the breakpoints, the program’s output under them, and the keys along the bottom. It attaches to a run or starts one, as the window does. Tab moves between the source, the frames and the bindings, and the arrow keys or j and k move within one.

KeyDoes
bSets or clears a breakpoint on the source line under the cursor.
BAsks where to break: file:line, a line, or a function.
pPauses the running program.
s, i, oSteps over, into and out.
cContinues.
eAsks for Rust to evaluate where the program is paused.
Enter, →, ←Open and close a binding, in the bindings pane.
qQuits the debugger. The run goes on if the debugger didn’t start it.

In your editor

rawr dap is a Debug Adapter Protocol server on stdio. It comes with rawr itself. An editor that speaks the protocol launches a program under it, or attaches to one running in a terminal.

  • Launch starts rawr run on program, a crate’s directory or Cargo.toml, or one .rs file, with args. Relative paths start at cwd. The program waits at its first statement until the editor has set its breakpoints and sent configurationDone, so a breakpoint in code that runs at startup is hit.
  • Attach reaches a rawr run started in a terminal for program. A run started in a terminal has no debugger until a shell asks. The program then takes one at its next step, keeping its state and its process, with or without Rust dependencies. Its stack leaves out the calls that were under way when the debugger arrived, except the one the program is in, which shows without its name.
  • Breakpoints go on lines and on functions. A line with no statement is refused, with why.
  • Next, step in and step out stop at the program’s next statement. Pause stops a running program at the next statement it runs. A program waiting in a window’s event loop pauses when the loop calls into it again. A step past the end of a function the event loop called goes on into the loop and stops at the next statement the program runs, such as the next view or update.
  • The call stack names each frame by its Rust path, such as counter::App::update.
  • Variables show each binding as Rust’s {:?} prints it. A struct, a tuple, a list or a map expands into its fields or items, and those expand in turn.
  • The Debug Console and watch expressions evaluate Rust where the program is paused, as if it were a block written just before the paused statement. rustc’s rules for that line apply. With a caller’s frame selected, it runs in that caller, before the statement making the call, and a change stays in that caller. See eval.
  • A save reloads the program as at a terminal. The Debug Console says when it reloaded, restarted or failed. Breakpoints follow their line’s text across saves.
  • The program’s output goes to the Debug Console.

VS Code

The Rawr extension in editors/vscode-rawr adds a debugger of type rawr. Package and install it:

cd editors/vscode-rawr
npx @vscode/vsce package --skip-license --out rawr.vsix
code --install-extension rawr.vsix

Press F5 in a Rawr file to run the crate it belongs to, found by the nearest Cargo.toml above it, or the file alone when there is none. A .rs file that isn’t marked runs nothing and says so. Or add a configuration to .vscode/launch.json. The Rawr: run and Rawr: attach snippets write these:

{
  "type": "rawr",
  "request": "launch",
  "name": "Rawr: run",
  "program": "${workspaceFolder}"
}

For attach, "request": "attach" with the same program. The rawr.path setting names the rawr command when it isn’t on PATH.

Neovim

With nvim-dap:

local dap = require("dap")
dap.adapters.rawr = { type = "executable", command = "rawr", args = { "dap" } }
dap.configurations.rust = dap.configurations.rust or {}
table.insert(dap.configurations.rust,
  { type = "rawr", request = "launch", name = "rawr run", program = "${workspaceFolder}" })
table.insert(dap.configurations.rust,
  { type = "rawr", request = "attach", name = "rawr attach", program = "${workspaceFolder}" })

Helix

In the project’s .helix/languages.toml. It replaces Helix’s debugger for Rust in that project only:

[[language]]
name = "rust"

[language.debugger]
name = "rawr"
transport = "stdio"
command = "rawr"
args = ["dap"]

[[language.debugger.templates]]
name = "rawr run"
request = "launch"
completion = [{ name = "program", completion = "filename", default = "." }]
args = { program = "{0}" }

[[language.debugger.templates]]
name = "rawr attach"
request = "attach"
completion = [{ name = "program", completion = "filename", default = "." }]
args = { program = "{0}" }

Then :debug-start rawr run, or Space g for the debug menu.

Zed

Zed takes a debug adapter from an extension. An extension whose extension.toml declares [debug_adapters.rawr] answers get_dap_binary with the command rawr and the arguments ["dap"], over stdio. rawr ships no Zed extension yet. With one installed, .zed/debug.json names it:

[
  { "label": "rawr run", "adapter": "rawr", "request": "launch", "program": "$ZED_WORKTREE_ROOT" },
  { "label": "rawr attach", "adapter": "rawr", "request": "attach", "program": "$ZED_WORKTREE_ROOT" }
]

In the playground

The playground has a debugger too. Click the bug icon beside Share. The program starts again from its start under the debugger, in the browser, and a debugger panel opens right of the output, with a console under the code. Click the bug again to turn it off, and the program runs as before.

  • Click a line number to set a breakpoint there, and click it again to clear it. Breakpoints set before a run are in place before main starts.
  • The panel’s toolbar continues (F8), pauses (F8), and steps over (F10), into (F11) and out (Shift+F11), as in DevTools. The paused line is highlighted, and the panel lists the frames and the bindings of the one you pick.
  • The console runs Rust where the program is paused, in the frame you pick. Enter evaluates, Shift+Enter adds a line, and each answer stays above the prompt.
  • The debugger needs WebAssembly JS Promise Integration (JSPI). In a browser without it, the bug icon is greyed, and a tap or a click on it says why.
  • A pause stops main’s own code, and the functions it calls. A function the page calls, such as an iced view or update, runs whole.

With an agent on the same run

Every shell attached to a run hears each pause, resume and reload. An agent’s click through rawr mcp that reaches a breakpoint stops the editor there too, and a continue from the editor lets the agent’s program go on. The run’s output reaches every shell, even when the run started in a terminal. A shell that attaches later first shows the last of what the run printed before it. This holds for a program with Rust dependencies too, for what its own code prints. Text a dependency writes to the terminal itself reaches no shell.

Breakpoints are the run’s, not one shell’s. A breakpoint set or cleared from rawr tui, rawr gui, an agent or another editor shows in every other shell at once: the editor adds or removes it in its gutter, and a shell that attaches later shows those already set.

Limits

  • The protocol sees one thread: the one that runs the program’s code.
  • Code in Rust dependencies runs whole. A step can’t stop inside a crate’s function, and its lines take no breakpoints.
  • A pause inside a call from native code, such as a window’s event loop, holds that loop. The window doesn’t redraw or take input until the program goes on.
  • Evaluation in a caller’s frame refuses a binding the running call borrows, such as one passed to it as &mut, until the call returns. A frame entered before the debugger attached isn’t on the stack, so code can’t run in it.
  • A value whose Debug text isn’t in the shapes the standard derives write, as a hand-written impl may print, shows whole, without fields.
  • Launch refuses a program that draws a terminal UI. Run it with rawr run in a terminal and attach.
