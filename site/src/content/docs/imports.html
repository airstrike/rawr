Imports

Use the crates in your Cargo.toml and your native modules from marked code. rawr-import compiles them with Cargo.

Install rawr-import

Once rawr-import is installed, rawr hands it every program with dependencies or native modules.

The installer from Start includes it:

curl -LsSf https://rawr.airstrike.fyi/install.sh | sh

rawr-import runs on 64-bit macOS and 64-bit Linux. It reads crate APIs with a Rust nightly and its rustc-dev and rust-src components: the nightly the project names, or the pinned nightly-2026-07-11 when it names none. The first program that needs them installs them through rustup, once per machine. Which nightly explains the choice. It has been tested on Apple Silicon Macs. CI runs it on x86_64 Linux. Requirements lists the platforms.

An iced app runs on rawr-import too. iced says how.

Project setup

A crate that cargo run runs needs only the marker. rawr-import adds no file to it.

Your own cargo builds rawr’s runner. It runs from the project’s directory, with your shell’s environment. It uses the project’s toolchain, Cargo config and profiles, and it builds in the project’s target/. So rawr run and cargo build share every compiled dependency, and each compiles a dependency only once. That holds for a path dependency inside the workspace too. rawr links each one into target/rawr/runner at the path it has in the workspace, because Cargo names a path package by that path.

rawr’s runtime

rawr’s own crates are compiled once per machine, not once per project. The first rawr run on a toolchain compiles them into runtime/ in rawr’s home, which is ~/.cargo/rawr unless RAWR_HOME says otherwise. Every project’s runner links that copy, so a second project on the same toolchain compiles none of rawr’s crates. Your own cargo compiles the copy, with the project’s compiler.

The copy is keyed by rawr’s version and sources, the lockfile rawr was released with, the compiler’s rustc -vV, and the runtime’s features and profile. Nothing about a project goes in, so two projects with different dependencies share it. A new toolchain or a new rawr compiles a new copy, and a runner never links a copy compiled for another key. Copies unused for a day are removed, apart from the three used last. Removal never delays a run.

A crate that both your project and rawr use, such as futures-core, compiles twice: once in your target/ and once in rawr’s runtime. The two copies never meet, because rawr’s runtime takes no other crate’s types from a runner.

A project whose runner can’t link the shared copy compiles rawr’s crates in its own target/, as before, and rawr says so once. That happens when a native library or symbol is defined both by the project’s crates and by rawr’s.

The rawr crate compiles at opt-level = 3, so the interpreter inside the runner is fast. Set RAWR_RUNTIME_OPT_LEVEL to 0, 1, 2, s or z to compile it at a lower level. The runtime compiles faster, and scripts run slower. Each level is a copy of its own.

Which nightly

rawr reads your dependencies’ APIs with a nightly, because only a nightly has rustc’s private crates. It picks the nightly as rustup picks the toolchain cargo runs on in the project’s directory. cargo +nightly rawr run or RUSTUP_TOOLCHAIN names it first. Next come a rustup override set for the directory and a rust-toolchain.toml or rust-toolchain file in the project’s directory or above it. A project that names none of these, or names a stable or beta release, reads with the pinned nightly-2026-07-11, not rustup’s default. Its own code still builds on the toolchain it names.

A nightly the project names must be one from nightly-2026-07-11 through nightly-2026-11-02. A nightly outside that range stops the run with an error that names the range. A name such as nightly is fine while the nightly it installs is in the range.

The range moves forward as nightly does. Every day CI builds the driver on the latest nightly and reads std with it. When that works, a pull request moves the range’s end to that nightly, and the next release carries it. When it fails, an issue titled “Nightly <date> breaks rawr-import-driver” records the compiler’s errors until the driver is taught the change. Until then, a nightly updated past the range stops the run, and a dated nightly from the range keeps working.

rawr reads crate metadata with rawr-import-driver, which links the compiler it reads with. The installed driver is the pinned nightly’s. For any other nightly, the first run on it builds a driver from the sources rawr-import carries, and prints Building rawr-import-driver for <nightly> (once per toolchain). The driver goes in drivers/ in rawr’s home, under the nightly’s rustc commit. A later run on the same nightly uses it, and updating nightly to a new commit builds one more. The same build writes that nightly’s std table beside the driver, and rawr checks programs against it, so a program sees the std of the nightly it compiles against.

The runner still builds with the project’s own toolchain, as cargo build does.

rawr’s check build of your dependencies runs on that nightly. It is a check build. It runs build scripts and compiles proc macros, and for every other crate it writes only the metadata rawr reads. That build runs in nightly/<toolchain> in rawr’s home, one directory per machine for each nightly, apart from the units cargo build uses. Cargo decides what in it is fresh, so a second project checks only the crates its own closure adds, such as its own crate and its path dependencies. Cargo names a path dependency there by its absolute path, so two projects’ same-named path crates never stand in for each other. One project builds there at a time. While another holds it, rawr prints Cargo’s Blocking waiting for file lock on build directory. cargo clean doesn’t reach this directory. rawr cache clean removes it when no build has used it for an hour, and the directory of a nightly no build used for a day goes then.

Shared bindings

What rawr reads of a crate is kept once per machine, in bindings/ in rawr’s home. A later project that uses the same crate reads it from there. When every crate a program uses is there, rawr runs no nightly build and doesn’t start the nightly compiler. The first such run still asks the pinned cargo how the project resolves, which compiles nothing. Your cargo still compiles the crates themselves in your target/.

The first time a program reaches a crate, rawr reads the crate’s whole public API, including the paths its macros name. So a later program, or a save, that uses other items of it needs no nightly build either. This holds for a large crate such as iced too. Reading all of iced adds seconds to the first run that reaches it, against minutes for that run’s builds, and its entry takes about 90 MB. A crate whose whole API can’t be read keeps what each program read instead, and a program that uses other items reads them once with the nightly.

A project’s next run with nothing changed reuses its last resolution, so it doesn’t ask cargo again.

A crate is shared when it, and every crate it depends on, comes from a registry or from a git commit. A path dependency, a workspace member, and any crate that depends on one, stay in the project’s target/rawr.

Each entry is keyed by the crate alone, never by a program. The key covers:

  • the crate’s version, features, profile and target;
  • the checksum or commit of every crate it depends on;
  • the pinned nightly’s rustc -vV commit;
  • the format rawr reads crates in.

A new rawr whose format is unchanged keeps the entries already there.

Before sharing bindings, rawr compares the extraction nightly’s build-script results with your toolchain’s results: every cfg, environment value and generated file, including scripts used to build procedural macros. If the results differ or cannot be read, the run continues with local bindings and rawr names the crate it could not share. A shared entry must also match a later project’s results. A mismatch stops that run before execution and names the crate; rawr removes the entry when no reader holds it. When an adapter fails to compile and those results differ, the error names the crate whose API differs between the two toolchains.

Before using a shared entry, including during rawr check and a remembered run, rawr checks the toolchain and the files and environment variables the crate declared as inputs. A change sends the crate through extraction again. Declared files remain watched during a live run, including when its bindings were shared. While rawr reads an entry, another project cannot replace or remove it partway through the read.

An entry unused for 30 days is removed when another is added, unless a run is reading it. Removal never delays a run.

The toolchain must be Rust 1.95 or newer. With an older one, rawr run stops with RAWR-ENVIRONMENT-PROJECT-BUILD and says to update it.

A member of a Cargo workspace builds the same way. Its toolchain and config are the workspace’s, and it builds in the workspace’s target/.

A cargo script with dependencies builds the same way too, from its own directory in rawr’s home. Every script shares one build directory there. Run explains it.

rawr keeps what it makes for a crate in target/rawr. For a workspace member, that is target/rawr/members/<path> in the workspace’s target/, where <path> is the member’s directory. cargo clean removes it.

Use a dependency

Declare the dependency in Cargo.toml and import its items with use. You write no bindings.

Cargo.toml
[dependencies]
mathx = { path = "mathx" }
mathx/src/lib.rsa native crate
pub fn double(x: i64) -> i64 {
    x * 2
}
src/main.rsneeds the mathx crate
// rawr
use mathx::double;

fn main() {
    for n in 1..=3 {
        println!("{n} doubled is {}", double(n));
    }
}
on your machinerawr run1 doubled is 2 2 doubled is 4 3 doubled is 6

The first run compiles the dependencies and the runner. For a new project that uses semver, that took about 7 s on an Apple Silicon Mac, with semver’s bindings already in rawr’s home. The first project on a toolchain also compiles rawr’s runtime once for every project, which took about 2 minutes. After an edit to src/main.rs, the next run reused that build and took about 2.4 s.

rawr uses the dependencies as Cargo resolves them. It reads only the items your code uses. A path resolves as rustc resolves it. After use iced::widget::operation;, operation::scrollable::snap_to(..) names the function in the module nested under operation, at any depth and through the crate’s re-exports.

Native modules

A module of your crate whose first line isn’t // rawr is native Rust. rawr-import compiles it with Cargo, and marked code calls it as it calls a dependency. Calls from native code into marked code need a native crate root, as Run explains.

A native function can take and give a dependency’s types, by value or by reference. With mod label;, the call label::describe(&version) works when label.rs has pub fn describe(version: &semver::Version) -> String. rawr reads semver::Version there as rustc does, as semver’s own type, so the value your program got from semver is the one the function takes.

Imported values

A public imported struct can be constructed with its fields. A generic constructor infers its type arguments from those fields and from the type its use requires, then fills any remaining arguments from their defaults. For example, Size { width: Length::Shrink, height: Length::Shrink } makes a Size<Length>. Public fields can be assigned through a mutable value or a native &mut, as a custom widget’s tree.size = Size::new(width, height) changes the tree the crate lent it. Nested field assignments work when the intermediate fields are Copy.

A borrow of a crate value field, as &screenshot.rgba, lends the field where it is, and the struct stays whole. So save(&screenshot.rgba, screenshot.size.width) reads size after the borrow, as in Rust. A method that takes the field &self, its own or its Deref target’s, borrows it the same way, as screenshot.rgba.len() does. Moving the struct while the borrow is used is refused with rustc’s E0505. The lend lasts until the end of the statement, or until the end of the block for a let. Any other read of such a field still moves the struct. A field of a generic struct is still read that way too.

A struct in a marked file can hold a value of an imported type. It can derive Default, Debug, Clone and Copy when the crate implements that trait for the type. == and != work when the crate implements PartialEq. An imported value can key a HashMap or a HashSet when the crate implements Hash and Eq. It can key a BTreeMap or a BTreeSet when the crate implements Ord, as iced’s window::Id does. The map keeps its keys in the crate’s order. {:?} prints the crate’s Debug text. to_string() and {} print its Display text. Preset::to_string is a function value, as in pick_list(.., Preset::to_string).

A method whose result rawr cannot hold returns that result’s Display text instead, when its type has one. So chrono’s now.format("%H:%M:%S") is a String. A method that lends a &str from its value, as url’s url.scheme() does, gives a &str, as in Rust. rawr strings can’t point into native memory, so the call makes a copy of the text. rawr’s borrow checker keeps the value borrowed while the &str is used, as rustc does. So let s = url.scheme(); url.set_scheme("http"); println!("{s}"); is refused with rustc’s E0502, and changing url after the last use of s is fine.

A &self method that lends a slice of strings or crate values from its value, as iced’s combo_box::State::options() lends its &[T], gives the slice in place, with nothing copied. .len(), indexing, a for loop and iterator methods such as .iter().position(..) read the elements where they are. Reading a field of an element, as family.name, still copies that field. The value stays borrowed while the slice is used, as rustc keeps it. A slice of numbers, and one lent by a &mut self method or by a method that takes arguments, is still a copy.

A method can return a borrow guard, which is a type that borrows the value it came from and dereferences to what it guards. RefCell::borrow_mut returns one, and so do Freya’s State::read and State::write. *count.read() is the guarded value, and *count.write() += 1 changes it, as in Rust. rawr never keeps a guard. Each read calls the method, copies the value with its Clone, and drops the guard before the call returns. Each store calls the method again and assigns through the guard. *count.write() += 1 calls write once, as Rust does. rawr evaluates the right side first, then calls write, reads the value, applies the operator, stores the result and drops the guard, all in that one call. That is Rust’s order for a number, a bool or a char. For other types, such as a String, Rust calls write before it evaluates the right side. A method call through a guard, such as text.write().push_str("b"), still calls the method twice, once to read and once to store. A let mut value = count.write(); calls it at each use of value. A guard that is only Deref, or whose method takes arguments, gives a copy of the value as a &T.

A method or field an imported type lacks is found through the type’s own Deref, as in Rust. So a newtype over a String has len, and one over another of the crate’s types has that type’s methods and fields. A &mut self method is reached through the type’s DerefMut. A reference to the type is a reference to its target where a function takes one, as a &Name is the &str a function takes. That holds even where nothing else names the type’s deref, as a &Bytes is the &[u8] a function takes. rawr reads the target as it reads a borrow guard’s, so a target without Clone stops the program where it is read. A target that is a slice of numbers or a str is read as a copy, as any &[u8] a method gives is.

An imported type written without its defaulted type arguments takes their defaults. So palette’s Hsl is Hsl<Srgb, f32>. An enum whose type parameters have defaults works the same way. iced’s keyboard::Key is Key<SmolStr>, so Key::Named(Named::Escape) makes one where nothing else fixes its parameter, and a pattern such as KeyPressed { key: Key::Named(Named::Tab), .. } matches the value at the instance it has. A default that rawr cannot name, such as iced’s renderer, still has to be written. A type alias of a builtin type names that type. iced’s markdown::Uri is pub type Uri = String;, so markdown::Uri is a String, through its module or after use.

A Rust function or method that returns a Vec, a slice or a tuple gives a rawr Vec or tuple. An immutable static of a slice or a number reads as its value, as preset::ALL does for pub static ALL: &[Preset] = &[..]. A generic Rust function or method can take a tuple of Rust types, as Freya’s background((35, 35, 35)) does. A Rust function that takes a Vec of crate values, as Choices::new(vec![Family::new(..), ..]), takes the values themselves, moved as Rust moves them, so none is cloned.

A std type in a crate’s signature is rawr’s own type, in every position. A function can take or give a tuple, a &String, a &Vec<T>, a Range<usize>, a &Path or a Box<T>. rawr reads which std type each one is from std’s own table. An Rc<T> or Arc<T> of a crate’s type crosses as the crate’s own pointer. A pointer the crate gives keeps its count and is ptr_eq to the crate’s other pointers to it. One you make with Arc::new becomes the crate’s pointer the first time it crosses, and nothing is copied. A HashMap, HashSet, BTreeMap or BTreeSet keyed by strings, numbers, chars or bools is rawr’s map or set of that kind. The crate’s is made from it where it crosses, because the two keep their entries apart: keys are made anew and crate values move. A &HashMap of crate values lends each value to the call and keeps it after, without a copy. A &[T] of crate values is lent the same way, as one slice. A std type rawr can’t pass to a crate yet, such as an Rc<str> or a map keyed by a crate type, makes the function report “rawr doesn’t run `std::rc::Rc` in a crate’s signature yet” where you call it.

A result can borrow the values a function takes, as fn view<'a>(items: &'a [Item]) -> impl Show + 'a gives one. The values stay borrowed for as long as the result lives, as rustc has it. While it lives, you can read the values, and changing or moving them is rustc’s E0502 or E0505 where you write it. An impl Trait result may run code when it drops, so the values are free again once it drops, at the end of its scope or at drop(result), not at its last use. The values aren’t copied. rawr moves them into one slice beside the result, and they go back to their places in the Vec when it drops. The result’s trait doesn’t have to be one Rust can make a trait object of. You can call a generic method at several types, a method that gives Self, one that gives an associated type the result binds, as impl Stocked<Item = String> does, and a supertrait’s method. A Self such a method gives borrows the same values. They stay borrowed while it lives, even after the first result drops. A crate function that takes the result by value, as fn wrap(shown: impl Show) -> impl Show does, takes it with the values it borrows. They stay borrowed for as long as the function’s result lives, as rustc has it. This works where the result has one trait, each of whose methods takes &self or &mut self and takes and gives plain types: numbers, strings, Options of them and the crate’s own types without type arguments. Where a method doesn’t, as with iced’s Widget, a call that takes such a result by value stops with “rawr doesn’t move a result that borrows its call’s values yet”. A method that takes the result’s own type as an argument, gives it inside another type, or gives a borrow of the result stops with “rawr doesn’t call this method on a result that borrows its call’s values yet”.

A crate type’s impls of std’s traits work as its own traits’ impls do. grid[2] calls its Index, and "1,2".parse::<Coords>() calls its FromStr. A parse() whose target a later annotation names works too.

An associated constant of an imported type reads as a new value each time, as Color::WHITE does in Rust. An imported enum’s own functions are called beside its variants, so torin’s Size::fill() and Size::Fill are both there.

A match, if let or let else can match a variant of an imported enum, as in echo::Event::Connected(connection) => ... The pattern binds the variant’s fields as Rust does. A field of a number, a String or another value your program holds as its own is copied. A crate value field is bound by the binding mode.

  • By value, the pattern moves the field out of the matched value. A field without Clone, as an io::Error, can be passed on to a function that takes it. A guard sees the field by reference, so nothing moves before the arm is chosen.
  • Through &T, or as ref, the pattern borrows the field where it is, a field with Clone too. Methods that take &self and parameters of type &T reach the very field the matched value holds, and the matched value can be read in the arm too. The borrow lives as long as Rust lets it: a function can return it, a match can give it to a let, and a let else keeps it for the statements after. .clone() of it is a value of its own.
  • Through &mut T, or as ref mut, the pattern lends the field mutably. A &mut self method called on the binding changes the matched value itself.

Each field is read on its own. Binding only a Copy field, as in Failed { attempts, .. }, leaves the other fields alone, so a field without Clone beside it is no obstacle. A pattern below a variant, as in Wrapped::Held(Outcome::Opened(door), label), tests its field lent to it and binds from it as the outer pattern would. A match is exhaustive when its arms cover each variant together through the patterns below it, as rustc checks.

Some cases still differ from Rust. A mutable lend lasts until the end of the arm, not until the binding’s last use, so the matched value can’t be used in the arm after its field is lent mutably, and the field can’t leave the arm. Through &mut T, a field of a number or a String is copied, so a change to it through the binding is lost. Below a variant, literal and bool patterns don’t count toward exhaustiveness, so such a match needs a _ arm.

An imported value is dropped with its last owner in your code, as in Rust. A tokio channel closes once its last sender is gone.

Which trait a method call reaches depends on the traits in scope where it is written, as in rustc. When two of a crate’s traits give a type a method of the same name, a block that imports one of them calls that trait’s method, and a block that imports the other calls its own. A glob import brings in every trait its module exports, and a block that imports both gets rustc’s E0034. rawr works this out from the crates’ own trait facts, which it keeps per crate so that only a changed crate is read again. The facts of a crate from a registry or a git commit are kept once per machine in rawr’s home, as its bindings are. When the crate or its dependencies run a build script, they go there only after your toolchain’s build gave those scripts the results the nightly’s did. A later project whose build gives other results stops that run and reads the facts itself next time. Today this covers receivers taken by &self, &mut self or self and arguments of scalar types. A method name that a standard prelude trait also has, such as take, isn’t decided this way yet.

A trait’s default method is a method of each type the trait is implemented for, as Rust has it. Freya’s rect().expanded().center().child("Hello") calls three, through a blanket impl, an empty one and a generic method. Each returns the Rect it took as self.

A blanket impl’s associated functions belong to each type that meets its bounds, as in Rust. palette’s impl<T, U> FromColor<T> for U where U: FromColorUnclamped<T> + Clamp gives Hsl::from_color(rgb) and Rgb::from_color(hsl). Hsl converts from several types, and the argument picks the conversion, as rustc picks it.

An imported struct whose fields are all public is built with a struct literal, as in Rust. A field may borrow a slice of numbers or a &str, as iced’s canvas::LineDash { segments: &[3.0, 6.0], offset: 0 } does. rawr keeps what such a field borrows for as long as the program runs, as Rust keeps a literal. It keeps one copy for each distinct value.

A function that takes a &'static str, as iced’s Font::with_name does, or a type parameter whose trait is implemented for &'static str, as iced::application(..).title("Counter") takes impl Title<State>, takes your string literal as Rust does. rawr keeps it for as long as the program runs, without copying it, once for each distinct text at each call, however often the call runs. Passing a borrow of a local String there is refused with rustc’s E0597, since the local doesn’t live that long.

A type parameter takes what its bound is implemented for, however it is written. fn named<S: Into<String>>(s: S) and fn named(s: impl Into<String>) take the same arguments. AsRef<str>, AsRef<Path>, Into<PathBuf>, AsRef<[u8]> and ToString take a string literal, a String, a borrow of one, a PathBuf or a borrow of one, as std implements them. A literal or a borrow is lent to the call, and a value you pass by value moves, with nothing copied.

Your own function can take a parameter such as impl Into<Length> + Copy, as iced’s layout example does in fn square(size: impl Into<Length> + Copy) -> impl Widget<Message>. The bound holds of each type the crate’s From implementations convert from. A number literal takes the type of the one implementation of its kind, as rustc infers it. So square(50) passes a u32, because Length has From<u32> and no other integer conversion. rawr compiles the function once for each type its callers pass.

One item rawr can’t hold doesn’t stop a use krate::*. rawr leaves that item out, and a call to it says why.

A function or method can return impl Trait of a dependency’s trait, as in Freya’s fn app() -> impl IntoElement. As in rustc, the type it stands for is the type the body returns. It may sit inside an Option, a Result, a Vec, a Box, a tuple, a reference, or a generic type of the crate’s or your own, as iced’s loupe gives Loupe<impl Widget<Message> + 'a>. rawr doesn’t check that the body’s type implements the trait. cargo check reports it. A caller sees the body’s type, so it can call more than the trait’s methods. cargo check reports that as well.

Values that borrow

Some crates give values that borrow what they were made from. pulldown-cmark’s Parser::new(&text) borrows text, and each Event it gives borrows it too. quick-xml’s read_event_into(&mut buf) gives an Event that borrows buf. You write such code as each crate’s docs show it:

src/main.rspulldown-cmark’s events example
// rawr
use pulldown_cmark::{Event, Parser};

fn main() {
    let text = String::from("# Title\n\nSome *emphasis*.\n");
    let mut width = 0;
    for event in Parser::new(&text) {
        if let Event::End(_) = event {
            width -= 2;
        }
        println!("  {:width$}{event:?}", "");
        if let Event::Start(_) = event {
            width += 2;
        }
    }
}
on your machinerawr run Start(Heading { level: H1, id: None, classes: [], attrs: [] }) Text(Borrowed("Title")) End(Heading(H1)) Start(Paragraph) Text(Borrowed("Some ")) Start(Emphasis) Text(Borrowed("emphasis")) End(Emphasis) Text(Borrowed(".")) End(Paragraph)

rawr can’t keep a value that borrows, so a call that makes one opens a scope frame in native code. The frame owns a copy of each &str or &mut Vec the call borrows, and it keeps the value and everything made from it that carries the borrow. The rest of the value’s Rust scope runs inside the frame, and the frame ends where that scope ends:

  • for a let, at the end of its block;
  • for a for loop over the value, at the end of the loop;
  • for any other use, as a match on the value or a method called on it, at the end of the statement.

The frame’s copy is how the value runs. The borrow check still sees the borrow, as rustc does: while the parser is used, changing text is refused with rustc’s E0502.

The frame opens at the start of its statement. So a call or assignment written before the borrowing call in the same statement, as note(&text) in note(&text) + Parser::new(&text).count(), isn’t supported yet, and rawr says so with the statement’s line. Give the earlier call a statement of its own.

break, continue, return, ? and a panic leave the frame as they leave the scope. A value that borrows the frame’s copy can’t outlive it, as in Rust. A value that doesn’t borrow, such as a number, a String or an owned value of the crate, lives on as usual.

A method of a value that borrows can borrow it in turn, as quick-xml’s e.name() borrows the event e. Its frame holds e borrowed until the end of the statement. A &mut T a method gives, such as quick-xml’s reader.config_mut(), is read and stored as a borrow guard is. So reader.config_mut().trim_text(true) changes the reader’s own configuration.

A &mut Vec of numbers that the call fills, as read_event_into(&mut buf) fills buf, gets the call’s changes back when its frame ends. That is where Rust’s borrow of it ends, so the statement after the match, such as buf.clear(), sees them. A let that binds such a value, as in let event = reader.read_event_into(&mut buf)?;, isn’t supported yet. Match on the call in a statement of its own, as quick-xml’s README does.

An imported type that implements Iterator is walked by a for loop, and the iterator methods work on it, as in e.attributes().map(|a| a.unwrap().value).collect::<Vec<_>>(). A Cow<str> a crate gives is a String, and a Cow<[u8]> or a &[u8] is a copy of its bytes, which no longer borrows. A byte string pattern, as in b"tag1" => .., matches a &[u8], as in Rust.

A value in a frame is printed, cloned and matched as any imported value is. It stays in the frame until the frame ends, even after your code drops it.

A value in a frame can be an argument of a native call, as it is in Rust. pulldown-cmark’s README hands its parser to push_html:

src/main.rspulldown-cmark’s README example
// rawr
use pulldown_cmark::{html, Options, Parser};

fn main() {
    let markdown_input = "Hello world, this is a ~~complicated~~ *very simple* example.";
    let mut options = Options::empty();
    options.insert(Options::ENABLE_STRIKETHROUGH);
    let parser = Parser::new_ext(markdown_input, options);

    let mut html_output = String::new();
    html::push_html(&mut html_output, parser);
    print!("{html_output}");
}

push_html takes the parser by value, so the call moves it out of the frame, as Rust moves it. Using parser after the call says it was moved (E0382). The call runs inside the frame, and a value it gives that carries the borrow stays in the frame too.

A &mut String that a native call writes into, as push_html’s first argument is, is your own string, lent in place. So is a &mut Vec of numbers or strings. The first such call turns your value into the native value the crate works on, and your variable keeps that native value. Later calls lend it where it is, so the room one call reserves is still there at the next, as under cargo run. Your own code reads and changes it there too.

Generic items and your own types

A generic Rust function or method can take your own types, as mpsc::channel::<Job>() does with a struct from a marked file, or as iced::run takes your State and Message. rawr builds the item in its runner at a Rust type of its own for each of your types, named as you name it in your crate. So std::any::type_name::<State>() is counter::State, as under cargo run, and each of your types has its own TypeId. That type holds your value by a handle, so native code that lends it to a function of yours, as view(&state) or update(&mut state, message), lends the value itself and copies nothing.

Its Clone, Debug and Default are your type’s own, derived or written by hand, and it is Send and Sync. A T: Clone, T: Debug or T: Default bound is checked on your type, as rustc checks it, so a struct without Clone can’t fill a T: Clone. A bound such as Copy or Hash, or a crate’s own trait your type doesn’t implement, isn’t met, and the runner’s build stops with rustc’s error that names it. Tuples, arrays and options of your types cross as rawr::Value, which carries them as they are. A function that takes &T, as fn shown<T: Visit>(value: &T) does, takes a borrow of your value.

Your type can implement a crate’s trait whose methods are generic, as fn visit<V: Visitor>(&self, visitor: V) -> V::Out is. The crate picks V, so your method’s body reads V as a type it knows only through its bounds. It can call V’s methods and its associated functions, as V::Error::custom("..") or <V::Error as Problem>::custom(".."), and name its associated types, as V::Out. V may sit inside another type, as Option<V> does, and its bound may take the impl’s lifetime, as R: Reader<'a> in impl<'a> Read<'a> for Pair. The runner’s impl is generic as the trait’s method is, so each value of V stays native at its own type for the call, and it needn’t be 'static.

A crate’s re-export of a std item is that item, as in rustc. A derive’s code that writes serde::__private::Formatter, __private::fmt::Result, __private::Some(x) or __private::None names std’s own, in types, calls and patterns. A std type’s method called by its path, as Formatter::write_str(f, ".."), is the method on its first argument.

A crate function that takes a trait object, as fn expecting(expected: &dyn Expected) or fn tally(tally: &mut dyn Tally) does, takes a borrow of any value whose type implements the trait, and rustc coerces it there. The value can be a crate type, a std type the crate implements the trait for, as &"text" is through impl Expected for &str, or one of your types, shared or &mut, whose changes come back to you. Your type implements the trait as it would for a generic function, so its methods run as you wrote them. serde’s de::Error::invalid_length(len, &"struct Task with 2 elements") is one such call. A method of yours that takes a &mut fmt::Formatter, as a crate trait’s method may, writes into the formatter native code passes it. A fmt body can pass its formatter on to a function of yours that takes one, as fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result { describe(f) } does.

A generic method of a type native code fills takes a turbofish, as keys.next_key::<Parity>() or MapAccess::next_key::<Field>(&mut map) does, at one of your types too. A function that takes &'static [&'static str], as serde’s deserialize_struct takes its fields, takes an array of your strings, which rawr keeps for as long as the program runs. A derive’s expansion is in its item’s module, so it names what that module does, and a path through extern crate serde as _serde; names the crate.

A type parameter that none of your values fixes, as iced::run’s Theme, which your view’s widget gives, is rustc’s to infer where the runner calls the item. A parameter impl IntoIterator<Item = X> takes an array of yours as a Vec<X>.

A range of floats, as in 0.5..1.0, is a value that a generic item can take. rand’s rng.random_range(0.5..1.0) is one. Its R: SampleRange<T> bound has an impl for Range<T>, so T is the range’s own float, as rustc infers it. rawr reads that from the crate’s implementations of the bound’s trait. A range of integers or chars is that value too where such an item takes it, so rand::random_range(0..points.len()) gives a usize and rng.random_range('!'..'z') a char. Anywhere else, 0..n is an iterator.

A native cast by TypeId, such as Box<dyn Any>::downcast, between two of your types gives None, as in Rust, and so does one between two instances of a generic type of yours.

A parameter F: Fn(..) -> R, FnMut or FnOnce takes a function of yours, or a closure that captures nothing, as a Rust function item that the runner makes for it. Each of your functions is an item of its own, of a type of its own, and takes no space, as a Rust function item does. It calls your function in the version of your program that is current when native code calls it, so a save shows at the next call. An item may take several of them, as iced::run(Counter::update, Counter::view) does. Your function may take &mut and & of your types, and give a value that borrows what it takes, as a view gives a widget that borrows the state’s strings: those strings are kept for as long as the state is lent, without copying them. A crate’s trait that is implemented for every function of a shape, as iced’s UpdateFn and ViewFn are, takes your function in the same way.

A closure that captures takes the place of F: FnOnce() -> R, as spawn_blocking takes one, or of F: Fn(..) -> R + 'static and F: FnMut(..) -> R + 'static, which native code may call again. The closure runs with an evaluation of its own on whichever thread calls it. An item may take several of them, beside functions of yours, as iced’s Task::sip(sipper, Message::Progressed.with(id), Message::Finished.with(id)) does.

A method of a crate’s trait that a blanket impl gives every Fn(..) works on your function, on a variant’s constructor and on a closure, when the trait is in scope. iced’s impl<F: Fn(A, B) -> O, ..> Function<A, B, O> for F is one. Message::Loaded.with(id) runs iced’s own Function::with, which gives an impl Fn(B) -> O. That value fills a crate’s callable parameter of its shape, as Task::map’s or Task::sip’s, as itself. It must be Send.

A closure also takes the place of F: Fn(..) -> R or F: FnMut(..) -> R with no 'static bound, as image’s ImageBuffer::from_fn(64, 64, |x, y| ..) takes one. Native code can call it only during the call, so it borrows what it captures, as in Rust. A change it makes, as calls += 1, is your local’s own, and you read it after the call.

A parameter that is a function pointer, as f: fn(u32, u8) -> u32, takes a function of yours or a closure that captures nothing, whatever the number of its inputs.

A closure can take and give values of imported types when native code calls it on the thread that runs your program. That is the case when a native call of yours calls it back before it returns, as Freya’s launch calls your app on each frame. On another thread, such a closure stops the program with an error. A function or closure that gives a value of one of your types is the exception. iced’s executor calls |_| Message::Tick(chrono::Local::now()) for Subscription::map on a thread of its own, for example. Such a call runs on the thread that runs your program, where its value is first used, so it can make imported values too.

A parameter impl Into<T> takes a closure, or a function of yours, when T has one From<F> implementation for a callable F. Freya’s WindowConfig::new(app) takes fn app() through impl From<F> for AppComponent, where F: Fn() -> E. Its on_press(|_| ..) takes a closure through impl From<H> for EventHandler<D>, where H: FnMut(D). Freya calls it on each press.

Any other parameter impl Trait is a type parameter that the argument fills, as <T: Trait> is. Freya’s width(impl Into<Size>) takes Size::fill(), and its color(impl Into<Fill>) takes Color::WHITE. For impl Into<T>, rawr reads T’s From implementations. When the argument fits exactly one of them, its number literals take that implementation’s types, as rustc infers them. So background((35, 35, 35)) passes (u8, u8, u8), because Fill converts from no other tuple of three, and padding(12.) passes an f32. Whether the bound holds is rustc’s to check where the runner calls the method.

Where T is another of the item’s type parameters, a number literal is T’s number, through core’s impl From<T> for T. So iced’s slider(1..=100, value, ..).default(50) passes 50 as the slider’s u8. A RangeInclusive<T> of an integer type takes a range of yours, converted to that type with a range check. A range of the crate’s own type, such as iced’s Radians::RANGE, is a value you can read and pass on, so slider(Radians::RANGE, self.angle, Message::AngleChanged) makes a slider of Radians. A closure’s parameter with no type can be such a range. Its T comes from the call’s other arguments, as rustc infers it. In iced’s vectorial_text, |label, range, value, message: fn(f32) -> _| slider(range, value, message) makes T an f32, so a later call passes 2.0..=80.0 as a range of f32.

A crate’s function is a fn pointer wherever one is expected. A cast may leave the pointer’s parts to inference, as iced’s styling does in [("Primary", button::primary as fn(&Theme, _) -> _), ("Secondary", button::secondary)]. The array’s second function then coerces to the same pointer type.

A fn pointer value fills a crate’s impl Fn(..), FnMut or FnOnce parameter of its shape, wherever the pointer comes from: an array’s element, as iced’s styling passes .style(style), a parameter, as vectorial_text’s message: fn(f32) -> _ goes to slider(range, value, message), or a field. It is passed as the closure that calls the pointer. A pointer that takes a &mut isn’t supported there yet.

A crate’s implementation of a std trait for a std type is yours to call, as rustc has it. With iced’s impl From<Degrees> for f32, f32::from(degrees) and let value: f32 = degrees.into() both convert through it. The value can be any expression, such as f32::from(self.rotation.degrees()). When the crate converts the type to several std types, as iced does Degrees to f32 and to f64, the target picks the implementation, as rustc selects it. A target your program leaves open, as in let y = degrees.into(); y * 2.0, where y is some float, is rustc’s E0283. So is one no use fixes. A crate trait of its own with an into method, imported where you call degrees.into(), makes the call rustc’s E0034. Where that trait isn’t imported, rustc calls Into::into, which rawr doesn’t support yet beside such a trait. A conversion the crate doesn’t implement, as u32::from(degrees), is rustc’s E0277.

So is a crate’s operator for a number. With iced’s impl Mul<Radians> for f32, 2.0 * Radians::PI multiplies through it and gives its Output, a Radians, so ferris’s (rotation + step) % (2.0 * Radians::PI) works. The number on the left picks the implementation, beside the type’s own Mul<f32> and Mul, as rustc selects it. A literal such as 2.0 takes the number type that implementation is for. A number with a type the crate implements no such operator for is rustc’s E0277, as rustc reports it. A compound assignment with a number on the left, as value += angle, isn’t supported yet.

A parameter Option<F> of a callable F takes an Option of a function or closure of yours, as iced’s on_toggle_maybe(self.enabled.then_some(Message::Toggled)) does.

A function of the crate, named without a call, fills a callable parameter of its shape, as .style(container::rounded_box) and .style(checkbox::primary) do. The runner passes the Rust function itself, so its inputs, such as the &Theme it reads, never cross into your code.

A crate that lends your function a &mut Vec<String> or a &mut String, through a callback, a slot or a closure, lends you its own storage, as in Rust. Your edits, pushes, assignments and moves reach the crate directly, keeping the vector’s allocation and capacity, and so do writes made before an error or a caught panic. A reference to an element, as &mut v[i] or v.last_mut() gives, reaches that element without copying it, and ends with the callback. You can also call a crate’s function that takes &mut Vec<String>.

A function that gives an opaque impl Trait, as iced’s iced::widget::iced(..) -> impl Widget<..> and iced::application(..) -> Application<impl Program<..>> do, gives a value of a type of its own, at the type arguments its call fixes. So does a trait’s method whose impl Trait the trait’s own default body gives, as iced’s Widget::explain does. You can pass it on, call the trait’s methods on it, as column! calls Widget::_boxed, and call methods of a type that holds it, as .fonts(..) and .run(). Rust code can’t write such a type, so each call that takes the value is compiled in the runner where the call that made it is, and runs from there.

Such a value can borrow, as iced’s layout example gets when it calls self.example.view().explain(color).boxed() on an Element<'_, ..>. The value borrows what the element borrows, and it lives in the scope frame of the values that borrow, as the element does. That works whether or not a public path names the type the method’s body gives. It also works when you call such a method on what another one gave, as in .explain(a).explain(b). Keeping the value past the block of a local it borrows is refused with rustc’s E0597.

The call that makes such a value need not fix all its type arguments. As in rustc, a later use fixes the rest. In column![opaque(slider(..)), widget.map(Message::Pressed)], .map(..) fixes the widget’s message through its callable’s input. column! then boxes each widget into the view’s Element, which fixes the theme and renderer. The value’s type has the traits its impl Trait names and their supertraits, so a value written as impl Framed<..> is a Widget<..> too when Widget is a supertrait of Framed.

Your own impl of a crate’s trait can’t yet be used at a type that holds such a value, as iced’s loupe uses its impl Widget for Loupe<W> at Loupe<impl Widget>. The runner compiles your impl for each type it is used at, and Rust code can’t name an opaque type, so rawr check reports the use.

A call can also take an Option of such a value, as iced’s stack![content, viewer] takes gallery’s viewer: Option<impl Widget<Message>>. It runs at that type even when the option is None and nothing has made a value of the type yet.

A call Trait::method(text, ..) of a crate’s trait, where the crate implements the trait for &str, takes your string as that &str. iced’s column!["Which is your favorite language?", ..] writes Widget::_boxed("..") this way. The call borrows the string as rustc does. A method whose result doesn’t borrow it has it for the call alone. One whose result does, as _boxed gives an Element<'a>, keeps it in the view it is made in, or for as long as the program runs outside a view. A trait implemented only for &'static str keeps it for as long as the program runs, once for each distinct text at each call, and a borrow of a local String there is refused with rustc’s E0597.

A crate trait’s provided method that takes self can also be called on your own type through Trait::method(value, ..). This includes a trait reached through a blanket implementation, as iced’s column![circle, ..] boxes your custom widget. The runner calls the crate’s method on the native representation of your type, using your implementation of its required methods.

A type alias that names a type with each of its own parameters, in order, has the type’s associated functions. iced’s widget::Text<'a, Theme = crate::Theme> names core::widget::Text<'a, Theme>, so the $crate::Text::new(..) that text! writes is core::widget::Text::new.

Such an alias also works when the type it names has no public path of its own in the crate you import. iced’s Element names iced_core’s Element, and canvas::Cache names iced_graphics’s geometry::Cache, and iced re-exports neither. You write the type through the alias, with its defaults, as Rust code does. The runner writes it the same way.

A type that a crate’s signature gives can lack a public path in the crate you import, with no alias for it either. You can still use it, as in Rust. iced’s Widget::map gives iced_core’s widget::Map, which iced re-exports only under its advanced feature. canvas.map(Message::Curve) works without that feature, and you can pass the result on and call its methods. The runner names the type through the crate that defines it.

An alias naming one concrete instance also has that instance’s methods when its type arguments are private. For example, a custom widget can call fill_quad on iced’s Renderer without naming its graphics backends. Generated calls use the public alias, and the native compiler checks the implementation’s bounds.

A type alias of an associated type is the type it names at its defaults. iced’s canvas::Geometry<Renderer = crate::Renderer> is <Renderer as geometry::Renderer>::Geometry, so canvas::Geometry is the geometry of iced’s own renderer. Write it without arguments.

A method whose output is its type parameter’s associated type gives that type at the receiver’s argument. iced’s Cache<Renderer>::draw gives Renderer::Geometry, so cache.draw(renderer, size, |frame| ..) on a canvas::Cache gives a canvas::Geometry. Its closure borrows the &mut Frame that iced lends it. A crate alias reached through its module has its type’s associated functions too, as canvas::Cache::with_group(group) does.

An implementation whose input names an associated type of its parameter, or an associated type of one, takes that type at the parameter’s argument. palette’s Rgb<S, T> converts from Lab<<S::Space as RgbSpace>::WhitePoint, T>. For Srgb, the space is Srgb and its white point is D65, so Rgb::from_color(lab) takes a Lab<D65, f32>, as rustc reads it.

A crate function or method named without a call can go where Option::map or Result::map takes a closure. So message.map(canvas::Action::publish).map(canvas::Action::and_capture) works as in Rust.

A crate type compares with a number when the crate implements PartialOrd<f32> or PartialEq<f32> for it, as iced does for Degrees and Radians. So clock’s rotation < 180.0 works, though iced writes only partial_cmp and < is the standard library’s lt. When the type also compares with itself, the right-hand side picks the impl, as rustc does.

A crate method can give a value whose type names the closure you pass it. iced’s Widget::map(self, f) gives Map<Self, F, Message>, so self.bezier.view(&self.curves).map(Message::AddCurve) gives a widget that holds your closure. The runner holds it as a Box<dyn Fn(Curve) -> Message>, which is the F it writes. rawr check accepts such a program. rawr run doesn’t run it yet.

A slice of your own values fills a type parameter as Rust’s &[T] would, as iced’s pick_list(selected, Language::ALL, Language::to_string) fills L: Borrow<[T]>. The runner passes a Vec of its Rust types for your values, which borrows as the slice does. Those Rust types compare by your type’s PartialEq and print by its Display, derived or written by hand.

A field of an imported type in a struct of yours that derives Default takes the crate’s own Default, as #[derive(Default)] struct Tooltip { position: Position, .. } does with iced’s tooltip::Position. A generic type’s Default works the same way, as a canvas::Cache field does with iced’s impl<Renderer> Default for Cache<Renderer>. Type::default named without a call is a function value, as iced::application(State::default, ..) takes it, whether the struct derives Default or implements it by hand.

When a bound such as W: Widget<Message, Theme, Renderer> leaves a type parameter that only the crate’s impls decide, rawr picks the one impl that fits the type you passed and follows that impl’s own bounds, as rustc does. So a view whose column![..] holds widgets of the crate’s default theme gives that theme to the application that takes it. If no impl fits, or more than one does, the parameter is left for rustc to infer when it builds the runner.

A closure that native code calls with a &T gets a copy of the value when T has Clone. iced’s PaneGrid::new(&state, |pane, value, is_maximized| ..) calls its closure with a &T of each pane’s value.

An async method that borrows its receiver crosses too. Run explains how its future holds the receiver.

An async function whose future borrows its arguments crosses whatever the arguments’ types are, as fount’s google::load(family: &str, catalog: Option<&Catalog>) does. The future holds each borrowed value until it ends: a crate value is lent to it, an Option lends what its Some holds, a tuple lends each member, a Result lends what its variant holds, and a string is your program’s own, with nothing copied. A &Path is your PathBuf itself, lent. A &[u8], &Vec<T>, &String or &u32 is the Rust value made from your array, string or number for the call, as for any call that takes one, and the future holds it. A struct that holds references doesn’t cross yet.

A function borrows an Option<&T> for the call alone, as iced’s combo_box(&self.languages, .., self.selected.as_ref(), ..) takes its selection. T can be your own type or a crate’s. A lifetime a function’s output borrows its inputs at works the same whether it is late-bound or early-bound. The lifetime is late-bound when it is written only in the inputs and the output, and early-bound when a where clause names it too. rustc treats both the same at a call.

A method can give a crate type that borrows a &str from its receiver, as iced’s Key::as_ref(&self) -> Key<&str> does. The value borrows the receiver while it lives, as rustc’s does. A match reads it at that type, so Key::Character("r") matches the character the key holds. A generic enum’s variants match at the types its value has.

A method whose input is an associated type its impl sets crosses at that type, as palette’s shift_hue(self, amount: Self::Scalar) takes an f32 for an Hsl of f32. So does one that a blanket impl sets through another trait’s associated type. palette’s impl<T: Lighten> Darken for T sets type Scalar = T::Scalar, so hsl.darken(0.075) takes the f32 that Hsl’s own Lighten impl sets, as rustc normalizes it.

Known gaps

  • A program that rawr-import runs exits with status 1 when it fails, a panic included. Rust would exit with 101.
  • A program with a marked main picks up a body edit when native code next calls back into it, as Freya does at its next event. A native main picks up a body edit at its next call. Reload says more.
  • A guarded value without Clone, or an imported type’s Deref target without one, stops the program where it is read. A guard of a Vec or a tuple can be read but not changed yet. A method that gives an Option of a reference works, as iced’s pane_grid::State::get_mut does, and a change made through it stays. A guard inside a Result, as Mutex::lock gives, isn’t supported yet.
  • A method that is generic over a sealed trait, such as itoa::Buffer::format, can’t be called yet.
  • A while let whose subject borrows a &mut buffer its call fills isn’t supported yet. Match on the call in the loop’s body, as quick-xml’s README does.
  • A value that borrows can’t be stored in a struct of yours, kept in a collection past its frame, or held across an .await.
  • A value in a frame can be an argument by value, not by reference yet. A call can’t take values from two frames yet.
