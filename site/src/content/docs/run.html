Run

How rawr run splits a crate between interpreted and native code, and how the two share one program.

What rawr runs

rawr run takes a Cargo crate or a single .rs file. Without a path, rawr looks in the current directory and its parents for a crate.

In a Cargo workspace, -p names a package, as under cargo run:

rawr run -p invaders

rawr check -p takes a package name too.

rawr finds a package’s targets as Cargo lists them, from cargo metadata. A binary may be src/main.rs, a file under src/bin/ or a [[bin]] entry. In a package with several binaries, --bin names the one to run, as under cargo run --bin. Without --bin, the package’s default-run picks one:

rawr run --bin async1

A .rs file that the package lists as a binary runs as that binary. So rawr run exercises/async1.rs in rustlings’ package gets the package’s dependencies and profile, as cargo run --bin async1 does. A file that no package lists runs on its own.

A program gets the dependencies Cargo links for the host. A [target.'cfg(..)'.dependencies] table joins when Cargo’s build includes it on this machine. rawr asks Cargo’s unit graph, so it never evaluates a cfg itself.

The program runs with its package’s profile. Under panic = "abort", a panic aborts the program, as it aborts the binary Cargo builds. A shell sees status 134, SIGABRT’s.

Without Cargo installed, rawr runs only src/main.rs or src/lib.rs, and only what needs no build.

Arguments and stdin

Arguments after -- go to the program, as under cargo run:

rawr run examples/grep -- -n pie menu.txt

std::env::args() gives the program’s name first. The name is the path cargo run would run, the binary’s name under target/debug/. For a workspace member, that is the workspace’s target/. For a single file, it is the file’s path without .rs.

The program reads the stdin of rawr run, a terminal or a pipe:

cat menu.txt | rawr run examples/grep -- pie

At a terminal the running program gets the keyboard, so Ctrl-C reaches it as it reaches a program cargo run started. Ctrl-C ends rawr run too.

At a terminal the program also writes to the terminal itself, as under cargo run. rawr saves the terminal’s settings before the program starts. After the program ends, rawr puts them back if the program changed them, even when a restart killed it. While the program holds the terminal raw, rawr’s own lines wait until then. Apps and libraries says more.

The examples/grep crate in rawr’s repository is a small grep with flags, files and stdin. cargo build --release builds the same crate, and its binary prints the same lines.

rawr’s examples are packages of its Cargo workspace, as iced’s are. From the repository’s root, rawr run -p grep runs one under rawr. cargo run -p grep runs it natively.

The // rawr marker

A file whose first line is // rawr is interpreted. Every other file is native Rust.

The marker is the first line of the file’s Rust. A shebang line and a cargo-script frontmatter block may come before it:

#!/usr/bin/env -S cargo +nightly -Zscript
---cargo
[package]
edition = "2024"
---
// rawr
fn main() {
    println!("hello");
}

The marker must be the line right after the frontmatter. A blank line between them leaves the file unmarked. A file whose frontmatter cargo rejects isn’t marked, and rawr run reports cargo’s error.

  • The crate root may be marked or native. A crate with a native root runs when a module it declares is marked. If no file is marked, rawr run stops with RAWR-ENVIRONMENT-MISSING-SOURCE.
  • In a package with both src/main.rs and src/lib.rs, the marker may go in either crate’s tree. A library and a thin main says how rawr runs a marked module of the library.
  • Marked code may call native modules.
  • Native code may call marked code, whether the crate root is native or marked. A native module below a marked root names the root’s items as a Rust module names its parent’s, public or not. The calls go through the same trampolines as a native main’s, so a save of the marked code reaches the next call.
  • A path dependency is compiled natively, even if its files start with // rawr. Only the crate you run is interpreted.

Inner attributes go after the marker, as comments may come before them in Rust:

// rawr
#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]

fn main() {}
  • The lint attributes allow, warn, deny, forbid and expect are accepted. rawr ignores them.
  • Build settings and documentation are accepted and ignored. These are windows_subsystem, crate_name, crate_type, recursion_limit, type_length_limit, no_builtins, debugger_visualizer and doc. //! comments are accepted too.
  • #![cfg_attr(predicate, ..)] applies its attributes when the predicate holds. rawr builds as a debug build, so debug_assertions holds. A feature holds when Cargo enables it, as Features says. test holds under rawr test only. The attributes it applies follow the same rules.
  • Attributes that change the prelude or the language are errors. These include no_std, no_implicit_prelude, no_main and feature.

cargo build reads every one of these attributes as Rust does.

Features

A marked crate’s cfg(feature = "…") holds for the features Cargo enables for it. rawr asks Cargo which ones those are, from Cargo’s unit graph. That covers cfg!, #[cfg] on items and statements, and #[cfg_attr]. With no flags, those are your default features and what they enable, as under cargo run.

rawr run, rawr check and rawr test take Cargo’s feature flags: --features <list> (or -F), --no-default-features and --all-features. rawr hands them to Cargo as they are written, and the background cargo check gets them too.

A crate with Rust dependencies runs its marked code in rawr-import’s runner. The runner gets the same features, and its native modules build with them, so the crate prints what cargo run prints under each flag.

rawr run --no-default-features --features fast

In a browser

rawr run --web runs a crate in a browser. The crate uses crates from its Cargo.toml that draw into a page, such as iced on its web shell, or ratatui through ratzilla’s DOM backend. A cargo script with dependencies in its frontmatter runs there too, as rawr run --web script.rs. So does a program with no dependencies, such as one marked .rs file. Its output shows on the page:

rawr run --web
rawr: the program runs at http://127.0.0.1:7878/

rawr builds the crate’s dependencies, their bindings and its runner for wasm32-unknown-unknown, as cargo build --target wasm32-unknown-unknown would. The build goes in target/rawr/web, apart from the native build. A script’s goes in the build directory every script shares. A program with no dependencies runs on one runner of rawr and the standard library, which rawr builds once per rawr version in its home and every such program shares. So the first such program waits for that build and later ones don’t. The toolchain needs that target, so run rustup target add wasm32-unknown-unknown once. Then wasm-bindgen packs the runner with the page. rawr uses the wasm-bindgen on your PATH when its version is the one the runner links. Otherwise it installs that version once in rawr’s home.

The page runs the crate’s marked files against the runner. When you save, rawr sends the new text to the page. The running program takes it in place and keeps its state, as rawr run does. A compile error shows over the program and in the terminal, and the program keeps running its last good code. The error names the crate’s files from the directory you ran rawr in, as rawr run names them. What the program prints shows in the terminal and in the browser’s console. It shows on the page as well, while nothing else draws there. A save that calls an API of a crate the runner doesn’t cover yet builds the runner again. The page says so over the program, which keeps running its last code meanwhile. Then the page restarts on the new runner, so the program’s state starts over.

A browser tab has one thread. So a program there hands its loop to the page and never blocks on its input. A closure that native code calls on each animation frame, as ratzilla’s draw_web takes, runs the edited code from the next frame on. An async loop awaits its input through wasm_bindgen_futures::spawn_local. An edit to the async function the program waits in can’t resume it there. The page then starts the program again in a fresh instance, and the page and the terminal both say why. An edit anywhere else keeps the program’s state. --port <port> picks the port, and --out <dir> writes the page’s files to dir for any static server.

Scripts

A .rs file with a frontmatter block is a cargo script wherever it sits. rawr runs it as a file of its own, as cargo does. Inside a Cargo package it still doesn’t use the package’s Cargo.toml.

A script may declare dependencies in its frontmatter, as under cargo -Zscript. rawr-import runs it the way it runs a crate with dependencies, and the script prints what it prints under cargo.

#!/usr/bin/env -S cargo +nightly -Zscript
---cargo
[dependencies]
itoa = "1"
---
// rawr
fn main() {
    let mut buffer = itoa::Buffer::new();
    println!("{}", buffer.format(128u64));
}

rawr expands the frontmatter as cargo does. The package takes its name from the file, and its edition is 2024 unless the frontmatter names one. Relative paths in it are the script’s directory’s. Cargo refuses some tables in a script’s manifest, such as [workspace], [lib] and [build-dependencies], and rawr refuses them with cargo’s message.

Nothing is written beside the script. rawr keeps each script’s manifest and lockfile in scripts/<name>-<digest> in rawr’s home, which is ~/.cargo/rawr unless RAWR_HOME says otherwise. The digest is of the script’s path, so a script keeps its lockfile from run to run. A new dependency is locked when the frontmatter changes, and the dependencies already locked stay as they are.

Your own cargo builds every script in one build directory, scripts/build. A crate that one script compiled is reused by the next script that needs it. rawr’s own crates are compiled once per toolchain for every script and project, as Imports explains. So a script starts in seconds once its dependencies are compiled.

A native main

A crate’s main can stay native while you mark only the module you are working on. Here main.rs is native Rust. It declares the marked module ticker:

src/main.rs
mod ticker;

fn main() {
    for tick in 0.. {
        println!("{}", ticker::line(tick));
        std::thread::sleep(std::time::Duration::from_millis(500));
    }
}
src/ticker.rs
// rawr
pub fn line(tick: u64) -> String {
    format!("tick {tick}")
}

rawr run compiles main.rs with Cargo and interprets ticker.rs. Each call that native code makes to ticker::line runs the marked function in the interpreter.

Change the text in format! and save. The running program takes the save at its next call into marked code. The next line shows the new text. tick counts on from where it was. A save that changes something native code uses restarts the program instead, as What a save does lists.

cargo run and cargo build --release compile both files natively, since the marker is only a comment. How it works describes how rawr builds the native side.

Each side names the other’s items by the rules Rust applies between modules. So a marked module can call a private function of the native root, as a child module can in Rust. Any file of the crate’s module tree may be marked. That includes a file below native modules. Native boundary gives the rules.

Which thread runs marked code

The native main runs on the process’s main thread, as under cargo run. A call it makes into a marked module runs on that thread. The interpreter runs there too. A call from another thread runs on that thread. So an app whose event loop must own the main thread, such as one built on winit, runs under rawr run. That holds whether native code or a marked function starts the loop. A marked crate root’s main runs on the main thread as well, so it can start a winit loop itself, as Freya’s launch does. A marked function that native code calls and that runs for the whole program takes saves while it runs. A run() that starts iced is one. The program’s next callback, such as iced’s next update or view, runs the new code, as for a running marked main.

Example crates

These crates in rawr’s repository have a native main. Run each one from the repository’s root:

  • rawr run -p islands runs a loop that bounces a ball. Its marked physics.rs moves and draws the ball.
  • rawr run -p invaders runs a space-invaders game on winit and softbuffer. Each frame calls its four marked modules once to move the game on and once more for the picture.
  • rawr run -p tui runs a to-do list on ratatui. A save to its marked app.rs or ui.rs repaints the screen without waiting for a key.

cargo run -p with the same name runs each crate natively.

A library and a thin main

Many apps keep their code in the library and have a short main.rs that calls it:

fn main() {
    let mut game = arcade::score::Game::new();
    game.play(3);
    println!("{}", arcade::report::line(&game));
}

Mark a module of the library, such as src/score.rs, and rawr run runs the package from its library. The library root stays native. The marker goes in the modules it declares. The binary and its own modules stay native too. The binary’s main is the program’s main. It reaches the marked module through the library, as cargo build builds it. So arcade::score::Game::new() calls the marked function through its trampoline. The library’s native modules call it the same way.

The binary is the one cargo run runs. It may be src/main.rs, a file under src/bin/ or a [[bin]] entry. Its own modules sit beside it, as Cargo finds them.

When both the binary’s tree and the library’s have marked modules, rawr run stops with an error that names both trees. Remove the marker from one of them.

An iced app can sit in the library the same way. A marked app.rs whose pub fn run() -> iced::Result calls iced::run(..) runs from a main.rs that is only fn main() -> iced::Result { mycrate::app::run() }. It opens its window. A save to app.rs shows at iced’s next update or view. main gets back iced’s own iced::Result.

Limits today

  • A marked module can’t reach a private field of a struct in the native root yet.
  • A function whose values can’t cross yet panics when native code calls it. The message names the function.
  • A public marked function that returns impl Trait or is async stops rawr run with an error that names it.
  • A private marked function that returns impl Trait or is async has no trampoline. A native module below that calls it gets rustc’s error for a missing item.
  • A marked type can’t become the object of another crate’s trait yet. It can’t become the object of a native trait with type or lifetime parameters either.
  • A marked value can’t be lent as a &mut dyn of a native trait yet.
  • On a native trait’s object, marked code can’t call a method that takes &mut self yet. The same holds for a method that is generic over a type or names Self past its receiver.
  • Native code can’t call a marked type’s written Hash through a native trait’s object yet. A derived Hash works.
  • A native trait object’s method whose reference result rawr can’t give yet is an error at rawr check. A &[Row] of a field is one such result.
  • A static mut isn’t supported yet.
  • A cycle of statics isn’t supported yet when its type keeps the pointer inside an enum or a union, as an Option<&'static Callsite> field does. A cycle whose type is generic over a type isn’t supported yet either. rawr check says so.
  • A marked src/lib.rs beside a native src/main.rs doesn’t run yet. rawr run stops with an error that says to mark the modules it declares instead.

A running marked main

A marked main often hands control to a native loop: a framework’s event loop, a game loop or a timer. That loop calls your marked functions and closures back. A save reaches the program at the loop’s next such call, and the program keeps running.

  • The next call runs the new code. Everything that call runs uses the same version of your code.
  • The framework keeps its state: its window, its widgets and the values it holds for you.
  • The new code compiles beside the running program, so the loop doesn’t stall while it compiles.
  • A save of several files arrives whole.
  • A save that doesn’t compile prints its error, and the program keeps running.

A body edit compiles inside the running program, against the native code it was built with, and nothing else is prepared again. On rawr’s reload benchmark, a save reaches the next callback in about 80 ms with 0.3.25, against about 1.3 s before. The same process keeps running, with its state. Most of the 80 ms is the watcher waiting for the save to settle and the program’s own next tick. A new native call or a changed Cargo.toml still prepares the whole project, as the list below says. A save that prepares again says why in one line:

rawr: preparing again: `Cargo.toml` changed

A closure that native code holds runs its new body when the function that writes it has the same closures as before, with the same captures. Otherwise it runs its old body until the framework asks for it again. A function passed by name always runs its new body when its signature is the same.

Some saves restart the program with one line that says why:

  • a struct or enum with new fields or variants whose live values can’t take them, as a field change lists;
  • an edit to main itself, closures written in it included, since main runs only once;
  • a changed function that main gave native code, since main doesn’t run again to give a new one;
  • a program whose native code never called back into marked code;
  • an edit to an async function a future is suspended in, since its frame can’t resume in the new body;
  • a new native call, or an edit to Cargo.toml or a native file;
  • a panic after a save, such as a framework’s check that its hooks keep their order.
rawr: `Scale` changed its fields; restarting the program

A restart that needs a new native build builds it while the program keeps running. The old program ends just before the new one starts, so the terminal, a port or a lock it held is free for the new one. A build that fails leaves the old program running and prints the error. A program that ends with status 0 during the build ends the run. Nothing of the old program’s state carries over to the new one.

When the edit shows

A loop that runs every frame shows the edit at its next frame. A game loop and a ratatui loop are such loops.

A framework that redraws only what changed shows the edit at its next event. Freya is such a framework: it calls a component again only when its state changes, so an edit shows when you next click or type. Showing an edit at once would need the framework to rerun every component and keep its state, and Freya has no call that does both. Its own reload resets every use_state.

An async main

A marked crate root may have an async fn main under its runtime’s attribute, such as #[tokio::main]. The runtime is the one in your Cargo.toml, built by Cargo as cargo run builds it. rawr adds none and favors none.

Cargo.toml
[dependencies]
tokio = { version = "1", features = ["macros", "rt-multi-thread", "time", "sync"] }
src/main.rs
// rawr
use std::time::Duration;
use tokio::sync::mpsc;

#[derive(Debug, Clone)]
struct Job {
    id: u32,
}

#[tokio::main]
async fn main() {
    let (sender, mut receiver) = mpsc::channel::<Job>(1);
    let producer = async move {
        for id in 1..=3 {
            tokio::time::sleep(Duration::from_millis(100)).await;
            sender.send(Job { id }).await.unwrap();
        }
    };
    let consumer = async move {
        while let Some(job) = receiver.recv().await {
            println!("{job:?}");
        }
    };
    tokio::join!(producer, consumer);
    let sum = tokio::task::spawn_blocking(|| (1..=100).sum::<u32>()).await.unwrap();
    println!("sum {sum}");
}
on your machinerawr runJob { id: 1 } Job { id: 2 } Job { id: 3 } sum 5050

Each job prints 100 ms after the last one, on tokio’s own clock.

Under rawr run, rawr’s copy of your crate in target/rawr/crate holds a native main with your attribute copied as written, arguments and all. That main awaits the future of your marked main. Your crate never depends on rawr, and cargo build --release builds it as it is.

How it runs:

  • An async block or an async fn gives a Rust future that any runtime can poll.
  • Your code runs on one thread, the one that holds the program. That thread also runs your runtime’s main, so tokio::spawn, spawn_blocking and sleep start when you call them, as in Rust. A future polled on another thread hands each step of your code to that thread, which runs it the next time main is polled. A runtime’s own futures, such as tokio’s sleep, run on whichever thread polls them.
  • tokio::spawn takes a future of yours, and its handle’s .await gives the future’s value. A spawned future runs though nobody awaits it.
  • A function that takes impl Future<Output = T>, such as iced’s Task::future, takes your future’s output as its T. So in Task::future(async move { fount::system::load(&font).await }).then(|bytes| match bytes { .. }), bytes is the Result that load gives, as rustc reads it. The value becomes native on the thread that holds the program, where your imported values live.
  • A native value whose type is a future goes there too, whatever bound makes it one. iced’s gallery passes its image.download(Size::Original), an impl Straw<Bytes, Blurhash, Error> that sipper’s Core makes a future, to Task::future, whose T is then Result<Bytes, Error>, as rustc reads it.
  • A generic item called at one of your types, such as mpsc::channel::<Job>(), carries your values as they are. A value that comes back is checked against the type you named. Imports says more.
  • An async method that borrows its receiver, such as Sender::send or Receiver::recv, keeps it until its future ends. A Clone receiver is copied for &self. A &mut self receiver is lent, and using it before the future ends is a borrow error.
  • Your own async fn holds each & and &mut parameter, its &mut self too, until its future ends, as in Rust. A change it makes after an .await is the caller’s place’s own, whether the parameter is a Vec, one of your structs or a crate’s value such as a connection. Using the place before the future ends is rustc’s borrow error.
  • A native value drops with its last owner, so a channel closes when its last sender goes.
  • spawn_blocking runs your closure on a worker thread, with an evaluation of its own.
  • A save keeps the program running. The new code takes over the next time one of your futures resumes, such as a timer loop at its next tick or a spawned task at its next step, and your futures keep their locals. A save that changes main, or the body of an async function or block a future is waiting in, restarts the program, and rawr says why in one line.

Limits today:

  • join! and select! work. try_join! doesn’t yet.
  • On tokio’s multi-thread runtime, a step of a spawned future runs inside main’s task. So your code there sees main’s tokio::task::id() and task-locals, and a tracing span that instruments the spawned future isn’t entered. On the current_thread runtime it sees the spawned task’s.
  • An iced app has no runtime main. There, a runtime’s future is made when it is first polled, so a sleep starts its timer at the await. A call that needs a runtime the app doesn’t run fails with an error that says to give async fn main the runtime’s attribute.
  • A closure that spawn_blocking runs can’t use values of imported types.
  • A generic item whose bound picks behaviour by type alone, such as Default or Deserialize, can’t take one of your types. rawr says which bound when it builds the runner.
  • A main that is async needs a runtime’s attribute, as Rust does. Without one it is rustc’s E0752.

A program with no dependencies, such as a lone .rs file, can use async fn, async blocks and .await too. They check as rustc checks them, and calling an async fn makes its future, as in Rust. Running a future needs a runtime crate, so #[tokio::main] or tokio::join! there is rustc’s E0433, since no tokio crate is linked.

Checking

rawr check checks a program without running it. Then it runs cargo check, because rawr’s check accepts some code that rustc rejects. The Overview lists those cases.

rawr run runs cargo check beside the program. When rawr run ends with the program, cargo’s errors are printed after it.

A script is checked too, with your own cargo. rustc refuses a frontmatter block outside cargo -Zscript, so rawr checks a copy of the script with the block blanked, in the script’s directory in rawr’s home. rustc’s errors name the script and its own lines.

rawr runs a program itself or hands it to an installed extension.

Reload

rawr run watches every program it runs.

  • An iced app picks up a save at its next message, and keeps running. Apps and libraries says what it keeps.
  • A native main picks up a body edit at its next call into the marked file, and keeps running.
  • A marked main in a native loop picks up a body edit at the loop’s next call into marked code, and keeps running.
  • Any other running program restarts when you save, with the same arguments. One line on stderr says so:
rawr: the source changed; restarting the program

A save that doesn’t compile prints its error, and the program keeps running.

A restarted program reads stdin on from where the old one stopped. Input the old program had already read doesn’t come back.

When the program ends and stdin is a terminal, rawr run waits. The next save runs the program again, with the same arguments. Ctrl-C ends the wait. When stdin isn’t a terminal, rawr run ends with the program and gives its exit status.

With rawr-import, a crate whose native code didn’t change reuses its earlier build.

The menu bar

A window program that rawr run runs on macOS gets a rawr menu in the menu bar. The menu comes after the program’s own menus. It never replaces them.

ItemWhat it does

The program keeps its own name. The menu bar, the Dock and the program’s own app menu show its binary’s name, as under cargo run. The program’s window keeps the title the program gives it.

Under cargo run the program has no rawr menu. Other systems have no rawr menu yet.

Release builds

An app that embeds the rawr crate to run scripts does ship the interpreter. Embedding covers that case.

Speed

Calls into native code run at native speed. Keep a hot loop in a native module or a crate, and Cargo compiles it.
