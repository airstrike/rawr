Run

How rawr run splits a crate between interpreted and native code, and how the two share one program.

What rawr runs

rawr run takes a Cargo crate or a single .rs file. Without a path, rawr looks in the current directory and its parents for a crate.

In a Cargo workspace, -p names a package, as under cargo run:

rawr run -p invaders

rawr check -p takes a package name too.

Arguments and stdin

Arguments after -- go to the program, as under cargo run:

rawr run examples/grep -- -n pie menu.txt

std::env::args() gives the program’s name first. The name is the path cargo run would run, the binary’s name under target/debug/. For a workspace member, that is the workspace’s target/. For a single file, it is the file’s path without .rs.

The program reads the stdin of rawr run, a terminal or a pipe:

cat menu.txt | rawr run examples/grep -- pie

At a terminal the running program gets the keyboard, so Ctrl-C reaches it as it reaches a program cargo run started. Ctrl-C ends rawr run too.

At a terminal the program also writes to the terminal itself, as under cargo run. rawr saves the terminal’s settings before the program starts. After the program ends, rawr puts them back if the program changed them, even when a restart killed it. While the program holds the terminal raw, rawr’s own lines wait until then. ratatui says more.

The examples/grep crate in rawr’s repository is a small grep with flags, files and stdin. cargo build --release builds the same crate, and its binary prints the same lines.

rawr’s examples are packages of its Cargo workspace, as iced’s are. From the repository’s root, rawr run -p grep runs one under rawr. cargo run -p grep runs it natively.

The // rawr marker

A file whose first line is // rawr is interpreted. Every other file is native Rust.

The marker is the first line of the file’s Rust. A shebang line and a cargo-script frontmatter block may come before it:

#!/usr/bin/env -S cargo +nightly -Zscript
---cargo
[package]
edition = "2024"
---
// rawr
fn main() {
    println!("hello");
}

The marker must be the line right after the frontmatter. A blank line between them leaves the file unmarked. A file whose frontmatter cargo rejects isn’t marked, and rawr run reports cargo’s error.

  • The crate root may be marked or native. A crate with a native root runs when a module it declares is marked. If no file is marked, rawr run stops with RAWR-ENVIRONMENT-MISSING-SOURCE.
  • Marked code may call native modules.
  • Native code may call marked modules when the crate root is native.
  • With a marked root, native code can’t use code from marked files yet. rawr reports an error if it does.
  • A path dependency is compiled natively, even if its files start with // rawr. Only the crate you run is interpreted.

Scripts

A .rs file with a frontmatter block is a cargo script wherever it sits. rawr runs it as a file of its own, as cargo does. Inside a Cargo package it still doesn’t use the package’s Cargo.toml.

A script may declare dependencies in its frontmatter, as under cargo -Zscript. rawr-import runs it the way it runs a crate with dependencies, and the script prints what it prints under cargo.

#!/usr/bin/env -S cargo +nightly -Zscript
---cargo
[dependencies]
itoa = "1"
---
// rawr
fn main() {
    let mut buffer = itoa::Buffer::new();
    println!("{}", buffer.format(128u64));
}

rawr expands the frontmatter as cargo does. The package takes its name from the file, and its edition is 2024 unless the frontmatter names one. Relative paths in it are the script’s directory’s. Cargo refuses some tables in a script’s manifest, such as [workspace], [lib] and [build-dependencies], and rawr refuses them with cargo’s message.

Nothing is written beside the script. rawr keeps each script’s manifest and lockfile in scripts/<name>-<digest> in rawr’s home, which is ~/.cargo/rawr unless RAWR_HOME says otherwise. The digest is of the script’s path, so a script keeps its lockfile from run to run. A new dependency is locked when the frontmatter changes, and the dependencies already locked stay as they are.

Your own cargo builds every script in one build directory, scripts/build. A crate that one script compiled is reused by the next script that needs it. rawr’s own crates are compiled once per toolchain for every script and project, as Imports explains. So a script starts in seconds once its dependencies are compiled.

A native main

An app can keep its main native and mark only the module you are working on. Under rawr run, each function of that module that native code can call gets a generated stub with the same signature. The stub runs the function in the interpreter.

The stubs live in rawr’s own copy of the crate, under target/rawr/crate. For a workspace member, the copy is under target/rawr/members/<path>/crate in the workspace’s target/. Your crate never depends on rawr.

Native code sees the public items of a marked module: its functions, methods, structs, enums, constants and type aliases. Private items stay in the interpreter.

Numbers, bool, char, String and &str cross between native code and a marked module. Vec and Option of them cross too. So do the structs and enums of marked modules whose fields cross.

A parameter may be one of those values or a reference to one. A &mut argument comes back with the changes the function made.

A reference to another crate’s value, such as ratatui’s &mut Frame, is lent to the function for the call instead. Its methods reach the native value itself, and the borrow ends when the call returns, as in Rust. The ratatui page shows one.

A function whose values can’t cross yet panics when native code calls it, and the message names the function. A public function that returns impl Trait stops rawr run with an error that names it.

A save of a marked file reaches the running program at its next call into that file. An edit to a function body or to a private item swaps in place, and the program keeps its state. An edit that changes what native code sees needs a new native build. That covers a signature, a struct’s fields and a public constant. rawr then restarts the program and prints why:

rawr: `physics::Ball` changed its fields; restarting the program

An edit to a native file restarts the program too.

The examples/islands crate in rawr’s repository is such an app.

The native main runs on the process’s main thread, as under cargo run. The interpreter runs on a thread of its own. So an app whose event loop must own the main thread, such as one built on winit, runs under rawr run.

The examples/invaders crate is a space-invaders game on winit and softbuffer. Its native main.rs owns the window, the keys and a pixel framebuffer. Four marked modules hold the game: its rules, the invaders’ march, the hits and what each frame draws. Each frame calls them once to move the game on and once more for the picture.

rawr run -p invaders

cargo run -p invaders plays the same game natively.

A save that changes a colour, a speed or a sprite’s shape shows at the next frame. The game keeps its score and its invaders. A new field on the game’s state restarts the game.

The examples/tui crate is a to-do list on ratatui. Its native main.rs owns the terminal, and its marked app.rs says what the keys do and what the screen shows. A save repaints the screen at once, with no key pressed. ratatui covers terminal apps.

Limits today:

  • A native module other than the root can’t declare a marked module.
  • Marked code can’t call items written in the native root itself.

A marked main runs on the process’s main thread too, with the interpreter. So a marked crate root can start a winit event loop itself, as Freya’s launch does. A save reaches such a program while it runs, as a running marked main says.

A running marked main

A marked main often hands control to a native loop: a framework’s event loop, a game loop or a timer. That loop calls your marked functions and closures back. A save reaches the program at the loop’s next such call, and the program keeps running.

  • The next call runs the new code. Everything that call runs uses the same version of your code.
  • The framework keeps its state: its window, its widgets and the values it holds for you.
  • The new code compiles beside the running program, so the loop doesn’t stall while it compiles.
  • A save of several files arrives whole.
  • A save that doesn’t compile prints its error, and the program keeps running.

A closure that native code holds runs its new body when the function that writes it has the same closures as before, with the same captures. Otherwise it runs its old body until the framework asks for it again. A function passed by name always runs its new body when its signature is the same.

Some saves restart the program with one line that says why:

  • a struct or enum with new fields or variants, since native code may hold a value of the old shape;
  • an edit to main itself, closures written in it included, since main runs only once;
  • a changed function that main gave native code, since main doesn’t run again to give a new one;
  • a program whose native code never called back into marked code;
  • a new native call, or an edit to Cargo.toml or a native file;
  • a panic after a save, such as a framework’s check that its hooks keep their order.
rawr: `Scale` changed its fields; restarting the program

When the edit shows

A loop that runs every frame shows the edit at its next frame. A game loop and a ratatui loop are such loops.

A framework that redraws only what changed shows the edit at its next event. Freya is such a framework: it calls a component again only when its state changes, so an edit shows when you next click or type. Showing an edit at once would need the framework to rerun every component and keep its state, and Freya has no call that does both. Its own reload resets every use_state.

An async main

A marked crate root may have an async fn main under its runtime’s attribute, such as #[tokio::main]. The runtime is the one in your Cargo.toml, built by Cargo as cargo run builds it. rawr adds none and favors none.

Cargo.toml
[dependencies]
tokio = { version = "1", features = ["macros", "rt-multi-thread", "time", "sync"] }
src/main.rs
// rawr
use std::time::Duration;
use tokio::sync::mpsc;

#[derive(Debug, Clone)]
struct Job {
    id: u32,
}

#[tokio::main]
async fn main() {
    let (sender, mut receiver) = mpsc::channel::<Job>(1);
    let producer = async move {
        for id in 1..=3 {
            tokio::time::sleep(Duration::from_millis(100)).await;
            sender.send(Job { id }).await.unwrap();
        }
    };
    let consumer = async move {
        while let Some(job) = receiver.recv().await {
            println!("{job:?}");
        }
    };
    tokio::join!(producer, consumer);
    let sum = tokio::task::spawn_blocking(|| (1..=100).sum::<u32>()).await.unwrap();
    println!("sum {sum}");
}
on your machinerawr runJob { id: 1 } Job { id: 2 } Job { id: 3 } sum 5050

Each job prints 100 ms after the last one, on tokio’s own clock.

Under rawr run, rawr’s copy of your crate in target/rawr/crate holds a native main with your attribute copied as written, arguments and all. That main awaits the future of your marked main. Your crate never depends on rawr, and cargo build --release builds it as it is.

How it runs:

  • An async block or an async fn gives a Rust future that any runtime can poll.
  • Your code runs on one thread, the one that holds the program. That thread also runs your runtime’s main, so tokio::spawn, spawn_blocking and sleep start when you call them, as in Rust. A future polled on another thread hands each step of your code to that thread, which runs it the next time main is polled. A runtime’s own futures, such as tokio’s sleep, run on whichever thread polls them.
  • tokio::spawn takes a future of yours, and its handle’s .await gives the future’s value. A spawned future runs though nobody awaits it.
  • A generic item called at one of your types, such as mpsc::channel::<Job>(), carries your values as they are. A value that comes back is checked against the type you named. Imports says more.
  • An async method that borrows its receiver, such as Sender::send or Receiver::recv, keeps it until its future ends. A Clone receiver is copied for &self. A &mut self receiver is lent, and using it before the future ends is a borrow error.
  • A native value drops with its last owner, so a channel closes when its last sender goes.
  • spawn_blocking runs your closure on a worker thread, with an evaluation of its own.

Limits today:

  • join! works. try_join! and select! don’t yet.
  • On tokio’s multi-thread runtime, a step of a spawned future runs inside main’s task. So your code there sees main’s tokio::task::id() and task-locals, and a tracing span that instruments the spawned future isn’t entered. On the current_thread runtime it sees the spawned task’s.
  • An iced app has no runtime main. There, a runtime’s future is made when it is first polled, so a sleep starts its timer at the await. A call that needs a runtime the app doesn’t run fails with an error that says to give async fn main the runtime’s attribute.
  • A closure that spawn_blocking runs can’t use values of imported types.
  • A generic item whose bound picks behaviour by type alone, such as Default or Deserialize, can’t take one of your types. rawr says which bound when it builds the runner.
  • A main that is async needs a runtime’s attribute, as Rust does. Without one it is rustc’s E0752.

Checking

rawr check checks a program without running it. Then it runs cargo check, because rawr’s check accepts some code that rustc rejects. The Overview lists those cases.

rawr run runs cargo check beside the program. When rawr run ends with the program, cargo’s errors are printed after it.

Who runs a program

rawr runs a program itself or hands it to an installed extension.

ProgramRuns in
No dependencies and no native modulesrawr itself.
Dependencies in Cargo.toml or native modulesrawr-import, which compiles the native code with Cargo.
Uses the iced craterawr-iced, which reloads the app on save. Without rawr-iced, rawr-import runs it through generated bindings.

If the extension a program needs isn’t installed, rawr names it and prints the commands that install it. Set RAWR_VERBOSE=1 to see which binary ran a program.

Reload

rawr run watches every program it runs.

  • rawr-iced reloads an iced app when you save a marked file. Reload says what it keeps.
  • A native main picks up a body edit at its next call into the marked file, and keeps running.
  • A marked main in a native loop picks up a body edit at the loop’s next call into marked code, and keeps running.
  • Any other running program restarts when you save, with the same arguments. One line on stderr says so:
rawr: the source changed; restarting the program

A save that doesn’t compile prints its error, and the program keeps running.

A restarted program reads stdin on from where the old one stopped. Input the old program had already read doesn’t come back.

When the program ends and stdin is a terminal, rawr run waits. The next save runs the program again, with the same arguments. Ctrl-C ends the wait. When stdin isn’t a terminal, rawr run ends with the program and gives its exit status.

With rawr-import, a crate whose native code didn’t change reuses its earlier build.

Release builds

cargo build --release compiles the marked files natively too. No interpreter ships with the build.

rawr-iced’s #[preview] and #[widget] attributes come from the rawr-macros crate. Under Cargo they leave the item as written.

An app that embeds the rawr crate to run scripts does ship the interpreter. Embedding covers that case.

Speed

Calls into native code run at native speed. Keep a hot loop in a native module or a crate, and Cargo compiles it.
