Apps and libraries

rawr runs an app on the libraries it already uses. Cargo compiles them, and a save of a marked file reaches the running app.

How rawr runs an app

rawr has no framework of its own. Every crate in [dependencies] is native Rust. rawr run builds it with Cargo as cargo run does. The app’s unmarked modules are native too. The package’s own library is also native. A marked src/main.rs names src/lib.rs by the crate name as a Cargo binary does.

rawr interprets marked files. rawr run and rawr check pass apps with dependencies to rawr-import. rawr-import reads each library’s API and generates the bindings your marked files call. Nothing in rawr is written by hand for a particular library. Marked code calls the library’s own functions, types and traits under their own names.

An app with dependencies needs rawr-import. Imports provides the installation commands. The rawr command is required before installing rawr-import. A library item rawr cannot reach yet stops rawr run with an error at that item. Imports lists the known gaps.

cargo build --release compiles every file natively, including marked files. The marker is a comment. The release binary contains no rawr and behaves the same.

Where the marker goes

An app takes one of two shapes.

  • A marked main hands control to the library’s loop. iced uses this shape. main calls iced::run(update, view). iced calls your functions back. A running marked main describes this shape.
  • A native main owns the loop and calls marked modules. Terminal apps, games on winit and plain loops use this shape. A native main describes it.

In both shapes, the code that calls marked functions is native. It runs at native speed. Every library call made by marked code also runs at native speed.

What a save does

rawr run watches the files it runs. A save of a marked file reaches the app at its next call into marked code.

  • An edit to a function body or a private item swaps in place with the app’s state kept.
  • A struct or enum with new fields or variants restarts the app because native code may hold a value of the old shape.
  • An edit to main, a native file or Cargo.toml restarts the app.
  • A save that fails the check prints its error. The last good version keeps running.

A restart prints one line on stderr that says why:

rawr: `physics::Ball` changed its fields; restarting the program

When the edit shows depends on the loop. A loop that runs every frame shows it at the next frame. A library that redraws only after an event shows it at the next event.

rawr run runs cargo check beside the app. A running marked main describes how saves reach a running app. Checking explains when check errors are printed. Reload covers programs that use neither shape.

iced

An iced app’s marked main calls iced::run or iced::application(..).run(). iced owns the event loop, window and drawing. It calls update and view through Rust functions that the runner generates to call the current marked code. State and Message cross as your own named Rust types through generic calls. The window title is iced’s default for your crate.

Mark the file

These commands create a crate and add iced:

rawr new counter && cd counter
cargo add iced --git https://github.com/iced-rs/iced --rev be88873d38544455e26c7a104eb757da2cbbac6b
Cargo.toml
[package]
name = "counter"
version = "0.1.0"
edition = "2024"

[dependencies]
iced = { git = "https://github.com/iced-rs/iced", rev = "be88873d38544455e26c7a104eb757da2cbbac6b" }

counter is an ordinary Cargo crate. These examples use iced master at revision be88873d.

rawr run and cargo build share one build of iced with no other file. Your own cargo builds rawr’s runner with the project’s toolchain and config in the project’s target/. Imports explains the shared build.

This src/main.rs is iced’s counter example with // rawr as its first line:

src/main.rs
// rawr
use iced::Center;
use iced::widget::{Widget, button, column, text};

pub fn main() -> iced::Result {
    iced::run(Counter::update, Counter::view)
}

#[derive(Default)]
struct Counter {
    value: i64,
}

#[derive(Debug, Clone, Copy)]
enum Message {
    Increment,
    Decrement,
}

impl Counter {
    fn update(&mut self, message: Message) {
        match message {
            Message::Increment => {
                self.value += 1;
            }
            Message::Decrement => {
                self.value -= 1;
            }
        }
    }

    fn view(&self) -> impl Widget<Message> {
        column![
            button("Increment").on_press(Message::Increment),
            text(self.value).size(50),
            button("Decrement").on_press(Message::Decrement)
        ]
        .padding(20)
        .align_x(Center)
    }
}

Run

rawr run

rawr run opens the window. The first run compiles iced and the runner. It also reads iced’s API. This takes minutes. Later runs reuse the build.

cargo run compiles the same app natively. RAWR_VERBOSE=1 shows which binary ran the program.

What reloads

  • A save applies at the next message with the state kept.
  • iced builds the view again when a message arrives. Until then, the window shows the last view.
  • A struct or enum with new fields or variants restarts the app because iced may hold a value of the old shape.
  • An edit to main restarts the app because main runs only once.
  • An edit to a native file or Cargo.toml rebuilds it with Cargo and restarts the app.

Limits

iced’s counter, checkbox, slider, tooltip, pick_list and url_handler examples run unchanged but for the // rawr line. Each shows the title, the theme and the widgets that cargo run gives it.

iced::application(..).subscription(App::subscription) takes your method, and iced calls it with your state. update can return iced’s Tasks, such as Task::none() or window::latest().and_then(window::close). A function of iced’s that returns an impl Widget or an impl Program, such as iced::widget::iced(..) or iced::application(..), gives a value that marked code passes on to iced.

  • Other iced examples stop at the first item the generated bindings do not reach.
  • Previews do not render yet.

ratatui

A ratatui app’s main stays native and owns the terminal, loop and keys. Marked modules hold what the keys do and what the screen shows. The app needs no rawr crate or special API.

Mark the file

The app is an ordinary Cargo crate with ratatui and crossterm:

Cargo.toml
[dependencies]
crossterm = "0.29"
ratatui = "0.30"

The crate needs no other file. rawr run and cargo build share one build of ratatui as Imports explains.

The examples/tui crate in rawr’s repository is a to-do list. Its native main.rs is a ratatui loop:

src/main.rs
mod app;
mod ui;

fn main() -> std::io::Result<()> {
    let terminal = ratatui::init();
    let result = run(terminal);
    ratatui::restore();
    result
}

fn run(mut terminal: DefaultTerminal) -> std::io::Result<()> {
    let mut app = app::App::new();
    loop {
        terminal.draw(|frame| ui::draw(frame, &mut app))?;
        let Event::Key(key) = event::read()? else {
            continue;
        };
        // q quits; other keys go to the app.
        // ...
        app::update(&mut app, key);
    }
}

Its marked ui.rs draws on the Frame ratatui passes to the closure:

src/ui.rs
// rawr
use ratatui::Frame;
use ratatui::layout::{Constraint, Layout};
use ratatui::widgets::{Block, List, ListItem, ListState, Paragraph};

use crate::app::App;

pub fn draw(frame: &mut Frame, app: &mut App) {
    let areas = Layout::vertical([
        Constraint::Length(3),
        Constraint::Min(1),
        Constraint::Length(1),
    ])
    .split(frame.area());
    frame.render_widget(
        Paragraph::new(app.input.clone()).block(Block::bordered().title(" New to-do ")),
        areas[0],
    );
    let rows: Vec<ListItem> = app
        .todos
        .iter()
        .map(|todo| ListItem::new(todo.text.clone()))
        .collect();
    let mut list = ListState::default().with_selected(app.selected);
    frame.render_stateful_widget(List::new(rows).highlight_symbol("> "), areas[1], &mut list);
    app.selected = list.selected();
    // ...
}

Its marked app.rs holds the to-dos and what each key does to them.

Mark the modules you work on, and keep main native.

  • Native code owns ratatui::init, the loop, crossterm’s events, Terminal::draw and ratatui::restore.
  • Marked code holds the app’s state and what a key does to it.
  • Marked code draws through a function such as ui::draw that takes &mut Frame and builds ratatui’s widgets and layouts on it.

Values cross between native and marked code as they do for any native main. Numbers, bool, char, String, Vec, Option, Result and the structs and enums of marked modules cross. A key reaches the app as an enum of its own. Native code makes that enum from crossterm’s KeyCode.

A &mut Frame borrows the terminal’s buffer. It cannot be copied into marked code. rawr lends it for the length of the call. Each of frame’s methods reaches the native frame itself. The rendered content is in the buffer when draw returns. A borrowed parameter of any type your marked crate does not declare is lent the same way.

The borrow ends with the call as in Rust. A marked function cannot keep the frame in its return value or in an argument native code takes back. rawr rejects those borrows with E0515 or E0521. A copy kept anywhere else is unusable after the call. Using it produces E0597.

A widget’s state works as in Rust. render_stateful_widget borrows the ListState for its call. The list scrolls the selection into view in that state. An app can keep the selection and offset as plain numbers. draw creates the ListState from those numbers and reads them back after rendering.

A lent value can be an argument of a native call. It can also be the receiver of its methods. Native code can keep the ListState and lend it with the frame:

src/ui.rs
// rawr
use ratatui::widgets::{Block, List, ListState};
use ratatui::Frame;

pub fn draw(frame: &mut Frame, state: &mut ListState) {
    if state.selected().is_none() {
        state.select(Some(1));
    }
    let list = List::new(["alpha", "beta", "gamma"])
        .block(Block::bordered().title("list"))
        .highlight_symbol("> ");
    frame.render_stateful_widget(list, frame.area(), state);
}

main calls it as terminal.draw(|frame| ui::draw(frame, &mut state)). The list changes main’s own ListState as in Rust.

Run

The example is a package of rawr’s Cargo workspace. This command runs it from the repository root:

rawr run -p tui

rawr run examples/tui also runs it. cargo run -p tui runs it natively.

Change a title’s text in ui.rs and save. The new title shows within a second or two, with no key pressed. The to-dos and the selected row stay as they were.

What reloads

A save of a marked file reaches the program at its next call into that file.

  • An edit to a function body or private item swaps in place. The app’s state stays in native memory.
  • An edit to a signature, a struct’s fields or a public constant changes what native code sees. It requires a new native build. rawr restarts the program and prints one line on the restored screen:
rawr: `app::App` changed its fields; restarting the program
  • An edit to a native file restarts the program.
  • A save that does not compile leaves the program running with its last good code.

A loop waiting in event::read() draws only when an event arrives. A save is not an event.

After a save swaps in, rawr sends SIGWINCH to the program as a resized terminal does. crossterm turns it into Event::Resize. The loop draws again with the new code. The loop requires no changes for this. Any event that ends event::read() causes the loop to draw the next frame.

SIGWINCH is ignored by default. A program that does not listen for it does not notice it. rawr sends it only when the program’s stdin is a terminal. A loop that ticks with event::poll draws on its next tick.

rawr leaves the terminal as it found it, however the program ends.

  • Before the program starts, rawr saves the terminal’s settings.
  • A restart ends the program with SIGKILL. Its ratatui::restore() never runs.
  • After the program ends for any reason, rawr restores the settings if they changed. It then leaves the alternate screen and shows the cursor. It turns off mouse reports, bracketed paste, focus reports and the kitty keyboard flags.
  • On a panic, ratatui’s own panic hook restores the terminal first.

rawr writes nothing to the terminal while the program holds it raw. Its own lines wait until the terminal is restored. This includes the restart line, a failing save’s error and the build’s progress line.

At a terminal, the program writes to the terminal itself as under cargo run. crossterm, termion and colour detection see a terminal. A program that never touches the terminal requires no restoration.

Limits

  • Layout::areas, which returns an array whose length is a const generic, isn’t reached yet. Layout::split is.
  • Line::from and other From conversions of ratatui’s types can’t be called directly yet. A widget that takes impl Into<Text> takes a String.
  • A marked struct can’t hold a native value that native code keeps between calls, such as a ListState, yet.
  • A marked impl Widget doesn’t reach native code yet.
  • A failing save’s error shows when the program ends or restarts, not while the program holds the screen.
  • rawr resets the terminal only when the program changed its settings. A program that enters the alternate screen without raw mode isn’t reset.
  • A marked crate root whose main drives the loop itself never calls back into marked code. Each save restarts that program, and its state starts over. A running marked main says when a save swaps instead.
  • rawr-import runs on Unix systems only.

Other libraries and loops

Any other library runs through the same generated bindings.

A plain loop

A program needs no library to reload. The examples/islands crate has a native main with a loop that calls one marked module each tick:

src/main.rsshortened
mod physics;

fn main() {
    let mut ball = physics::Ball::new(20.0, 8.0);
    loop {
        ball.advance(0.25, 40.0);
        println!("{}", physics::render(&ball, 40));
        std::thread::sleep(std::time::Duration::from_millis(250));
    }
}

The real main stops after 20 seconds. Its marked physics.rs moves the ball and draws its line. A save takes effect at the next tick. The ball continues from where it was.

rawr run -p islands

winit

The examples/invaders crate is a space-invaders game on winit and softbuffer. Its native main.rs owns the window, keys and pixel framebuffer. Four marked modules hold the game’s rules, the invaders’ march, the hits and what each frame draws.

rawr run -p invaders

A save that changes a colour, speed or sprite’s shape shows at the next frame. The game keeps its score and invaders. A winit event loop must own the main thread. It owns that thread under rawr run as under cargo run.

Freya

Freya starts its own winit loop from a marked main. It calls a component again only when the component’s state changes. An edit shows at the next click or key.

Async runtimes

A marked crate root can have an async fn main under its runtime’s attribute such as #[tokio::main]. Cargo builds the runtime specified in Cargo.toml. rawr adds no runtime. An async main describes what works.

A library that reaches a part of Rust rawr doesn’t support yet stops with an error at that part. Imports lists the known gaps. An issue with a small reproduction helps close one.

Reload events

An app with an editor of its own can show what each save did. rawr run tells the running program through one environment variable.

RAWR_RELOAD_EVENTS names a Unix socket. It is set only under rawr run and under rawr start from rawr mcp. It is absent under cargo run. Its presence indicates that the program runs under rawr.

Each connection to the socket gets one JSON object per line in order from the moment it connects. The program can connect late or never connect. rawr does not wait for it.

EventMeans
{"event":"restarted","reason":"`Scale` changed its fields"}A save restarted this process, for that reason. It comes first, and only in a restarted process. A first start gets none.
{"event":"queued"}A save compiled. The program takes it at its next call into marked code. On macOS rawr asks its windows to redraw, so a frame that calls marked code takes it without waiting for input.
{"event":"swapped"}The program runs the saved code now. It kept its state.
{"event":"failed","message":"no field `missing` on type `Scale`","file":"/app/src/main.rs","line":11,"column":45,…}A save failed. The program keeps running the last good code. file, line and column are the error’s position, or null when it has none. Columns count from 1.
{"event":"preparing","reason":"`Cargo.toml` changed"}A save can’t compile inside this process against the native build it runs, for that reason. rawr prepares the program again, and queued or restarting follows.
{"event":"restarting","reason":"`Scale` changed its fields"}A save can’t swap into this process. rawr ends it and starts the program again.

These are the lines rawr mcp reads. Other events such as running can also appear on the stream. A reader skips any event it does not know.

The rawr-reload crate reads the stream. It has no dependencies. A native crate can take it as an ordinary dependency:

rawr-reload = { git = "https://github.com/airstrike/rawr" }
src/editor.rs
if let Some(outcomes) = rawr_reload::outcomes() {
    std::thread::spawn(move || {
        for outcome in outcomes {
            match outcome {
                rawr_reload::Outcome::Failed { message, at } => show_error(message, at),
                outcome => show_status(outcome.to_string()),
            }
        }
    });
}

outcomes() is None outside rawr run. Each next blocks until rawr reports what a save did. The stream is read on a thread of its own. Outcome has five variants: Restarted { reason }, Queued, Swapped, Failed { message, at } and Restarting { reason }. at is an Option<Span> with file, line and column. running() reports whether the variable is set.
