Apps and libraries

rawr has no framework of its own. An app keeps the libraries it already uses, Cargo compiles them, and the files you mark call them. A save reaches the running app.

How rawr runs an app

Every crate in [dependencies] is native Rust. rawr run builds it with Cargo, as cargo run does. The app’s unmarked modules are native too. So is the package’s own library: a marked src/main.rs names src/lib.rs by the crate name, as a Cargo binary does.

rawr-import reads each library’s API and generates the bindings your marked files call. Nothing in rawr is written by hand for a particular library. Your marked code calls the library’s own functions, types and traits, under their own names.

An app with dependencies needs rawr-import. Imports says how to install it, and lists the parts of Rust that don’t cross yet. A library item rawr can’t reach yet stops rawr run with an error at that item.

cargo build --release compiles every file natively, the marked ones included. The marker is a comment, and no interpreter ships.

Where the marker goes

An app takes one of two shapes.

  • A marked main hands control to the library’s loop. iced works this way: main calls iced::run(update, view), and iced calls your functions back. A running marked main describes it.
  • A native main owns the loop and calls marked modules. A terminal app, a game on winit or a plain loop works this way. A native main describes it.

In both shapes, the code that calls your marked functions is native. It runs at native speed, and so does every library call your marked code makes.

What a save does

rawr run watches the files it runs. A save of a marked file reaches the app at its next call into marked code.

  • An edit to a function body or to a private item swaps in place. The app keeps its state.
  • A struct or enum with new fields or variants restarts the app, since native code may hold a value of the old shape.
  • An edit to main, to a native file or to Cargo.toml restarts the app too.
  • A save that fails the check prints its error. The last good version keeps running.

A restart prints one line that says why:

rawr: `physics::Ball` changed its fields; restarting the program

When the edit shows depends on the loop. A loop that runs every frame shows it at the next frame. A library that redraws only after an event shows it at the next event. Reload has the details.

iced

iced is a Rust dependency like any other. rawr run and rawr check hand an iced app to rawr-import, as they hand over any program with dependencies in Cargo.toml. rawr-import reads iced’s API and generates the bindings your marked files call. Nothing in rawr is written by hand for iced. Set RAWR_VERBOSE=1 to see which binary ran a program.

Your main calls iced’s own iced::run(update, view) or iced::application(..).run(), as an ordinary generic call. iced runs the event loop, the window and the drawing. Your State and Message cross into it as Rust types of their own, named as you name them, so the window’s title is iced’s default for your crate. Your update and view cross as Rust functions the runner makes, which call the version of your code that is current. Generic items says how.

Mark the file

An iced app needs rawr-import. Imports gives the commands. Install the rawr command first.

Make a crate and add iced to it:

rawr new counter && cd counter
cargo add iced --git https://github.com/iced-rs/iced --rev be88873d38544455e26c7a104eb757da2cbbac6b

counter is an ordinary Cargo crate. The examples on this page use iced master at revision be88873d.

Cargo.toml
[package]
name = "counter"
version = "0.1.0"
edition = "2024"

[dependencies]
iced = { git = "https://github.com/iced-rs/iced", rev = "be88873d38544455e26c7a104eb757da2cbbac6b" }

rawr run and cargo build share one build of iced, with no other file. Your own cargo builds rawr’s runner with the project’s toolchain and config, in the project’s target/. Imports explains it.

Replace src/main.rs with iced’s own counter example, with // rawr as its first line:

src/main.rs
// rawr
use iced::Center;
use iced::widget::{Widget, button, column, text};

pub fn main() -> iced::Result {
    iced::run(Counter::update, Counter::view)
}

#[derive(Default)]
struct Counter {
    value: i64,
}

#[derive(Debug, Clone, Copy)]
enum Message {
    Increment,
    Decrement,
}

impl Counter {
    fn update(&mut self, message: Message) {
        match message {
            Message::Increment => {
                self.value += 1;
            }
            Message::Decrement => {
                self.value -= 1;
            }
        }
    }

    fn view(&self) -> impl Widget<Message> {
        column![
            button("Increment").on_press(Message::Increment),
            text(self.value).size(50),
            button("Decrement").on_press(Message::Decrement)
        ]
        .padding(20)
        .align_x(Center)
    }
}

Run

rawr run

cargo run compiles the same app natively. A release build doesn’t need the interpreter.

The first rawr run compiles iced and the runner in the project’s target/, and reads iced’s API. That takes minutes. Later runs reuse the build.

What reloads

An iced app’s marked main hands control to iced’s event loop. iced calls your update and view back, so a save reaches the app as A running marked main describes.

  • A save applies at the next message, with the state kept.
  • iced builds the view again when a message arrives, so until then the window shows the last view.
  • A struct or enum with new fields or variants restarts the app, since iced may hold a value of the old shape.
  • An edit to main restarts the app, since main runs only once.
  • An edit to a native file or to Cargo.toml rebuilds it with Cargo and restarts the app.

One line on stderr says why the app restarted.

The save prints its error, and the last good code keeps running.

rawr run also runs cargo check beside the app. Checking says when its errors are printed.

Limits

  • iced’s counter, checkbox, slider, tooltip, pick_list and url_handler examples run unchanged but for the // rawr line, with the title, the theme and the widgets cargo run gives them.
  • iced::application(..).subscription(App::subscription) takes your method, which iced calls with your state. Tasks work as iced gives them, so update can return Task::none() or window::latest().and_then(window::close).
  • A function of iced’s that gives an impl Widget or an impl Program, as iced::widget::iced(..) and iced::application(..) do, works as a value you pass on to iced.
  • iced’s other examples run as the generated bindings reach the items they use. One that stops shows an error at the gap. Imports lists the known gaps.

Previews don’t render yet. Previews says what remains of them.

ratatui

A ratatui app needs no rawr crate and no special API. You write it as ratatui’s own examples do. main owns the terminal, the loop, the keys and the drawing. One module that starts with // rawr holds what the keys do and what the screen says. Under rawr run that module is interpreted, and cargo build --release compiles all of it natively.

Mark the file

The app is an ordinary Cargo crate with ratatui and crossterm:

Cargo.toml
[dependencies]
crossterm = "0.29"
ratatui = "0.30"

rawr-import runs it, as it runs every crate with dependencies. Imports says how to install it. The crate needs no other file. rawr run and cargo build share one build of ratatui, as Imports explains.

The examples/tui crate in rawr’s repository is a to-do list. Its native main.rs is a plain ratatui loop:

src/main.rs
mod app;
mod ui;

fn main() -> std::io::Result<()> {
    let terminal = ratatui::init();
    let result = run(terminal);
    ratatui::restore();
    result
}

fn run(mut terminal: DefaultTerminal) -> std::io::Result<()> {
    let mut app = app::App::new();
    loop {
        terminal.draw(|frame| ui::draw(frame, &mut app))?;
        let Event::Key(key) = event::read()? else {
            continue;
        };
        // q quits; other keys go to the app.
        // ...
        app::update(&mut app, key);
    }
}

Its marked ui.rs draws the screen on the Frame ratatui hands the closure, as any ratatui app does:

src/ui.rs
// rawr
use ratatui::Frame;
use ratatui::layout::{Constraint, Layout};
use ratatui::widgets::{Block, List, ListItem, ListState, Paragraph};

use crate::app::App;

pub fn draw(frame: &mut Frame, app: &mut App) {
    let areas = Layout::vertical([
        Constraint::Length(3),
        Constraint::Min(1),
        Constraint::Length(1),
    ])
    .split(frame.area());
    frame.render_widget(
        Paragraph::new(app.input.clone()).block(Block::bordered().title(" New to-do ")),
        areas[0],
    );
    let rows: Vec<ListItem> = app
        .todos
        .iter()
        .map(|todo| ListItem::new(todo.text.clone()))
        .collect();
    let mut list = ListState::default().with_selected(app.selected);
    frame.render_stateful_widget(List::new(rows).highlight_symbol("> "), areas[1], &mut list);
    app.selected = list.selected();
    // ...
}

Its marked app.rs holds the to-dos and what each key does to them.

Mark the modules you are working on, and keep main native.

  • Native code owns the terminal: ratatui::init, the loop, crossterm’s events, Terminal::draw and ratatui::restore.
  • Marked code holds the app’s state and what a key does to it.
  • Marked code draws, too. A marked function may take &mut Frame, and build ratatui’s widgets and layouts on it, as ui::draw does.

Values cross between native and marked code as they do for any native main. Numbers, bool, char, String, Vec, Option, Result and the structs and enums of marked modules cross. A key reaches the app as an enum of its own, which native code makes from crossterm’s KeyCode.

A &mut Frame borrows the terminal’s buffer, so it can’t be copied into marked code. rawr lends it instead, for the length of the call. Each of frame’s methods reaches the native frame itself, so what draw renders is in the buffer when the call returns. A borrowed parameter of any type your marked crate doesn’t declare is lent the same way.

The borrow ends with the call, as in Rust. A marked function can’t keep the frame in what it returns, or in an argument native code takes back. rawr refuses that with Rust’s borrow rule (E0515, E0521). A copy kept anywhere else is useless after the call, and using it says so (E0597).

A widget’s state works as in Rust. render_stateful_widget borrows the ListState for its call, and the list scrolls the selection into view in it. Here the app keeps the selection and the offset as plain numbers, and draw makes the ListState from them and reads them back.

A lent value can be an argument of a native call, as well as the receiver of its methods. So native code can keep the ListState and lend it with the frame:

src/ui.rs
// rawr
use ratatui::widgets::{Block, List, ListState};
use ratatui::Frame;

pub fn draw(frame: &mut Frame, state: &mut ListState) {
    if state.selected().is_none() {
        state.select(Some(1));
    }
    let list = List::new(["alpha", "beta", "gamma"])
        .block(Block::bordered().title("list"))
        .highlight_symbol("> ");
    frame.render_stateful_widget(list, frame.area(), state);
}

main calls it as terminal.draw(|frame| ui::draw(frame, &mut state)). The list changes main’s own ListState, as in Rust.

Run

The example is a package of rawr’s Cargo workspace. Run it from the repository’s root:

rawr run -p tui

rawr run examples/tui runs it too. cargo run -p tui runs it natively.

Change a title’s text in ui.rs and save. The new title shows within a second or two, with no key pressed. The to-dos you added and the selected row stay as they were.

What reloads

A save of a marked file reaches the program at its next call into that file.

  • An edit to a function body or to a private item swaps in place. The app’s state lives in native memory, so it carries on.
  • An edit that changes what native code sees needs a new native build. That covers a signature, a struct’s fields and a public constant. rawr restarts the program and prints one line on the restored screen:
rawr: `app::App` changed its fields; restarting the program
  • An edit to a native file restarts the program too.
  • A save that doesn’t compile leaves the program running with its last good code.

A loop that waits in event::read() draws only when an event comes. A save is no event, so the new code would wait for a key.

After a save swaps in, rawr sends SIGWINCH to the program, as a resized terminal does. crossterm turns it into Event::Resize, and the loop draws again with the new code. Your loop needs nothing for this. Any event that ends event::read() draws the next frame.

SIGWINCH is ignored by default, so a program that doesn’t listen for it doesn’t notice. rawr sends it only to a program whose stdin is a terminal.

A loop that ticks with event::poll draws on its next tick anyway.

rawr leaves the terminal as it found it, however the program ends.

  • Before the program starts, rawr saves the terminal’s settings.
  • A restart ends the program with SIGKILL, so its ratatui::restore() never runs.
  • After the program ends for any reason, rawr puts the settings back when they changed. It then leaves the alternate screen and shows the cursor. It turns off mouse reports, bracketed paste, focus reports and the kitty keyboard flags.
  • On a panic, ratatui’s own panic hook restores the terminal first.

While the program holds the terminal raw, rawr writes nothing to it. Its own lines wait until the terminal is restored. That covers the restart line, a failing save’s error and the build’s progress line.

At a terminal, the program writes to the terminal itself, as under cargo run. So crossterm, termion and colour detection see a terminal.

A program that never touches the terminal costs nothing here. Its settings don’t change, so rawr restores nothing.

cargo build --release compiles the marked module natively, like any other module. The binary has no rawr in it and behaves the same.

Limits

  • Layout::areas, which gives an array whose length is a const generic, isn’t reached yet. Layout::split is.
  • Line::from and other From conversions of ratatui’s types aren’t called directly yet. A widget that takes impl Into<Text> takes a String.
  • A marked struct can’t hold a native value such as a ListState that native code keeps between calls yet.
  • A marked impl Widget doesn’t reach native code yet.
  • A failing save’s error shows when the program ends or restarts, not while it holds the screen.
  • rawr resets the terminal only when the program changed its settings. A program that enters the alternate screen without raw mode isn’t reset.
  • The marked module may also be the crate root with a marked main. A loop that main drives itself never calls back into marked code, so each save restarts the program, and its state starts over. A running marked main says when a save swaps instead.
  • rawr-import runs on Unix systems.

Other libraries and loops

A library not on this page runs the same way, through the same generated bindings.

A plain loop

A program needs no library to reload. The examples/islands crate is a native main with a loop that calls one marked module each tick:

src/main.rsshortened
mod physics;

fn main() {
    let mut ball = physics::Ball::new(20.0, 8.0);
    loop {
        ball.advance(0.25, 40.0);
        println!("{}", physics::render(&ball, 40));
        std::thread::sleep(std::time::Duration::from_millis(250));
    }
}

The real main stops after 20 seconds. Its marked physics.rs moves the ball and draws its line. A save takes effect at the next tick, and the ball carries on from where it was.

rawr run -p islands

winit

The examples/invaders crate is a space-invaders game on winit and softbuffer. Its native main.rs owns the window, the keys and a pixel framebuffer. Four marked modules hold the game’s rules, the invaders’ march, the hits and what each frame draws.

rawr run -p invaders

A save that changes a colour, a speed or a sprite’s shape shows at the next frame. The game keeps its score and its invaders. A winit event loop must own the main thread, and under rawr run it does, as under cargo run.

Freya

Freya, for example, starts its own winit loop from a marked main. It calls a component again only when the component’s state changes, so an edit shows at the next click or key.

A library that reaches a part of Rust rawr doesn’t support yet stops with an error at that part. Imports lists the known gaps, and an issue with a small reproduction helps close one.

Async runtimes

A marked crate root may have an async fn main under its runtime’s attribute, such as #[tokio::main]. The runtime is the one in your Cargo.toml, built by Cargo. rawr adds none. An async main says what works.

Reload events

An app with an editor of its own can show what each save did. rawr run tells the running program through one environment variable.

RAWR_RELOAD_EVENTS names a Unix socket. It is set only under rawr run, and under rawr start from rawr mcp. Under cargo run it is absent. Its presence is the sign that the program runs under rawr.

Each connection to the socket gets one JSON object per line, in order, from the moment it connects. The program may connect late, or never. rawr doesn’t wait for it.

EventMeans
{"event":"restarted","reason":"`Scale` changed its fields"}A save restarted this process, for that reason. It comes first, and only in a restarted process. A first start gets none.
{"event":"queued"}A save compiled. The program takes it at its next call into marked code.
{"event":"swapped"}The program runs the saved code now. It kept its state.
{"event":"failed","message":"no field `missing` on type `Scale`","file":"/app/src/main.rs","line":11,"column":45,…}A save failed. The program keeps running the last good code. file, line and column are the error’s position, or null when it has none. Columns count from 1.
{"event":"restarting","reason":"`Scale` changed its fields"}A save can’t swap into this process. rawr ends it and starts the program again.

The lines are the ones rawr mcp reads. Other events, such as running, may appear on the stream as well. A reader skips any event it doesn’t know.

The rawr-reload crate reads the stream. It has no dependencies, and a native crate can take it as an ordinary dependency:

rawr-reload = { git = "https://github.com/airstrike/rawr" }
src/editor.rs
if let Some(outcomes) = rawr_reload::outcomes() {
    std::thread::spawn(move || {
        for outcome in outcomes {
            match outcome {
                rawr_reload::Outcome::Failed { message, at } => show_error(message, at),
                outcome => show_status(outcome.to_string()),
            }
        }
    });
}

outcomes() is None outside rawr run. Each next blocks until rawr says what a save did, so read it on a thread of its own. Outcome has five variants: Restarted { reason }, Queued, Swapped, Failed { message, at } and Restarting { reason }. at is an Option<Span> with file, line and column. running() says whether the variable is set.
